## API design review (open)

- [ ] **Callback context / instance access review** (user ruling: review first, then discuss - change nothing yet). Trigger: widening `createItemContentElFn` with a query ctx would make `createHighlightedTextEl` one-liners possible without the `let sel` closure recipe. Before that, inventory how EVERY settings callback and protected hook reaches instance state and pick ONE consistent contract. Current shapes: bare domain params (`filterFn(item, query)`, `itemDisabledFn(item)`, `itemToStringFn(item)`); narrow ctx objects (`createTriggerContentElFn({ chosenItems, items })`, `createTriggerArrowContentElFn({ isOpened })`); nothing (`onOpen` / `onClose`). No callback receives the instance, and `this` is nowhere documented (a non-arrow settings fn invoked as `this.settings.fn(...)` accidentally sees the SETTINGS object as `this` - decide whether to neutralize or spec that too). The same review covers the adjacent user question: whether `void` mutators (`setItems`, `setChosenItems`, `setPlaceholder`, ...) should return `this` for chaining. Options to weigh: keep narrow ctx objects (current precedent; an added param is TS-backward-compatible), pass the instance itself (max reach, but promotes the whole class surface into every callback's API), or documented `this` binding (hostile to arrow fns). Outcome applies back to the highlight ctx.

## Accepted limitations (known, deliberately not planned)

- A single set of `.d.ts` serves both ESM and CJS. TypeScript consumers on `moduleResolution: nodenext` who `require()` the package hit the classic dual-types edge (bundler / `import` consumers are unaffected). Fixing it properly means bundling declarations into per-format `.d.ts` / `.d.cts` - revisit if anyone actually hits it.
- Per-item click listeners stay (no event delegation) until a benchmark shows a win; lazy render already bounds the cost. See the event-delegation deferral in `archive/roadmap-v0.0.1.md`.
- The popup positions with `position: fixed` from INSIDE the component subtree (no body portal - rationale and the full two-class failure taxonomy in `DESIGN.md` "In-place popup (no body portal)"). Browsers WITH the Popover API (all current ones) get the implemented top-layer enhancement, which removes both failure classes; browsers WITHOUT it keep them permanently: a containing-block-creating ancestor displaces the popup, and an ancestor stacking context can trap its paint order under overlapping higher-ordered content. That residue is accepted, and a body portal stays rejected either way.
