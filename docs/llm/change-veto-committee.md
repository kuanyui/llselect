# Committee: vetoing a user change, the change reason, and the item language

Agent-facing record of the committee convened on three API questions raised by a survey of other select libraries and by the owner's own use of llselect 0.0.9 in another project (a mode select that must be confirmed in a modal dialog before it switches). Six members, each a fresh read-only session at its highest effort, got the same brief: Opus 4.8, Opus 5, Sonnet 4.6, Sonnet 5, Codex Sol, Codex Astra. Codex 5.5 was skipped: the Codex CLI answers that gpt-5.5 is not supported with a ChatGPT account. Two rounds ran. Round one, on the owner's instruction two members at a time, took 33 minutes; round two, three at a time, took about 15 minutes of member time, with a sampler reading memory every ten seconds: at most 324 MB per `claude -p` process and 330 MB per `codex` process, and never less than 1.06 GB available of the 2.9 GB the container reports. The first run of round two stalled after its first batch because the runner's bare `wait` also waited for the sampler loop; the second batch ran after the fix. Raw outputs stayed in the session scratchpad; this file carries the briefs in short, the corrections, the positions, the tallies and the recommendation. The owner ratified the Q1 event shape after round one and, after round two, the Q2 reason set and field name together with the plain string union for its values (round two's Q5), with the value meanings written as bullets on the type alias and on the `meta.reason` field docstring; then Q4 as close, the owner's call against the recommendation below, with its scope written into the docstring; then the item-language setting as `itemToLangFn` with the protected `itemToLang`, the owner's call against round two's 6:0 for `itemToLanguageTagFn`: HTML's own attribute name, the `ariaLabel` precedent for attribute values, and no second sense of "tag" beside the chips; its docstring must say the value is a BCP 47 code such as `ja`, not a language name, and carry the smallest example, a three-language picker on an English page with the rendered row before and after, because the need is rare and a reader must understand it at a glance; the ratified decisions go to `DESIGN.md`, `A11Y.md` and `naming-conventions.md`.

## The brief in short

- Q1: should a setting let an app block one user change at the moment it happens, and in what shape? A: a boolean predicate `*Fn` (only `false` blocks). B: a function returning the value to commit. C: a protected gate method only, no setting. D: status quo plus a README recipe for the revert-inside-`onChange` pattern. E: an `on*` event whose argument carries an explicit `preventDefault()`, return value ignored. Sub-questions: scope (`user` = the library's own pointer and keyboard paths only; `all` = every setter call), the gate's place (entry layer or inside the setters), and whether a vetoed single-mode pick still closes the popup.
- Q2: should `LLSelectChangeMeta` gain a closed `reason` union and the one affected `item`? Granularity `minimal` (`'choose' | 'unchoose' | 'clear' | 'set' | 'items'`) or `control-level` (plus `'tag-remove'`, `'choose-all'`, `'unchoose-all'`, `'toggle'`, `'bulk'`); field name `reason` or `action`.
- Q3: should an item's language reach the option row, whose `aria-label` the library pins to `itemToString` when the content is custom? A: `itemToLangFn`. B: docs only, a subclass recipe. C: copy the content element's `lang` to the row automatically.
- The owner's stated preference for Q1, given as one argument and not a ruling: return-value cancellation is implicit (`return false` versus `return` versus `return undefined`), an explicit call in the style of `event.preventDefault()` is not.
- Evidence from the dogfooding session: reverting inside `onChange` never paints the blocked value (both writes happen in one task), but `onChange` and `onChosenChanged` run twice, every side effect must sit after the check, and the pattern rested on the nested-setter guarantee that, at the time, only a protected field's docstring stated (the `onChange` docstrings state it now, DOCUMENTATION-638); the subclass route works for single mode but leaks the chip remove button, the choose-all row and the clear button in multiple mode; opening a modal directly inside `onChange` is safe: when the dialog takes focus, the `focusout` handler closes the popup, and `close()` never reclaims focus that already left the select widget.

## Corrections to the brief, verified by the members

- `withUserChangeSource` restores the previous attribution in a `finally`, while `fireChange` resets `changeSource` to `'api'` before any observer runs (Opus 5, Codex Sol, Codex Astra). So the attribution is consumed by the FIRST change of a gesture: an action row whose `onActivate` calls two setters reports `'user'` for the first and `'api'` for the second, and an action row that calls `setItems` first makes the reconciliation's `onChange` report `'user'`. Both are pre-existing quirks; neither test file pins them (`test/events.test.ts` enumerates the four library-owned paths; `test/action-rows.test.ts` checks one change).
- The `withUserChangeSource` docstring listed four paths and omitted the action rows, which the code does wrap (Codex Sol, Codex Astra); fixed, DOCUMENTATION-640.
- The entry layer cannot compute `next` for an action row: the library runs an opaque app callback there and performs no selection operation itself (Codex Sol).
- The `onClose` docstring did not say what `null` means, against the CLAUDE.md rule (Codex Sol); fixed, DOCUMENTATION-637.
- `onFilterQueryChange` has no paired protected hook; only open, close and the chosen change have one (Codex Sol).
- Settings are frozen by convention with two runtime exceptions, `placeholder` and `uiTranslationPack`; the translation pack's message functions do get `this` (Codex Sol, Codex Astra). Not material here.
- The "dropped or reordered" clause of the reconciliation is multiple-only; single fires only on a drop (Opus 4.8).
- "Disabled items never reach the hook" needs one qualification: the clear button wipes chosen disabled items too, so a veto on clear concerns them (Codex Astra).
- One `reason` plus one `item` cannot replace the ui-select bridge's diff for bulk writes and clears; it only shortcuts the single-item cases (Codex Astra).
- The out-of-scope items the brief called "tracked separately" (a close reason, scroll-to-end, a maximum count) were not yet in `TODO.md`; only the active-option change event was (Sonnet 5).
- A blank `itemToString` writes a blank `aria-label`, and the accessible-name computation then falls back to the content (Codex Astra). Pre-existing edge, not for this round.

## Positions and tally

### Q1 - the shape

- E, an `on*` event with an explicit cancel call: Opus 4.8, Opus 5, Sonnet 4.6, Codex Sol, Codex Astra (5). A, a boolean predicate: Sonnet 5 (1). Nobody took B, C or D, though Opus 4.8 calls D-now / E-later coherent if the owner weights YAGNI heavily, and Opus 5 wants D's documentation shipped alongside E.
- The argument that decided it for most: the return type `void` removes the `undefined` ambiguity by construction, and `preventDefault()` is vocabulary every web developer knows. Opus 5 adds a structural one: a cancel cannot be undone by a later handler, so a protected hook and the setting can BOTH run and either may cancel, like `onChosenChanged` / `onChange`; a predicate makes the protected method the single answer, and a subclass override that forgets `super` silently drops the app's setting.
- Sonnet 5 for A: a veto is a decision, which this API puts in `*Fn` predicates, while `on*` everywhere else means "this already happened"; TypeScript rejects a `boolean`-typed function that returns `undefined`, which closes most of the sentinel risk; a cancel method on a settings argument is new, and `preventDefault` names the DOM method the library already calls on the originating keydown.
- Names, from the E voters: setting `onBeforeChange` (all five; it reads like `beforeinput` / `beforetoggle`); method `preventDefault()` over `cancel()` (all five; "cancel" also reads as "the user cancelled"); a readable `defaultPrevented` (all five, so the hook and the setting can see each other's decision); protected hook `onChosenChanging` (all five). The event's type: a separate exported interface `LLSelectBeforeChangeEvent<T>` (Opus 4.8, Codex Sol: the `onChange` meta bag must stay data-only) versus one that extends `LLSelectChangeMeta<T>` (Opus 5, Codex Astra). Sonnet 4.6 would put `next` and `previous` inside the event object and give the setting a single parameter; the other four keep `(next, previous, event)`.
- Contract points named by several members: `preventDefault()` counts only while the handler is on the stack, a call from a stored reference later does nothing; a veto leaves the chosen state and the selection DOM untouched and fires no `onChange`, while the activation may already have moved the active row; the protected hook runs first, the setting second, both run even when already cancelled; equality is checked before the hook, so a no-op pick never asks; the confirmation flow is veto now, ordinary setter later, which reports `'api'`.

### Q1 - scope and mechanics

- Scope `user`: all six. The AngularJS model write-back is `'api'` on purpose, and a hook that could block it would desynchronise `ngModel` from the select widget with nothing to resynchronise it (Opus 5, Sonnet 5); the `setItems` reconciliation is never vetoable, since a veto would keep an entry the list no longer holds (all).
- The gate's place: at the entry layer, in each library-owned user path, before the untouched `void` setter (Opus 4.8, Opus 5, Sonnet 4.6, Sonnet 5). Opus 5's reason is the consumed attribution above: a source test inside the setters would skip the hook for the second change of one gesture. Inside the setters under user attribution, so that an action row's own setter calls are gated too (Codex Sol, Codex Astra); Codex Astra would then replace the consumed flag with scoped attribution. The entry-layer camp treats an action row's setters as the app's own command, outside the hook.
- Disabled rules stay in front of the gate: a disabled control or item returns before the hook runs (all).

### Q1 - a vetoed single-mode pick

- Close anyway: Opus 4.8, Sonnet 5, Codex Sol, Codex Astra (4). Stay open: Opus 5, Sonnet 4.6 (2).
- For close: one invariant, activation closes; the confirmation flow wants the popup gone before the modal; jQuery UI does it and the measured subclass route did it; `open()` reopens for the "pick another" case.
- For stay: the simplest contract, a vetoed change changes nothing; the user wanted that item and a close abandons the intent; an app that wants the popup gone calls `close()` in the handler, while an app that wants it open cannot undo a library close.
- A premise that weighed on the close votes, refuted in round two (see "The brief's premise that fell" below): the brief claimed that `dialog.showModal()` hides every popover behind the library's back, so that under stay a handler opening a modal without `close()` would leave the select widget believing it is open while its popover is hidden. What stands: under close, a filterable single select loses its typed query on a veto.

### Q2 - reason and item

- `minimal`: all six. `reason`: all six; `action` already names action rows and keyboard actions in this project, one word one concept (Opus 5, Codex Sol); two of the values name consequences, not actions (Sonnet 5).
- Two definition fixes from Opus 5, accepted by the others' shapes: `reason` names the operation on the data and `source` names the initiator, so a programmatic `toggleItem` that adds is `{ source: 'api', reason: 'choose' }`; the choose-all row and every bulk op are `'set'` (refined when shipped: a bulk op whose result is empty is `'clear'`, and `item` rides with `'choose'` / `'unchoose'`; DESIGN.md "Change reason").
- Type shape: `LLSelectChangeMeta<T = unknown>` with a defaulted type parameter so existing annotations keep compiling (Opus 4.8, Opus 5, Sonnet 4.6, Codex Astra); Sonnet 5 notes that any standalone annotation of the non-generic name is a type-level break. `item` as an optional field present only on `'choose'` / `'unchoose'` (four members) or as a discriminated union on `reason`, where `item` exists exactly when the reason is one of those two (Codex Sol).
- Q2 ships even if Q1 is rejected: all six. Q1 without Q2: yes but less expressive (five); reluctantly, land Q2 first and Q1 on top (Opus 5).

### Q3 - the item language

- A, `itemToLangFn: ((item: T) => string | null) | null` with a protected `itemToLang(item)`: all six. C rejected as implicit and, worse, useless for the plain-text branch, which is the language-picker case (Opus 5, Sonnet 4.6). B rejected as a four-line subclass for a one-attribute fix.
- Where it applies: the option row (six); the single select's default trigger text (six); the single select's hidden value mirror (Opus 4.8, Opus 5, Sonnet 5, Codex Sol, Codex Astra; Sonnet 4.6 fears a `lang` in the `aria-labelledby` chain); the tag chip's text (Opus 4.8, Opus 5, Sonnet 5, Codex Astra; Sonnet 4.6 and Codex Sol leave tags out). Not the chip's remove button, whose one `aria-label` mixes pack text with item text (all); not the multiple-mode count summary or combined mirror (Opus 5, Codex Sol, Codex Astra). Groups and action rows stay subclass territory until asked (all); `groupKeyToLangFn` is the obvious later sibling.
- Docstring points: the value is a BCP 47 tag such as `ja`, not a language name, said in the first bullet (Opus 5); `null` from the function or as the setting sets no attribute and removes one set earlier (Codex Astra); the empty string keeps HTML's own meaning, language unknown (Codex Astra); a real screen reader must still be heard, because a `lang` attribute does not establish pronunciation (Codex Astra).
- Name: `itemToLangFn`, since the name should name the attribute it writes; `itemToLanguageTagFn` only if the owner wants the tag-not-name misreading closed in the name itself (Opus 5).

## Round two: the popup after a vetoed pick, the reason values, the setting's name, the gate

The owner ratified E, `onBeforeChange`, after round one, and asked for a dedicated round on the popup question because of a semantic worry: `preventDefault()` cancels an event's default action, and if a pick's default action is "commit and close", a faithful cancel covers both. Round two also asked how the `reason` values should be declared so that each value carries a docstring an editor shows (the owner floated a `const enum`), what the item-language setting should be called (the owner found `itemToLangFn` not explicit), and whether the entry-layer gate holds.

### The brief's premise that fell

- Round one's brief, and the round-two brief after it, asserted that under "stay" a modal opened from the handler desyncs the select widget, because `dialog.showModal()` force-hides every popover and only the next `close()` resyncs. Opus 5 and Codex Astra refuted it with the sources: while open, the library listens for `focusout` on `rootEl` and calls `close()` whenever focus leaves the root (`src/base.ts`, `attachFocusOut`), and `showModal()` moves focus into the dialog, so a modal that takes focus outside the select widget closes it synchronously under either rule. Codex Astra adds the HTML standard: the "hide popovers until" steps walk the showing auto and hint popover lists only, so a `popover="manual"` element is never hidden when a modal opens, and the hide-popover algorithm returns without throwing for an already-hidden element. The repository's own "Force-hide resilience" note, the comment in `close()` and the popover test's injected throw assert the force-hide behavior the standard does not describe (FIXME NEEDS-VERIFICATION-636).
- What survives of the modal argument: an overlay that never takes focus leaves the popup shown; while a modal is open the rest of the document, the popup included, is inert, and the `focusout` handler closes the select widget once the modal takes focus. Under both rules the app may call `close()` in the handler.
- Smaller corrections: `LLSelectChosenState` and `LLSelectChosenItemsOrder` carry no per-value bullets on their aliases (Codex Sol, Codex Astra); this tsconfig's `isolatedModules` implies `preserveConstEnums`, so a `const enum` would be preserved in the library build, and the documented mitigation is the publisher removing `const` from shipped declarations, not consumers setting `preserveConstEnums` (Codex Sol, Codex Astra); `src/i18n.ts` already uses "language id" for the primary subtag alone, a narrower thing than the full tag (Sonnet 5); under "close", `open()` called inside the handler is a no-op because the select widget is still open, so a reopen must be deferred (Codex Sol).

### Q4 - close or stay

- Close: Opus 4.8, Sonnet 4.6, Sonnet 5, Codex Sol (4). Stay: Opus 5, Codex Astra (2). The same 4:2 tally as round one, with Sonnet 4.6 and Codex Astra swapping sides; the four close votes were cast with the fallen premise in the brief: Sonnet 4.6 names the desync as its deciding argument, Sonnet 5 as a supporting one beside the activation invariant, and Opus 4.8 and Codex Sol argue from the activation invariant and the event's named default.
- For close: the event's default action is the change, closing belongs to the activation and runs either way, as a multiple-mode activation keeps the popup open either way; today re-picking the chosen item changes nothing and still closes, so a vetoed pick behaves like that no-change activation, and "stay" would make the veto the one no-change activation that keeps the popup open (Sonnet 5); a lost filter query is visible and recoverable, a silent desync is not (Sonnet 4.6, before the refutation).
- For stay: recoverability is asymmetric, `close()` is public and one line, while `close()` wipes the query and the input and nothing restores them (Opus 5, Codex Astra); keyboard users retry in place instead of being ejected to the trigger (Opus 5); the contract is one mode-independent sentence, "a vetoed change commits nothing and triggers no automatic close" (Codex Astra's wording, since the click path already moved the focused row before activation); `beforetoggle` and `beforeinput` each cancel exactly the transition they name (Opus 5); precedent is inconclusive, jQuery UI and Syncfusion close, Select2 and SlimSelect stay, Kendo differs by input path (all).
- The third option, stay plus a `toggle` listener that treats an external hide as `close()`: every member keeps it out of this decision; the event is queued a task late, must ignore the library's own hide and must not re-enter the focus return; real-browser facts first (TODO "Popover external-hide resync").

### Q5 - how the reason values are declared

- `as const` object plus the derived union type, scoped to the new reason type: Sonnet 4.6, Sonnet 5, Codex Sol, Codex Astra (4). Keep the plain string union: Opus 4.8 (the object pattern is all seven value types or none, and the hover is a minor convenience), Opus 5 (reversible: adding the const later keeps the identical union type) (2).
- Facts all six agree on: no editor shows a docstring for a bare string literal of a union, so `case 'items':` never explains itself under any option; the object form shows the member docstring for `LLSelectChangeReason.Items` and keeps the literal assignable, and Codex Astra confirmed with the installed TypeScript 5.9.3 language service that the member docs survive declaration emission; a string `enum` rejects the plain literal, against the write-the-literal house style; a published `const enum` is the handbook's library hazard and this tsconfig emits a runtime enum anyway.
- Costs named: a runtime value export, a value and a type sharing one name, a second value-type pattern beside the unions, which `naming-conventions.md` section 3 must then rule on (Sonnet 5, Codex Astra). Opus 5 asks for the value bullets on both the alias and the `meta.reason` field docstring either way, since both do show on hover.

### Q6 - the setting's name

- `itemToLanguageTagFn`, protected `itemToLanguageTag(item)`: all six. Rankings agree on the tail: `itemToLangTagFn` or `itemToLangFn` next, `itemToLangIdFn` last.
- Reasons: section 3 names a mapping after the returned value, and HTML's own prose for the `lang` attribute says its value is a BCP 47 language tag, the term `src/i18n.ts`, DESIGN.md and README already use; `lang` names the destination attribute and leaves the tag-versus-name misreading open, which was the owner's objection; "language id" is Windows / ICU vocabulary, and `src/i18n.ts` already uses it for the primary subtag alone; `LangTag` abbreviates the word that carries the name's meaning, which no sibling does. Opus 5 flags that `tag` already names the chip family and judges "language tag" a closed standard compound that cannot be read as a chip; the later sibling is `groupKeyToLanguageTagFn`.

### Q1's gate, re-checked

- Entry layer: all six. The consumed attribution makes a setter-level check unreliable for a gesture's second change; the entry layer cannot and should not gate an action row's own setter calls; the paths are enumerable.
- Implementation notes from the members: compute the candidate value through one shared pure helper so the choose-all row and `toggleAllVisible` cannot drift (Opus 5, Codex Astra); the gate repeats the setters' equality check so a no-op pick never asks the hook (Opus 5); commit the precomputed operation, or revalidate after the handlers, so a synchronous setter inside the hook cannot make the advertised `reason` stale (Codex Sol, Codex Astra); test both the included paths and the excluded programmatic operations (Codex Sol, Codex Astra).

## Recommendation

- Q1: E, ratified by the owner after round one. Setting `onBeforeChange`, event method `preventDefault()`, readable `defaultPrevented`, protected hook `onChosenChanging`, a separate exported `LLSelectBeforeChangeEvent<T>` carrying `source`, `reason` and `item`. Scope user, gated at the entry layer in the four library-owned paths (row activation by click or key, the chip remove button, the clear button, the choose-all row); an action row's setters are the app's own command and stay outside.
- Q4: stay, against the 4:2 tally, because the technical premise behind the close votes fell, decisive for one of the four and supporting for a second: a modal that takes focus outside the select widget closes it through `focusout` under either rule, so "close" buys the motivating flow nothing, while "stay" keeps what "close" destroys (the typed query, the keyboard user's place in the list), needs no deferred reopen, and matches the owner's reading that `preventDefault()` cancels the whole pick. The contract: a vetoed change commits nothing, fires no `onChange` and triggers no automatic close; the handler owns the feedback, and an app that wants the popup gone calls `close()`. What "close" keeps that "stay" gives up: one activation invariant, since a vetoed pick becomes the one no-change activation that leaves the popup open. The owner ratified close: a vetoed single-mode pick closes the popup like any pick, and the `onBeforeChange` docstring must say that this applies only to a pick in single mode while the popup is open, while multiple mode, the clear button and the chip remove button leave the popup as it is.
- Q2: minimal, named `reason`, with the operation-not-initiator definition; land it before Q1 so the veto event carries it. Q5: ratified by the owner as the plain string union, against the 4:2 vote for the object: no runtime object, the value meanings written as bullets on the type alias and on the `meta.reason` field docstring, so a hover on the field or a jump to the type shows them. The discriminated-union shape for `item` is the more precise type and matches React Select's `actionMeta`.
- Q3: A, ratified by the owner as `itemToLangFn` with the protected `itemToLang(item)` (see the intro for the naming reasons), applied to the option row, the single trigger text, the single value mirror and the tag chip text; the docstring carries the minimal example and the BCP 47 note.
- Follow-ups recorded in FIXME.md and TODO.md: the two attribution quirks (QUALITY-634, QUALITY-635), the force-hide premise (NEEDS-VERIFICATION-636), the four documentation fixes (DOCUMENTATION-637 to 640), the close reason, the scroll-to-end callback, the maximum count, the popover external-hide resync, the modal-over-popup and the item-language real-browser passes. The CLAUDE.md RAM rule can say up to three reviewers at a time, never beside `npm run verify`, with the measured numbers.
