- [ ] **[QUALITY-634] - the user attribution is consumed by the first chosen-state change of a gesture, so an action row whose `onActivate` calls two setters reports `'user'` then `'api'`**
  - Symptom: `withUserChangeSource` sets `changeSource` for the whole wrapped call, but each variant's `fireChange` resets it to `'api'` before any observer runs, so only the first change of the gesture carries `'user'`.
  - Cause: the flag models "the first change of this interaction", written for the nested-setter-inside-`onChange` case, while an action row is the one wrapped path that may change the state twice.
  - Impact: any consumer that branches on `meta.source`, analytics for one, misattributes the second change; the AngularJS wrappers do not read it. `test/action-rows.test.ts` checks one change, so nothing pins either reading.
  - Fix: owner's ruling pending - scoped attribution per `withUserChangeSource` call (restore `'user'` after each `fireChange` until `fn` returns, keep the reset for nested setters inside `onChange`), or keep the consumption and state it, as the `withUserChangeSource` docstring now does.
- [ ] **[QUALITY-635] - `setItems` called first inside an action row's `onActivate` makes the reconciliation's `onChange` report `'user'`**
  - Symptom: an action row's `onActivate` that calls `setItems` first; the `onItemsChanged` reconciliation drops a chosen entry and fires `onChange` while `changeSource` is still `'user'`.
  - Cause: the same flag as QUALITY-634; the reconciliation path never forces `'api'`.
  - Impact: a consumer branching on `meta.source` gets an attribution that depends on call order; the `LLSelectChangeSource` docstring states the exception for now, pending this ruling.
  - Fix: pending with QUALITY-634; the reconciliation path can set `'api'` explicitly either way.
- [ ] **[NEEDS-VERIFICATION-636] - the force-hide premise behind `close()`'s catch block, the DESIGN.md "Force-hide resilience" bullet and the popover test rests on a spec reading the current HTML standard does not support**
  - Symptom: the comment says `dialog.showModal()` hides all popovers and that `hidePopover()` then throws `InvalidStateError`; `test/popover.test.ts` injects the throw instead of a real modal.
  - Cause: the HTML standard's "hide popovers until" steps walk the showing auto and hint popover lists only, so a `popover="manual"` element is never hidden when a modal opens, and the hide-popover algorithm returns without throwing for an already-hidden element (two committee members, round two).
  - Impact: none at runtime today (the guard is harmless), but the documented reason is wrong, and the modal-over-popup case is undocumented: when a modal takes focus outside the widget, the `focusout` handler closes it; when an overlay takes no focus, the popup stays shown; while a modal is open the rest of the document, the popup included, is inert.
  - Fix: a real-browser pass (the rootless Playwright recipe) on both behaviors, then correct the comment, the DESIGN.md bullet and the test's name, or record the browser facts if they differ from the spec.
- [x] **[DOCUMENTATION-637] - the `onClose` docstring never said what `null` means**
  - Fix: "`null` (default) = no consumer listener.", with the hook fact in its own bullet. The `onOpen` sibling says "no consumer listener" too, since the protected hook runs either way.
  - Verified: the post-fix review read both against the `onOpened` / `onClosed` hooks; `npm run verify` green.
- [x] **[DOCUMENTATION-638] - the `onChange` docstrings did not say that the value has already changed when it runs, that a setter may be called inside it, or that a modal may be opened from it**
  - Symptom: the owner's other project chose the revert-inside-`onChange` pattern without any public guarantee; the only statement lived in the protected `changeSource` field's docstring.
  - Fix: bullets on both variants: the trigger is already updated and the getter returns the new value; a nested setter reports `'api'`; a modal or a focus move is safe and focus that already left the widget is not reclaimed; in single mode a pick closes the popup after the handler if it is still open, while other changes leave it as it is.
  - Verified: the post-fix review read the bullets against `fireChange`, `onPopupListItemActivated`, the clear button and the `setItems` drop path, and had the closing sentence scoped to a pick and the list-render claim dropped; `npm run verify` green.
- [x] **[DOCUMENTATION-639] - the `rerender()` docstring named only in-place item mutation, while settings functions that read external state (the page language) need it too**
  - Fix: three more bullets: the case, named by the functions that rerun; the header and footer content, which never rerun; and the filter input's pack-owned attributes, which `rerender()` cannot reach.
  - Verified: the post-fix review read it against `rerender`, the header and footer wiring and `setUiTranslationPack`; `npm run verify` green.
- [x] **[DOCUMENTATION-640] - the `withUserChangeSource` docstring omitted the action rows and the consumption rule**
  - Fix: the list names an action row's `onActivate`, and the public `LLSelectChangeSource` and multiple-mode `onChange` lists name it too; the protected docstring states that the first chosen-state change consumes the attribution, before `onChosenChanged` runs; `LLSelectChangeSource` states the consumption rule in its own words and the reconciliation exception of QUALITY-635 (QUALITY-634 and 635 decide whether the behavior changes).
