# OPTIMIZE - performance log

Agent-facing log of llselect's own runtime performance: measurements, regressions, and the optimization work on them. The benchmark PAGE (its design, its traps, its own findings) lives in `SPEC_BENCHMARK.md`, `FIXME_BENCHMARK.md` and `BENCHMARK-LIBS-TUNE-FOR-FAIRNESS.md`; this file is about the library's numbers. The README "Benchmark" tables are the published numbers; they change only from a run on the machine the README's note describes, and a data update there never rewords the prose (CLAUDE.md "Update the data").

Status marks: `[ ]` open, `[~]` in progress, `[x]` done. Newest entry on top. No dates: `git log` owns the when; a measurement is identified by the commit the tree was at. Every measurement records the machine's power profile: a run without it is not comparable with the README (the lesson of the resolved entry below).

## The fit-content width measure keeps its cost

- [x] **`measureNaturalWidth` reads the computed `width` and `offsetWidth` instead of `offsetWidth` alone (the half-pixel fix, MEDIUM-704).** Measured in headless Chromium 153 on an open popup, 2000 calls each with a forced layout per call: the old read 5 microseconds, every candidate 5 to 6. The forced layout is the cost; the extra read is not. The candidates and the numbers: `popup-width-committee.md`.

## Color-scheme first decision forces one style recalculation per widget

- [ ] **Each widget's first color-scheme decision reads computed style and then writes an attribute, so in a batch every widget after the first forces a style recalculation.** About 50 ms per 1000 widgets on the main thread before the first paint. The benchmark page cannot see it (below). Found in the devcontainer runs of the entry "Mass instantiation looked regressed since v0.0.7". Fix proposed below, not applied, awaiting the owner.
- Mechanism: the batch loop in `queueFirstDecision` (`src/color-scheme.ts`) calls each widget's `decideNow`, which reads computed style (`readColorSchemeInputs` -> `getComputedStyle`) and then writes `data-llselect-color-scheme` on that widget's root; the write dirties style, so the next widget's read forces a recalculation again. The batch yields one microtask, not the one style flush its own comment promises. The shared `refreshAll` pass in `wireDocument` interleaves the same way on a scheme change.
- Evidence, from the devcontainer rig described in the entry below: a CPU profile of a synchronous 5000 x 10 build takes 226 to 230 ms at 0.0.7, 0.0.8 and 0.0.9 and 293 ms at the current build, and the whole difference is `syncColorScheme` -> `readColorSchemeInputs` -> `getComputedStyle`, 36 percent of the current build's samples. A trace of one 100 x 100 and one 1000 x 10 pass shows 1100 `UpdateLayoutTree` events forced from script by `readColorSchemeInputs`, one per widget, about 10 elements each; the older versions force none. Measured as the microtask time after each chunk, in interleaved runs of six fresh browser launches per version: current build 49.0 ms (Chromium 153) and 47.4 ms (156) per 1000 x 10 pass, 19.1 and 20.4 ms per 100 x 100 pass; 0.0.7 at most 0.4 ms; the current build higher in 12 of 12 adjacent pairs.
- Why the benchmark page cannot see it: `buildAll` adds a chunk's synchronous time to Build total before the microtask runs. In the devcontainer, Build total plus this flush is about 1.9 times 0.0.7's Build total.
- Proposed fix: a two-phase flush. In the microtask batch, first read every pending widget's inputs (one forced recalculation for the whole batch, the rest read a clean tree), then write every attribute; the same split in `refreshAll`. `PendingDecision` becomes a read step and an apply step, or `decideNow` returns the apply closure. Expected result: the 50 ms per 1000 widgets drops to one recalculation per batch.

## Bundle size since v0.0.7

- [x] **The minified UMD grew from 41.6 KB at v0.0.7 to 60.3 KB at the current 0.0.10 tree; gzip -9 from 10.3 KB to 14.6 KB.** Measured and attributed; nothing to do unless the owner sets a size target. The README's bundle-size row says 53.3 KB, the size at the 0.0.10 bump; it follows at the next bump, as data.
- Per release, minified UMD bytes: 0.0.7 41,628; 0.0.8 43,007; 0.0.9 50,795; current tree 60,304.
- Where the 18.7 KB went, minified bytes attributed to each source file through the source map: `base.ts` 25.3 to 38.1 KB (+12.8); `multiple.ts` 7.0 to 9.7 KB (+2.7); `color-scheme.ts` new, 1.8 KB; `single.ts` 1.9 to 2.9 KB (+1.0); `keyboard.ts` 1.0 to 1.4 KB (+0.4); `positioning.ts`, `icons.ts`, `grouping.ts`, `query-highlight.ts` and the English pack unchanged.
- What it bought, the feature commits between v0.0.7 and the current tree: prefix typeahead while the filter is inactive; popup header and footer slots; action rows before and after the items; pinned leading and trailing row blocks; `onFilterQueryChange`; `chosenItemsOrder`; `getVisibleEnabledItems()` public; the `colorScheme` setting with dark values in every theme and the batched first decision; `onBeforeChange`; `reason` and `item` on the change meta; `itemToLangFn` and `groupKeyToLangFn`; `onFocus`, `onBlur` and `onActiveItemChange`; `meta.reason` on `onOpen` and `onClose`; and the review rounds that hardened them.
- Against the other libraries on the benchmark page, minified: Tom Select 49.1 KB, Select2 71.4 KB plus jQuery 85.5 KB, Choices.js 73.6 KB, Slim Select 86.1 KB. llselect moved from the smallest to the second smallest.

## Mass instantiation looked regressed since v0.0.7

- [x] **Build and teardown of many widgets cost more than at v0.0.7 on the owner's machine, beyond the environment's own drift.** Resolved: the machine's power profile, not the code. The README numbers were taken under the KDE Performance profile, as the README's note records; the owner's later runs were not. Under Performance, v0.0.7 and the current build both give the README's numbers again, within a few percent, and the two builds are equal.
- The owner's runs, same i9-13900HX, the benchmark page with its default options (pre-select on, custom renderer off, no timeout off), one run per cell, llselect in ms. The browser was stated as Chromium 154.0.8037.57 stable x86_64 for the first new run and not restated for the later ones:

| Run | 100 x 100 build | 100 x 100 teardown | 1000 x 10 build | 1000 x 10 teardown |
|---|---|---|---|---|
| README, v0.0.7 (commit `7ccaf36`), Chromium 151, Performance | 12 | 0.50 | 30 | 4.30 |
| Tree at 0.0.10 about `b4d46d9`, Chromium 154, profile not recorded | 35 | 2.20 | 58 | 7.80 |
| v0.0.7 checked out and rebuilt, profile not recorded | 35 | 1.70 | 62 | 8.40 |
| dev head, profile not recorded | 36 | 1.70 | 61 | 8.50 |
| v0.0.7 checked out and rebuilt, Performance | 15 | 0.70 | 33 | 5.60 |
| dev head, Performance | 13 | 0.70 | 32 | 5.40 |

- The whole table comes back under Performance. The dev-head Performance run, build totals at 100 x 100 / 1000 x 10 with the README in parentheses: native `<select>` 33 / 33 (30 / 33), Choices.js 167 / 853 (171 / 869), Select2 140 / 484 (137 / 485), Tom Select 46 / 448 (45 / 466), Slim Select 73 / 127 (79 / 151).
- Under the unrecorded profile every library slowed, llselect the most. Ratios of the owner's two dev-head runs, unrecorded over Performance, at 100 x 100: llselect 2.8, Tom Select 2.5, Slim Select 2.0, native 1.6, Select2 1.4, Choices.js 1.3; at 1000 x 10: llselect 1.9, Choices.js 1.3, native 1.2, Slim Select 1.2, Tom Select 1.2, Select2 1.1. Hypothesis, not tested: a build that is mostly JavaScript compute scales with the core clock, while one dominated by DOM node creation or forced layout scales less; burst length alone does not explain it, since at 1000 x 10 llselect and native do about the same work per chunk and their ratios are 1.9 and 1.2.
- Controlled runs in this devcontainer, which found no regression worth the name and the color-scheme entry above. Rig: headless Chromium through Playwright (`rootless-browser-testing.md`); a page that mirrors the `llselect` adapter step for step and loads one version's unminified `dist/index.mjs` plus its vanilla theme, 0.0.7 / 0.0.8 / 0.0.9 from their npm tarballs and the current build from `npm run build`; a fresh browser process per launch, launches interleaved in A B B A order, five passes per launch with the warm median of each launch as one sample; CPU profiles through the CDP `Profiler` domain and traces through `Tracing`. This machine is also a 13900HX, inside a 4-core container; its absolute numbers are about twice the README's and drift by tens of percent between runs minutes apart, so only interleaved comparisons inside one run mean anything here.
  - Build total: the current build is slower than 0.0.7 by about 5 to 10 percent here. Six launches per version under Chromium 153: 1000 x 10 medians 57.4 ms for 0.0.7 (launches 53.2 to 66.1) and 61.3 ms current (59.2 to 64.4), the current build slower in 4 of 6 adjacent pairs; 100 x 100 medians 21.1 ms (20.2 to 22.1) and 23.3 ms (22.4 to 24.2), slower in 6 of 6. Under Chromium 156: 1000 x 10 52.1 ms (46.3 to 61.5) and 55.3 ms (46.6 to 59.5), 4 of 6; 100 x 100 21.2 ms (19.7 to 22.6) and 22.6 ms (20.4 to 23.9), 5 of 6. Established at 100 x 100 (11 of 12 pairs), only indicated at 1000 x 10 (8 of 12). The owner's single runs do not show it (13 against 15 ms, 32 against 33 ms).
  - Where those percent sit: a synchronous 2000 x 100 CPU profile puts the constructor path (`LLSelectSingle` inclusive) at 44.5 ms for 0.0.7 and 48.8 ms current, `setItems` equal (10.2 and 10.4 ms); the growth is spread over small per-widget DOM calls (`setAttribute` self time 8.2 to 12.5 ms, `addEventListener` 5.1 ms with the whole-life focus listener pair at 1.7 ms of it), and no single frame dominates. Not worth chasing.
  - No browser-version effect: the same two builds give the same picture under headless Chromium 151, 153 and 156. No Playwright release ships 154; 153 and 156 bracket it.
  - Teardown: the current `destroy()` costs about 1 ms per 1000 widgets more than 0.0.7 (`removeEventListener` for the whole-life focus listener pair, `detachFocusListeners`), in 9 of 12 adjacent pairs; not worth chasing.
  - A first run that shared one browser process across the four versions showed 0.0.7 at 34 ms and 0.0.9 at 61 ms; fresh processes in reverse order erased the spread, so it was process state and order, not code.
  - The benchmark page's timing code and its llselect adapter are unchanged since the README measurement (the diff since `7ccaf36` is demo chrome, chart colors, renamed selectors in the interaction section and the renamed custom-renderer option, which the mass build does not use), and the page writes no attribute on `<html>` or `<body>` during a run, so the shared `refreshAll` pass does not fire.
- What the benchmark measures (`demo/benchmark.js`, `buildAll`): Build total is the sum of the synchronous adapter `setup` calls over all widgets, one pass, with a `requestAnimationFrame` yield between chunks (25 widgets per chunk at 1000 widgets, 1 at 100); the yields and the final reflow are excluded. Teardown total is one timed loop of the adapter `teardown` over the widgets just built. DOM nodes is the resting count after the build. The interaction tables use medians of repeats; build and teardown do not, so each cell is a single pass.
- The llselect path per widget (the `llselect` adapter): `new LLSelectSingle(mount, { filterable: true, ariaLabel })`, then `setItems(items)`, then `setChosenItem(items[0])`, since every widget is built pre-selected; teardown is `destroy()`. The items array is built once and shared by all widgets.
