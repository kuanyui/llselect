# OPTIMIZE - performance log

Agent-facing log of llselect's own runtime performance: measurements, regressions, and the optimization work on them. The benchmark PAGE (its design, its traps, its own findings) lives in `SPEC_BENCHMARK.md`, `FIXME_BENCHMARK.md` and `BENCHMARK-LIBS-TUNE-FOR-FAIRNESS.md`; this file is about the library's numbers. The README "Benchmark" tables are the published numbers; they change only from a run on the machine the README's note describes, and a data update there never rewords the prose (CLAUDE.md "Update the data").

Status marks: `[ ]` open, `[~]` in progress, `[x]` done. Newest entry on top. No dates: `git log` owns the when; a measurement is identified by the commit the tree was at. Every measurement records the machine's power profile: a run without it is not comparable with the README (the lesson of the resolved entry below).

The goal (owner ruling), in the owner's words, translated from Chinese: "I think the performance goal is, first of all, that it must be on par with the native `<select>` as far as possible; the secondary goal is performance that blows the native `<select>` away." Each benchmark column of the README compares llselect with the native `<select>`, so a column where llselect is slower than the native `<select>` comes first. Optimization measures and targets the latest version of each browser (owner ruling, in the owner's words, translated from Chinese: "when optimizing, you only need to consider the latest version of the browsers"); older versions down to the support floor of `CLAUDE.md` must still work, but their speed does not steer a change.

## llselect is slower in Edge 154 than in Chromium 154

- [ ] **The owner's observation, made before this round of work and not measured by the agent: in Edge 154, llselect never beat the native `<select>` in ten runs of the scenario with 1000 select components, and lost by 10 to 20 ms, while it always won at 100 x 100.** In the owner's words, translated from Chinese: "this is not very important, but I will mention it; it is unrelated to this time, since I found it before: on Edge, llselect is clearly slower than on Chromium (ten runs, not once did it beat native `<select>`; 1000 select x 100 item always loses by between 10 and 20 ms; 100 x 100 does always win, no surprise, since there is less DOM). Is that normal? I thought it was the same engine, so it should be just as fast; the Edge version is 154 too." The benchmark page's scenarios are 1000 x 10 and 100 x 100, and the owner did not name the column.
- Hypotheses, not tested: Edge's enhanced security mode, which turns off the just-in-time compilers of JavaScript on sites that the user does not visit often; if the owner meant the build, that mode would slow the construction of llselect, which is JavaScript, more than the native `<select>`, which the browser builds in its own code. Also an extension that observes the DOM, and Edge's efficiency mode.
- Checks for the owner's machine: turn off "Enhance your security on the web" at `edge://settings/privacy`, or add the benchmark's host to its exceptions, and run again; run in an InPrivate window with extensions off; turn off efficiency mode at `edge://settings/system`.

## Color-scheme first decision forces one style recalculation per select component

- [x] **Each select component's first color-scheme decision reads computed style and then writes an attribute, so in a batch every select component after the first forces a style recalculation.** About 50 ms per 1000 select components on the main thread before the first paint. The benchmark page's Build total does not count it (below). Found in the devcontainer runs of the entry "Mass instantiation looked regressed since v0.0.7". Fixed in two steps (FIXME PERFORMANCE-706): the batch runs every select component's read before any write (for the roots outside other select components since FIXME MEDIUM-707), and the constructor writes a provisional attribute value before the subtree exists, so a confirmed guess writes nothing.
- Measured after the fix, the two benchmark passes (100 x 100 and 1000 x 10, 1100 select components in 140 tasks) in Chromium 153: forced style updates 140, one per task, 90 ms for all inserted elements (6600 in that run; the earlier trace counted 6730, the counts differ by run); the frames' own style updates 0 ms (before the fix 38 to 43 ms, every subtree styled twice; v0.0.7 styles the same elements in its frames for 53 ms). So the remaining cost over v0.0.7 is about 37 ms per 140 tasks, the fixed overhead of a forced style update, about 0.27 ms each here; a page that builds its select components in one task pays one. The two-phase flush alone had left 118 to 132 ms, since the attribute writes after styling restyled every subtree. The rig's microtask measurement after the fix: 31 ms per 1000 x 10 pass and 20 ms per 100 x 100 pass, most of it the styling moved from the frame into the batch, not extra work. The benchmark page now has a "Before paint" column that times this for every library alike, with a forced style and layout pass so that the libraries that defer nothing pay their styling in the same column (`SPEC_BENCHMARK.md`). The README tables carry that column since a later owner run, still at version 0.0.11, on the 13900HX, Performance profile, Chromium 154: llselect 22 ms at 100 x 100 and 39 ms at 1000 x 10, the native select 105 and 137.
- Mechanism before the fix: the batch loop in `queueFirstDecision` (`src/color-scheme.ts`) called each select component's decision, which read computed style (`readColorSchemeInputs` -> `getComputedStyle`) and then wrote `data-llselect-color-scheme` on that select component's root element; the write dirtied style, so the next select component's read forced a recalculation again. The batch yielded one microtask, not the one style flush its comment promised. The shared `refreshAll` pass in `wireDocument` interleaved the same way on a scheme change. Today both run every `read` before any `apply` for the roots outside other select components, and a nested root decides after them (`decideBatch`, FIXME MEDIUM-707).
- Evidence, from the devcontainer rig described in the entry below: a CPU profile of a synchronous 5000 x 10 build takes 226 to 230 ms at 0.0.7, 0.0.8 and 0.0.9 and 293 ms at the current build, and the whole difference is `syncColorScheme` -> `readColorSchemeInputs` -> `getComputedStyle`, 36 percent of the current build's samples. A trace of one 100 x 100 and one 1000 x 10 pass shows 1100 `UpdateLayoutTree` events forced from script by `readColorSchemeInputs`, one per select component, about six elements each, 6730 in all; the older versions force none. Measured as the microtask time after each chunk, in interleaved runs of six fresh browser launches per version: current build 49.0 ms (Chromium 153) and 47.4 ms (156) per 1000 x 10 pass, 19.1 and 20.4 ms per 100 x 100 pass; 0.0.7 at most 0.4 ms; the current build higher in 12 of 12 adjacent pairs.
- Why Build total does not count it: `buildAll` adds a chunk's synchronous time to Build total before the microtask runs. Before the fix, in the devcontainer, Build total plus this flush was about 1.9 times 0.0.7's Build total.
- The fix as proposed, then applied: a two-phase flush. In the microtask batch, first read every pending select component's inputs (one forced recalculation for the whole batch, the rest read a clean tree), then write every attribute; the same split in `refreshAll`; the decision object became a read step and an apply step (`ColorSchemeDecision`). The expected drop to one recalculation per batch happened (1100 to 140), but the total did not move until the second step, the provisional attribute, since every attribute write after styling had restyled its subtree.
