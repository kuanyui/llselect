# OPTIMIZE - performance log

Agent-facing log of llselect's own runtime performance: measurements, regressions, and the optimization work on them. The benchmark PAGE (its design, its traps, its own findings) lives in `SPEC_BENCHMARK.md`, `FIXME_BENCHMARK.md` and `BENCHMARK-LIBS-TUNE-FOR-FAIRNESS.md`; this file is about the library's numbers. The README "Benchmark" tables are the published numbers; they change only from a run on the machine the README's note describes, and a data update there never rewords the prose (CLAUDE.md "Update the data").

Status marks: `[ ]` open, `[~]` in progress, `[x]` done. Newest entry on top. No dates: `git log` owns the when; a measurement is identified by the commit the tree was at.

## Mass instantiation regressed since v0.0.7

- [ ] **Build and teardown of many widgets cost more than at v0.0.7 on the owner's machine, beyond the environment's own drift.** Investigated in this devcontainer (findings below): the current build's Build total is about 5 to 10 percent above v0.0.7, which cannot produce the owner's near doubling, and no browser-version effect reproduces; the current build also hides a per-widget forced style recalculation in the color-scheme first decision, about 50 ms per 1000 widgets that the page does not count, which a fix proposal below addresses; the owner's own numbers still need a repeat run.
- What the benchmark measures (`demo/benchmark.js`, `buildAll`): Build total is the sum of the synchronous adapter `setup` calls over all widgets, one pass, with a `requestAnimationFrame` yield between chunks (25 widgets per chunk at 1000 widgets, 1 at 100); the yields and the final reflow are excluded. Teardown total is one timed loop of the adapter `teardown` over the widgets just built. DOM nodes is the resting count after the build. The interaction tables use medians of repeats; build and teardown do not, so each cell is a single pass.
- The llselect path per widget (the `llselect` adapter): `new LLSelectSingle(mount, { filterable: true, ariaLabel })`, then `setItems(items)`, then `setChosenItem(items[0])`, since every widget is built pre-selected; teardown is `destroy()`. The items array is built once and shared by all widgets.
- Baseline: the README "Benchmark" tables, measured at v0.0.7 (commit `7ccaf36`) on the i9-13900HX Linux machine the README's note describes, Chromium 151.
- New run, by the owner, on the same 13900HX machine, Chromium 154.0.8037.57 stable x86_64, tree at 0.0.10 after the events work (about commit `b4d46d9`; which `public/` build served the page is not recorded), single run per cell:

| Library | 100 x 100 build (ms) | 100 x 100 DOM nodes | 100 x 100 teardown (ms) | 1000 x 10 build (ms) | 1000 x 10 DOM nodes | 1000 x 10 teardown (ms) |
|---|---|---|---|---|---|---|
| Native `<select>` | 52 | 10,200 | 3.90 | 38 | 12,000 | 7.20 |
| llselect | 35 | 900 | 2.20 | 58 | 9,000 | 7.80 |
| Choices.js | 207 | 20,900 | 8.10 | 1081 | 29,000 | 33 |
| Select2 | 187 | 10,900 | 17 | 568 | 19,000 | 42 |
| Tom Select | 118 | 900 | 1.90 | 517 | 9,000 | 22 |
| Slim Select | 134 | 11,000 | 7.40 | 173 | 20,000 | 32 |

- Ratios, new run divided by the README baseline (derived from the two tables):

| Row | Native `<select>` | llselect | The other four libraries |
|---|---|---|---|
| 100 x 100 build | 1.73 | 2.92 | 1.21 to 2.62 |
| 1000 x 10 build | 1.15 | 1.93 | 1.11 to 1.24 |
| 1000 x 10 teardown | 1.33 | 1.81 | 0.96 to 1.28 |
| 100 x 100 teardown | 1.18 | 4.40 | 1.23 to 1.70 |

- Reading of the two tables alone: every library is slower in the new run, so the environment moved (the browser went from Chromium 151 to 154; the power profile and background load of the new run are not recorded) and absolute numbers do not compare, the ratios do. llselect's ratio exceeds the other libraries' in every row, which suggested a regression of the library's own; the controlled runs below confirm only a small one in the page's number, about 5 to 10 percent, plus a larger cost the page does not count.
- Shape: resting DOM nodes are unchanged (900 and 9,000), so the popup list is still not rendered at rest. Per widget, build went from 120 to 350 microseconds at 100 items and from 30 to 58 microseconds at 10 items. Teardown per widget went from 5 to 22 microseconds at 100 items and from 4.3 to 7.8 at 10 items; the 100 x 100 teardown baseline is 0.50 ms in total, so that ratio is the least reliable of the four.
- Caveats: one pass per cell. Repeat the run three times, both configurations, before chasing a number.
- Findings from a controlled run in this devcontainer. Method: headless Chromium through Playwright (`rootless-browser-testing.md`); a page that mirrors the `llselect` adapter step for step and loads one version's unminified `dist/index.mjs` plus its vanilla theme, 0.0.7 / 0.0.8 / 0.0.9 from their npm tarballs and the current build from a fresh `npm run build`; five to seven chunked passes per cell (the first pass cold, the median of the rest warm), each version in a fresh browser process, the order reversed on a second run; CPU profiles through the CDP `Profiler` domain and traces through `Tracing` for attribution.
  - Build total, the number the page shows: the current build is slower than 0.0.7 by about 5 to 10 percent. Interleaved run, six fresh browser launches per version in A B B A order, five passes per launch, the warm median of each launch as one sample, under Chromium 153: 1000 x 10 medians 57.4 ms for 0.0.7 (launches ranged 53.2 to 66.1) and 61.3 ms for the current build (59.2 to 64.4), the current build slower in 4 of 6 adjacent pairs; 100 x 100 medians 21.1 ms (20.2 to 22.1) and 23.3 ms (22.4 to 24.2), slower in 6 of 6 pairs. The same run under Chromium 156, started with the current build: 1000 x 10 medians 52.1 ms (46.3 to 61.5) and 55.3 ms (46.6 to 59.5), slower in 4 of 6 pairs; 100 x 100 medians 21.2 ms (19.7 to 22.6) and 22.6 ms (20.4 to 23.9), slower in 5 of 6 pairs. So the difference is established at 100 x 100 (11 of 12 pairs) and only indicated at 1000 x 10 (8 of 12 pairs), where the launch-to-launch noise exceeds it. An earlier run with one launch per version (1000 x 10 warm medians under Chromium 151: 0.0.7 58.8, 0.0.8 58.3, 0.0.9 59.7, current 65.0 ms; 100 x 100 21.6 to 24.4 ms everywhere) could not separate this from drift and was first recorded as no regression. A first run that shared one browser process across the four versions showed 0.0.7 at 34 ms and 0.0.9 at 61 ms; fresh processes in reverse order erased the spread, so it was process state and order, not code.
  - Where the 5 to 10 percent sits: a synchronous 2000 x 100 CPU profile puts the constructor path (`LLSelectSingle` inclusive) at 44.5 ms for 0.0.7 and 48.8 ms for the current build, with `setItems` equal (10.2 and 10.4 ms); the growth is spread over small per-widget DOM calls (`setAttribute` self time 8.2 to 12.5 ms, `addEventListener` at 5.1 ms with the whole-life focus listener pair at 1.7 ms of it), and no single frame dominates. Not worth chasing before the flush below is fixed.
  - No browser-version effect: the same two builds give the same picture under Chromium 151, 153 and 156. No Playwright release ships Chromium 154 itself; 153 and 156 bracket it.
  - Absolute numbers here are about twice the README's and drift by tens of percent between runs minutes apart; only interleaved comparisons inside one run mean anything on this machine.
  - CPU profile of a synchronous 5000 x 10 build (no yields): 0.0.7, 0.0.8 and 0.0.9 take 226 to 230 ms, the current build 293 ms, and the whole difference is `syncColorScheme` -> `readColorSchemeInputs` -> `getComputedStyle`, 36 percent of the current build's samples. A trace of one 100 x 100 and one 1000 x 10 pass confirms the mechanism: 1100 `UpdateLayoutTree` events forced from script by `readColorSchemeInputs`, one per widget, about 10 elements each; the older versions force none.
  - The benchmark page cannot see this cost: the first color-scheme decision runs in a microtask (`queueFirstDecision`), after `buildAll` has already added the chunk's time to Build total. Measured as the microtask time after each chunk, in the interleaved runs above: current build 49.0 ms (Chromium 153) and 47.4 ms (156) per 1000 x 10 pass, 19.1 and 20.4 ms per 100 x 100 pass; 0.0.7 at most 0.4 ms; the current build higher in 12 of 12 adjacent pairs. The page pays it on the main thread before the first paint all the same: Build total plus this flush is about 1.9 times 0.0.7's Build total here.
  - Cause of the per-widget flush: the batch loop in `queueFirstDecision` calls each widget's `decideNow`, which reads computed style and then writes `data-llselect-color-scheme` on that widget's root; the write dirties style, so the next widget's read forces a recalculation again. The batch yields one microtask, not the one style flush its own comment promises. The shared `refreshAll` pass in `wireDocument` interleaves the same way on a scheme change.
  - Teardown: the current build's `destroy()` costs about 2.7 microseconds more per widget than 0.0.9 in the profiles (`removeEventListener` for the whole-life focus listener pair, `detachFocusListeners`); the interleaved runs put it at about 1 ms per 1000 widgets (medians 7.8 and 7.7 ms against 7.0 and 6.5 ms), in 9 of 12 adjacent pairs; not worth chasing.
- Proposed fix, not applied, awaiting the owner: a two-phase flush. In the microtask batch, first read every pending widget's inputs (one forced recalculation for the whole batch, the rest read a clean tree), then write every attribute; the same split in `refreshAll`. `PendingDecision` becomes a read step and an apply step, or `decideNow` returns the apply closure. Expected result: the 50 ms per 1000 widgets drops to one recalculation per batch.
- Still open: the owner's 58 ms against the README's 30 ms. The code accounts for the 5 to 10 percent above at most and the browser version for nothing measurable, so the rest is not reproduced here. One coincidence, checked and not an explanation: the 1.9 ratio of Build total plus flush above equals the owner's 58 against 30, but `buildAll` adds the chunk's time to its total before the microtask runs, so the page cannot count the flush. The benchmark page's timing code and its llselect adapter are unchanged since the README measurement (the diff since `7ccaf36` is demo chrome and chart colors), and the page writes no attribute on `<html>` or `<body>` during a run, so the shared `refreshAll` pass does not fire. The README tables change only from that machine, as data.
