# OPTIMIZE - performance log

Agent-facing log of llselect's own runtime performance: measurements, regressions, and the optimization work on them. The benchmark PAGE (its design, its traps, its own findings) lives in `SPEC_BENCHMARK.md`, `FIXME_BENCHMARK.md` and `BENCHMARK-LIBS-TUNE-FOR-FAIRNESS.md`; this file is about the library's numbers. The version history page, `demo/bench-history.html`, measures every published version and the current build in one sitting (`SPEC_BENCHMARK.md` "Version history page"). The README "Benchmark" tables are the published numbers; they change only from a run on the machine the README's note describes, and a data update there never rewords the prose (CLAUDE.md "Update the data").

Status marks: `[ ]` open, `[~]` in progress, `[x]` done. Newest entry on top. No dates: `git log` owns the when; a measurement is identified by the commit the tree was at. Every measurement records the machine's power profile: a run without it is not comparable with the README (the lesson of the resolved entry below).

The goal (owner ruling), in the owner's words, translated from Chinese: "I think the performance goal is, first of all, that it must be on par with the native `<select>` as far as possible; the secondary goal is performance that blows the native `<select>` away." Each benchmark column of the README compares llselect with the native `<select>`, so a column where llselect is slower than the native `<select>` comes first. Optimization measures and targets the latest version of each browser (owner ruling, in the owner's words, translated from Chinese: "when optimizing, you only need to consider the latest version of the browsers"); older versions down to the support floor of `CLAUDE.md` must still work, but their speed does not steer a change.

## The first build in a page got slower after 0.0.9

- [~] **Found: since 0.0.10, the build of every select component does more work, in DOM calls and in JavaScript; code that runs for the first time explains a small part only. The owner accepted the slowdown for the release of 0.0.15 and left the search to a later session; the plan below was that session's, and its results follow the plan. The fix waits for the owner's decision.** Build total at 1000 x 10, the medians in ms of the three runs of the version history page that the entry "Mass instantiation slowed between the README's run and the 0.0.15 candidate" records:

| Run | 0.0.9 | 0.0.12 | current | Native `<select>` |
|---|---|---|---|---|
| The owner's first run, ten rounds | 26 | 29 | 34 | 26 |
| The owner's second run, ten rounds | 26.75 | 32.00 | 32.05 | 25.95 |
| This devcontainer, headless Chromium 156, six rounds | 24 | 27 | 32 | 20 |

- The rise from 0.0.9 to 0.0.12 shows in all three runs: in the owner's second run, whose JSON keeps every run, an exact Mann-Whitney test of the ten runs per version gives U = 10 and a two-sided p of 0.0015. The rise from 0.0.12 to the current build shows in two of the three runs only: in the owner's second run the medians are 32.00 and 32.05 ms, U = 42.5 and p = 0.59. npm lacks 0.0.10, 0.0.11, 0.0.13 and 0.0.14, so no run places either rise in a version.
- The owner's words, translated from Chinese: "it looks like the performance really has degraded, but it seems still within an acceptable range? Find time later to optimize? It should be possible to deploy soon? I will deploy together with the few old versions that were missed, because I have other projects that use 0.0.12 and are now waiting for 0.0.13 to bring the fixed parts online". In the same message the owner asked for this plan, in the owner's words, translated from Chinese: "first write the investigation plan for the cause of the build slowdown that you mentioned into a document; a new session will look for the cause slowly later". The agent agreed that the slowdown is acceptable, for these reasons, taken from the owner's first run: at 1000 x 10 the current build takes 8 ms longer to build than the native `<select>`, 8 microseconds per select component; before paint, which the agent called the moment the user waits for, it is still about 2.8 times as fast as the native `<select>`; at 100 x 100 it leads in all three columns; and a page rarely builds 1000 select components at once. The user waits for Build total and Before paint together, though, 82 ms against 159 ms for the native `<select>` at 1000 x 10, which still favors the current build (Codex Sol). The owner then confirmed, in the owner's words, translated from Chinese: "1 acceptable".
- What the columns time (`demo/bench-core.js`, `buildAll` and `createLLSelectAdapter`): Build total is the synchronous loop alone. For each select component, the loop creates and appends the mount element, calls the adapter's `setup`, which runs the constructor, then `setItems` with the scenario's items and, with pre-select on, `setChosenItem` with the first item, and keeps the returned handle. The microtasks that a chunk queued, such as the first color-scheme decision with the style recalculation that it forces, and the forced style and layout pass after them, count in Before paint. So a rise in Build total lies in that loop: in the constructor, in `setItems`, in `setChosenItem`, or in a style or layout pass that one of them forces.
- Hypothesis, tested in step 4 below and refuted as the main cause: code that runs for the first time costs more, and each newer build runs more of it. V8 compiles most functions when they are first called, and the interpreter and the inline caches start cold. The minified `index.umd.js` grew from 50,795 bytes at 0.0.9 to 61,147 bytes at 0.0.12 and 86,259 bytes at the current build. Per select component, the 0.0.15 candidate created 9 elements against 8 at the README's run and called `setAttribute` 30 times against 28 (the CPU profiles of the entry named above). The warm rig of that entry, which measured after a warm-up pass in the same page, put the build of the current tree within about 1 ms of the README's run.
- Step 1, the method: measure only with the history page, which times the first build of llselect in a fresh frame, as the README's runs do after a page reload. In this devcontainer: the browser as `docs/llm/rootless-browser-testing.md` sets it up; `npm run build:site`; serve `public/`, for example through `make server`; open `/demo/bench-history.html`, set `#rounds`, click `#run`, wait until `#status` starts with "Done", and read the tables of class `bh-table`, or click "Copy the results as JSON" and read the clipboard, which holds every run. Six rounds of all twelve entries take about three minutes. Nothing else may run meanwhile: no reviewer CLI, build or test. The devcontainer reports the CPU of the README's machine, an i9-13900HX, so it likely shares that host, and a run here can disturb a run of the owner's. First settle whether the rise from 0.0.12 to the current build is real: ten rounds or more, and an exact test of the runs of each pair, as above.
- Step 2, more entries: the page measures every folder `demo/bench-history/<version>/` that `demo/bench-history/versions.json` lists, and the frame also accepts a version with a suffix, such as `0.0.13-a`. To measure a commit, build it in a git worktree on the disk, not under `/tmp`, which is a tmpfs in memory here: `git worktree add <folder> <commit>`, then `npm ci` and `npm run build` in it; copy its `dist/index.umd.js` and `dist/themes/vanilla.css` into `demo/bench-history/<label>/` as `index.umd.js` and `themes/vanilla.css`; add the label to `versions.json`; run `npm run build:site`. `npm run bench-history:prepare` writes `versions.json` from npm's list again, so add the local labels after it. - Step 4, cold against warm: a test copy of `demo/bench-history-frame.js`, not committed, that builds and tears down once before the measured build. ## Color-scheme first decision forces one style recalculation per select component

- [x] **Each select component's first color-scheme decision reads computed style and then writes an attribute, so in a batch every select component after the first forces a style recalculation.** About 50 ms per 1000 select components on the main thread before the first paint. The benchmark page's Build total does not count it (below). Found in the devcontainer runs of the entry "Mass instantiation looked regressed since v0.0.7". Fixed in two steps (FIXME PERFORMANCE-706): the batch runs every select component's read before any write (for the roots outside other select components since FIXME MEDIUM-707), and the constructor writes a provisional attribute value before the subtree exists, so a confirmed guess writes nothing.
- Measured after the fix, the two benchmark passes (100 x 100 and 1000 x 10, 1100 select components in 140 tasks) in Chromium 153: forced style updates 140, one per task, 90 ms for all inserted elements (6600 in that run; the earlier trace counted 6730, the counts differ by run); the frames' own style updates 0 ms (before the fix 38 to 43 ms, every subtree styled twice; v0.0.7 styles the same elements in its frames for 53 ms). So the remaining cost over v0.0.7 is about 37 ms per 140 tasks, the fixed overhead of a forced style update, about 0.27 ms each here; a page that builds its select components in one task pays one. The two-phase flush alone had left 118 to 132 ms, since the attribute writes after styling restyled every subtree. The rig's microtask measurement after the fix: 31 ms per 1000 x 10 pass and 20 ms per 100 x 100 pass, most of it the styling moved from the frame into the batch, not extra work. The benchmark page now has a "Before paint" column that times this for every library alike, with a forced style and layout pass so that the libraries that defer nothing pay their styling in the same column (`SPEC_BENCHMARK.md`). The README tables carry that column since a later owner run, still at version 0.0.11, on the 13900HX, Performance profile, Chromium 154: llselect 22 ms at 100 x 100 and 39 ms at 1000 x 10, the native select 105 and 137.
- Mechanism before the fix: the batch loop in `queueFirstDecision` (`src/color-scheme.ts`) called each select component's decision, which read computed style (`readColorSchemeInputs` -> `getComputedStyle`) and then wrote `data-llselect-color-scheme` on that select component's root element; the write dirtied style, so the next select component's read forced a recalculation again. The batch yielded one microtask, not the one style flush its comment promised. The shared `refreshAll` pass in `wireDocument` interleaved the same way on a scheme change. Today both run every `read` before any `apply` for the roots outside other select components, and a nested root decides after them (`decideBatch`, FIXME MEDIUM-707).
- Evidence, from the devcontainer rig described in the entry below: a CPU profile of a synchronous 5000 x 10 build takes 226 to 230 ms at 0.0.7, 0.0.8 and 0.0.9 and 293 ms at the current build, and the whole difference is `syncColorScheme` -> `readColorSchemeInputs` -> `getComputedStyle`, 36 percent of the current build's samples. A trace of one 100 x 100 and one 1000 x 10 pass shows 1100 `UpdateLayoutTree` events forced from script by `readColorSchemeInputs`, one per select component, about six elements each, 6730 in all; the older versions force none. Measured as the microtask time after each chunk, in interleaved runs of six fresh browser launches per version: current build 49.0 ms (Chromium 153) and 47.4 ms (156) per 1000 x 10 pass, 19.1 and 20.4 ms per 100 x 100 pass; 0.0.7 at most 0.4 ms; the current build higher in 12 of 12 adjacent pairs.
- Why Build total does not count it: `buildAll` adds a chunk's synchronous time to Build total before the microtask runs. Before the fix, in the devcontainer, Build total plus this flush was about 1.9 times 0.0.7's Build total.
- The fix as proposed, then applied: a two-phase flush. In the microtask batch, first read every pending select component's inputs (one forced recalculation for the whole batch, the rest read a clean tree), then write every attribute; the same split in `refreshAll`; the decision object became a read step and an apply step (`ColorSchemeDecision`). The expected drop to one recalculation per batch happened (1100 to 140), but the total did not move until the second step, the provisional attribute, since every attribute write after styling had restyled its subtree.
