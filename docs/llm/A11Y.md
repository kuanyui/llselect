# Accessibility behavior

The keyboard, focus, and ARIA contract for llselect. This is the behavior that automated tests target. Naming / architecture rationale lives in `DESIGN.md`; code-style rules in `../../CLAUDE.md`.

## Pattern

llselect has two ARIA modes, picked by the `filterable` setting. Booleans fix the mode per instance; the predicate form (`filterable: (items) => boolean`) re-evaluates it each time the popup OPENS (never mid-open), and an inactive open cycle behaves exactly like `filterable: false`:

- **`filterable: true`** - W3C ARIA APG "Combobox with list autocomplete" (the same focus model select2 uses). The trigger is a `button` that opens the popup; focus then moves to the filter `<input role="combobox">` inside the popup, and the option list is driven from it through `aria-activedescendant`. The popup wrapper is then a non-modal `dialog` named like the field, and the trigger's `aria-haspopup="dialog"` and `aria-controls` point to it: the popup holds a text field besides the listbox, and WAI-ARIA 1.2 `aria-haspopup` requires the value to match the role of the popup container. The input keeps `aria-controls` on the listbox. The input is the only focusable element the LIBRARY builds into the open popup, so by default Tab behaves like a native `<select>` - one tab stop, Tab leaves the select component. Focusable controls the app places in a header / footer slot are the documented exception (Focus, "Slot controls").
- **`filterable: false`** (default) - ARIA "Combobox (select-only)". The trigger itself is `role="combobox"` and keeps focus; `aria-activedescendant` lives on the trigger. The filter input is not displayed (it is present in the DOM with `hidden`; see `DESIGN.md`).

### Multiple selection deviates from the APG pattern

The APG combobox pattern is specified for single selection: the popup contributes ONE value to the combobox. `LLSelectSingle` follows it directly. `LLSelectMultiple` keeps the same keyboard / focus model but pairs it with an `aria-multiselectable="true"` listbox that stays open across toggles - the extension select2 and react-select also ship. There is no official APG pattern for a multi-select combobox, so this is a documented deviation, not an APG conformance claim; it needs assistive-technology validation (manual checklist in `TODO.md`).

> Status: Phase 8 has shipped. Both modes are implemented. `filterable: true` is pinned by `test/filterable.test.ts`; `filterable: false` is covered by the existing base / keyboard / outside-click / focus test files. The choose-all row is built (opt-in `chooseAllRow` multi setting, Phase 13); pinned by `test/select-all.test.ts`.

## Accessible name

WAI-ARIA 1.2 requires an author-supplied accessible name for the field; the library cannot invent one. Supply the `ariaLabelledBy` setting (space-separated id(s) of your visible label element(s) - preferred, keeps spoken and visible text in sync) or `ariaLabel` (a plain string). `ariaLabelledBy` wins when both are set. An empty or whitespace-only value of either counts as unset (the accname computation skips blank labels, so the ladder does too, and the unnamed-field warn still fires). The `labelEl` setting is the rung below both: with neither aria setting given, the label element's id becomes the resolved `ariaLabelledBy` (an id is minted from `classIdMap.labelId` when the element has none), and the table's first column applies. `labelEl` also emulates the behavior half native `<label for>` cannot deliver on these divs: clicking the label focuses the trigger - focus only, like a native `<select>` label, never opening - and `destroy()` unwires it (`label.test.ts`). `uiTranslationPack.filterInputAriaLabel` (default `"Search"`) is only a fallback for the filter input when neither is supplied - it names the operation, not the field. Wiring (`aria-name.test.ts`):

| Element | `ariaLabelledBy` set | only `ariaLabel` set | neither |
|---|---|---|---|
| Trigger, filter inactive (`combobox`) | `aria-labelledby`=ids (value = the screen-reader text inside the trigger, per combobox role) | `aria-label` | unnamed - violates WAI-ARIA 1.2 |
| Trigger, filter active (`button`) | `aria-labelledby`="ids + screen-reader-text id" - name = field name + current value | `aria-label` + chain `"trigger-id screen-reader-text-id"` (accname substitutes the trigger's own `aria-label`, same effect) | name = content only (the screen-reader text, no field name) |
| Filter input (`combobox`) | `aria-labelledby`=ids | `aria-label` | `aria-label` from `uiTranslationPack.filterInputAriaLabel` |
| Listbox | `aria-labelledby`=ids | `aria-label` | unnamed |
| Popup wrapper, filter active (`dialog`) | `aria-labelledby`=ids | `aria-label` | unnamed |
| Popup wrapper, filter inactive (no role) | none | none | none |

The "screen-reader text" in the chains above is a visually hidden span inside the trigger (`classIdMap.triggerScreenReaderTextId`, class `triggerScreenReaderTextClass`). It exists because of the combobox rule: WAI-ARIA 1.2 gives a combobox that is not a text field the value of its descendant content. The visible content slot `triggerContentEl` carries `aria-hidden="true"`, so the span is the trigger's only descendant content and a screen reader reads its text as the value; inline styles hide it, never `hidden` or `aria-hidden`, which would drop it from that value. While the filter is active, the chain above reaches the same span. The library writes it after every trigger content render from the protected `computeTriggerScreenReaderText()`, whose default first tries the `triggerContextToScreenReaderTextFn` setting, then reads out what the screen shows: the chosen item's `itemToString` text (single), `uiTranslationPack.triggerScreenReaderCountText` (multiple, `'count'` mode, English "3 of 74 selected"), `uiTranslationPack.triggerScreenReaderItemsText` over the chosen texts (`'tags'` mode, English "TypeScript, Rust"), or the placeholder while nothing is chosen. Custom trigger content never changes it. The displayed count, `uiTranslationPack.triggerContentCountText`, may stay short ("3 / 74 selected"), and a screen reader says a slash as "slash"; that is why the two texts are separate (`DESIGN.md` "Screen-reader text of the trigger"). No control sits inside the trigger (Trigger buttons strip below), so no control name enters the name or the value: the tags trigger announces `Apple, Banana`, not `Apple Remove Apple Banana Remove Banana`.

Language of parts: with `itemToLangFn` the library writes each item's BCP 47 code as `lang` on its option row, on the single select component's trigger content slot whenever an item is chosen (custom trigger content inherits it, and its own `lang` wins), on the screen-reader text while that text is exactly one chosen item's text, and on a tag chip's text or custom content, so a screen reader that switches voices reads the item in its own language. It never writes `lang` on a chip's remove button, whose accessible name mixes pack text with the item's text, on the multiple select component's count text, or on the screen-reader text while it joins several item texts, which are mixed-language, or holds the app's own text from `triggerContextToScreenReaderTextFn`. With `groupKeyToLangFn` the group container (`role="group"`), which carries the group's `aria-label`, gets the group's code; the `aria-hidden` label and the group's rows inherit it, and a row's own code from `itemToLangFn` wins. Without these settings the library writes no `lang`: its own item text inherits the page's language, and app-owned content keeps what the app set; WCAG 3.1.2, Language of Parts, is then the app's job.

| Group container (optgroup) | `group` | `aria-label`=label; disabled: `aria-disabled="true"` + `data-disabled="true"` | no |
| Group label | none | `aria-hidden="true"` (name already on the container) | no |

- The filter input is always built into the popup DOM. When `filterable: false` it carries the `hidden` attribute and is not focusable; the focus host stays the trigger (which keeps `role="combobox"`). Always-build keeps a future runtime toggle (e.g. select2-style `minimumResultsForSearch`) a CSS flip rather than a DOM rebuild. See `DESIGN.md` for the architecture rationale.
- Choose-all is the first `option` in the listbox so it sits in the arrow-key ring rather than being a separate tab stop. `aria-selected` has no `mixed` value. `aria-checked` has one and is supported on `option`, but the APG listbox pattern rules it out here: "If the selection state is indicated with aria-selected, then aria-checked is not specified for any options." Moving every item row to `aria-checked` would break the themes, which style `[aria-selected='true']`. So the indeterminate ("some selected") state is conveyed through the row's counting text (for example "Select all (3 of 10)") - visible text and accessible name alike - not a formal ARIA attribute.
- `hideChosenRows` (multiple): chosen items' rows are not rendered at all, so every rendered option carries `aria-selected="false"` even under `aria-multiselectable="true"`. The chosen state is perceived through the trigger (its screen-reader text: the count, or the chosen texts in tags mode) instead of the listbox. When every item is chosen, the popup presents the empty listbox plus the `role="status"` no-results element, exactly like a zero-match filter. Needs the AT pass in `TODO.md`.

## Focus

- Three words name three things in this contract and in the code:
  - "DOM focus" is the element that receives keyboard input, `document.activeElement`. Inside the select component that is the trigger, the filter input, a button of the trigger buttons strip, or a control the app placed in a header / footer slot. A row of the popup list never holds DOM focus.
  - "The active row" (also "the active option") is the row of the popup list that `aria-activedescendant` on the focus host points to and that the arrow keys move: an item row, an action row, or the choose-all row. Identifiers call this row "focused" (`focusedIndex`, `setFocusedIndex`, `focusChooseAllRow`, `popupListRowFocusedClass`); `naming-conventions.md` "Focus, active, activated ruling" says why. `onActiveItemChange` reports the item of this row to the app, `undefined` for a non-item row or no row; it fires only when that item changes under `compareFn`, so a move between two non-item rows is silent, and a mouse hover, which never moves the row, never fires it.
  - "Activate" means running the active row's action: Enter, Space while the filter is inactive, or a click. An item row is chosen (single) or toggled (multiple), the choose-all row toggles all, an action row runs its command. Subclasses see it through `onPopupListItemActivated`, `onPopupListActionRowActivated` and `onChooseAllRowActivated`; consumers see the result through `onBeforeChange` and `onChange`.
- Open (`filterable: true`): focus moves to the filter input, and the trigger leaves the tab order for the open cycle (`tabindex="-1"`, restored on close) - the open select component is a single tab stop, so Shift+Tab exits the select component instead of landing on the trigger with the popup still open. The buttons of the trigger buttons strip leave the tab order for every open cycle too (Trigger buttons strip). `aria-activedescendant` points to the first chosen option, else the choose-all row when rendered (`chooseAllRow`), else the first enabled option - never an action row.
- Open (`filterable: false`): focus stays on the trigger; `aria-activedescendant` lives on the trigger.
- Close, keyboard cancel (Esc or Alt+ArrowUp; with the filter active, Esc on an already-empty filter, Alt+ArrowUp always) or single-select pick: focus returns to the trigger (filter active - the input held focus) or simply stays on it (filter inactive). The same when a slot control holds focus at close time (Esc on it, or `close()` called from its own click).
- Close, pointer / focus dismissal (outside click on a focusable element, Tab or any focus move leaving the root): focus follows the user's action and is NOT pulled back to the trigger. Only when DOM focus is still inside the popup at close time - the filter input or a slot control (e.g. an outside press on a non-focusable area) - does it return to the trigger.
- The popup is not a focus trap.
- Select component focus events: `onFocus` fires once when DOM focus enters `rootEl` from outside or from nowhere; `onBlur` fires once when it leaves to outside or to nowhere; a move inside the select component fires neither. When focus leaving closes the popup, `onClose` runs before `onBlur`. `destroy()` and `setDisabled(true)` fire no `onBlur`. `close()` returns focus to the trigger before hiding the popup, so the hide itself produces no blur / focus pair. A click on the clear button or on a chip's remove button focuses the trigger when no element inside the select component holds focus. See `DESIGN.md` "Select component focus events".
- Slot controls (the conditional tab-stop contract): while the popup is open, the library's own elements form one tab stop, since the trigger buttons strip leaves the tab order then. Focusable controls the app places in `popupHeaderEl` / `popupFooterEl` are ordinary focusables, so while the popup is open Tab reaches them in DOM order - host -> header controls -> footer controls -> out, as long as the header stays in its default place after the filter input; in the filter-inactive mode the host is the trigger, so Tab from the trigger enters the popup instead of leaving it - and Shift+Tab from the first slot control returns to the host with the popup open. A header moved above the filter input (the subclass recipe, DESIGN.md "Popup header / footer slots") breaks this while the filter is active: forward Tab from the input skips the header's controls, and Shift+Tab enters them instead of leaving the select component. So such a header holds no control that is or can become a Tab stop, and at the end of `open()`, after `onOpen`, the library warns once per page in the console when the filter is active and such a control precedes the input. With the filter inactive the host is the trigger, which precedes the whole popup, so a moved header keeps the order. Focus inside a slot keeps the popup open (the focusout rule below); Tab past the last control leaves the root and closes without reclaiming focus. Arrow keys stay with the focused control: slot controls never enter the `aria-activedescendant` ring. Esc on a slot control closes the popup and returns focus to the trigger (a `keydown` listener on the popup, attached only when a slot exists; an Esc the app already handled - `defaultPrevented` - is left alone). This is a documented deviation from the APG rule that popup descendants stay out of the page Tab sequence, and it applies only when the app puts focusable content in a slot; an instance without slot content keeps exactly one tab stop while the popup is open. A slot control is the mouse-first place for a command; give it `tabindex="-1"` when a keyboard equivalent exists elsewhere.
- Mouse clicks in the popup never steal DOM focus: `mousedown` anywhere in the popup - an option, the no-results message, padding, or the list element itself - is default-prevented, so the combobox host (filter input / trigger) stays focused and keyboard input keeps working after mouse-toggling options. The one exception is the filter input's own subtree, which must take focus. Without this the browser's focus fixup would focus the `tabindex="-1"` listbox (keyboard dead) or blur the host (focusout would then close the popup). Native scrollbar dragging is unaffected - a scrollbar mousedown is not a cancelable content event.
- The same `mousedown` rule covers the header / footer slots: a slot button is activated without moving DOM focus off the combobox host, so keyboard input keeps working. A text field inside a slot must call `stopPropagation` on its own `mousedown` to take pointer focus.
- Opening never moves the window scroll (enforced in `open()`).
- Focus leaving the root (`focusout` whose `relatedTarget` is outside `rootEl`) closes the popup. The check is written against `rootEl.contains(next)`, so any in-popup control keeps the popup open while it holds focus.

## Keyboard - closed (focus on trigger)

| Key | Action |
|---|---|
| Enter / Space / ArrowDown / ArrowUp | open the popup |
| printable character (except Space) | prefix typeahead: open the popup, then move the active option to the first match - searching just after the chosen option when one is chosen (single mode; the native cycle rule, `computeTypeaheadClosedStartIndex`), from the top otherwise (the convenience focus `focusInitial` parks does NOT shift the search). The value does NOT change - typing never fires `onChange`; activation stays Enter / Space / click. If the hidden-anchor guard refuses the open, the buffer is emptied (nothing opened, so nothing to prefix). Not intercepted when the impending open cycle would have the filter active (`filterable` predicate evaluated fresh, read-only) - typing belongs to the filter input there. |
| Tab / Shift+Tab | move to the next / previous tab stop, popup stays closed: Tab from the trigger reaches the trigger buttons strip when it shows a button (Trigger buttons strip), else the next page element |
| anything else | not intercepted |

## Keyboard - open, filter inactive (focus on trigger)

| Key | Action |
|---|---|
| ArrowDown / ArrowUp | move `aria-activedescendant` to the next / previous enabled row (clamped, no wrap; disabled rows are skipped). ArrowUp from the topmost item continues onto the previous ring entry: the last leading action row when there is one, else the choose-all row when present. The ring runs choose-all row, leading action rows, items, trailing action rows (see Action rows). |
| PageDown / PageUp | move the active row by a fixed page size (10) across the ring; a jump past either end lands on the nearest enabled entry at that end, choose-all row and action rows included |
| Home / End | jump to the first / last enabled ring entry: Home lands on the choose-all row when present, End on the last trailing action row when present. |
| Enter / Space | activate the active row. Multi: toggle it, keep the popup open. Single: select it and close. On the choose-all row: toggle all. On an action row: run its command; the selection and the popup are left to that command (see Action rows). (Space activates here - unlike filter-active mode, there is no text field to type into.) |
| Escape / Alt+ArrowUp | close the popup; focus stays on the trigger |
| Tab / Shift+Tab | not intercepted: the native focus move leaves the select component, and focus leaving the root closes the popup. Does not change the selection. With focusable slot content the native move enters the slot first (Focus, "Slot controls"). The trigger buttons strip is no tab stop while the popup is open. |
| printable character (except Space) | prefix typeahead: move the active option to the next enabled option whose `itemToString` text starts with the typed buffer after the typeahead fold (each code point lower-cased on its own and the Greek final sigma normalized to sigma, on BOTH sides - `foldForTypeahead`; rationale in `DESIGN.md` "Prefix typeahead"). Keystrokes 1 s or less apart extend the buffer. A one-character buffer searches from just after the active option; repeating one initial keeps cycling through its matches (never a literal `"aa"` match - native rule); a longer mixed buffer searches from the active option itself, so extending it stays put while it still matches. The search wraps around the list (deliberately, unlike the clamped arrow navigation - a search means "anywhere", and cycling needs the wrap). Disabled rows are skipped; the choose-all row is never a match (its counting text mutates as the user selects). No match: active option and buffer stay put. Any mapped action key (arrows, Home / End, PageUp / PageDown, Enter, Space, Escape) resets the buffer; closing the popup resets it too. |

## Keyboard - open, filter active (focus on filter input)

| Key | Action |
|---|---|
| ArrowDown / ArrowUp | move `aria-activedescendant` to the next / previous row (clamped, no wrap). The choose-all row is the topmost row; action rows sit above / below the items (see Action rows). |
| PageDown / PageUp | move the active row by a fixed page size (10) across the ring; a jump past either end lands on the nearest enabled entry at that end, choose-all row and action rows included |
| Enter | activate the active row. Multi: toggle it, keep the popup open. Single: select it and close. On the choose-all row: toggle all. On an action row: run its command. |
| printable character | append to the filter string -> live filter |
| Space | insert a space into the filter. Does NOT toggle selection - toggling is Enter or click. |
| Home / End | move the text caret, NOT first / last option. Option jumping via Home / End is intentionally not provided in this model. |
| Tab / Shift+Tab | close the popup and move focus to the next / previous page element. Does not implicitly change the selection. With focusable slot content Tab visits the slot controls first (Focus, "Slot controls"). The trigger buttons strip is no tab stop while the popup is open, so Shift+Tab never lands on it. |
| Escape | if the filter string is non-empty, clear it (list resets to full); if already empty, close the popup and return focus to the trigger. |
| Alt+ArrowUp | close the popup whatever the filter string holds, and return focus to the trigger. Only Escape clears first. |

Filtering is IME-aware: while an IME composition is in progress (`compositionstart` ... `compositionend`) the list is not re-filtered on each keystroke; it filters once on `compositionend`. A keydown with `isComposing`, or with `keyCode` 229, belongs to the IME and triggers no action: Safari sends the key that ends a composition after `compositionend`, with `isComposing` false and `keyCode` still 229 (WebKit bug 165004), so the Enter that confirms a candidate chooses no row. Prefix typeahead exists only while the filter is inactive, and only for scripts typed without an IME (Latin, Cyrillic, digits, ...): an IME cannot compose on the non-editable trigger, so for CJK input the filter box remains the type-to-find mechanism (`filterable`). A key still counts as printable with AltGraph or macOS Option held - those chords produce characters, and the produced character arrives as the event's key. An Alt-carrying chord whose key is still a bare ASCII letter or digit produced nothing - that is a shortcut chord (Windows Alt menus, `accesskey`, VoiceOver's Ctrl+Option) and passes through. Ctrl-only and Meta chords are never intercepted. Rationale and the ratified rulings: `DESIGN.md` "Prefix typeahead".

## Filtering

- Each keystroke filters `items` through `filterFn`; the listbox renders only matches. `aria-activedescendant` resets to the first match; no match -> empty listbox with no active descendant, plus a `role="status"` no-results message BELOW the listbox (text from `uiTranslationPack.popupListNoResults`; rich content via `createPopupListNoResultsContentElFn(query)` - include real text, the status region announces its TEXT content; announced once when it appears - a keystroke that keeps the list empty does not rewrite the identical text, so it is not re-announced; never an option, so it stays out of the arrow-key ring).
- Filtering does not change the chosen set. A chosen item hidden by the filter stays chosen.
- `onFilterQueryChange(query)` fires after the re-render whenever the text actually changed: typing, the end of an IME composition, and the Esc that clears a non-empty query. Not for identical text, not for the silent reset `close()` performs (`onClose` covers that), not for `open()`, `setItems()` or `rerender()`. A handler reading `getVisibleItems()` sees the new list.

## Choose-all (tri-state)

- Opt-in: the `chooseAllRow` multi setting (default off). The row's label (visible text + accessible name) comes from `uiTranslationPack.chooseAllRowText`; the default row content is JUST that counting text - its numbers carry the tri-state, no default indicator is drawn (`data-chosen-state="none|some|all"` stays on the row as a CSS hook). Rich content replaces it via `createChooseAllRowContentElFn` (e.g. a `createOutlinedCheckboxSvgEl` tri-state SVG) - the accessible name then stays pinned to the counting text via `aria-label`, like custom item content. Why no default indicator: DESIGN.md "Choose-all default: plain counting text".
- none chosen -> unchecked; all chosen -> checked; some chosen -> indeterminate - all read from the counting text (`aria-selected` has no `mixed`, and `aria-checked` may not join it in one listbox: see Elements, roles, ARIA).
- Activating: unchecked / indeterminate -> select; checked -> deselect.
- Scope (RULED, was an open question): the VISIBLE enabled subset - the matching subset while a query is active, minus the chosen items while `hideChosenRows` is on, disabled items excluded. Choices outside that subset (filtered-out, hidden by `hideChosenRows`, disabled, or not in the current item list) are preserved either way. The public `chooseAll` / `unchooseAll` / `toggleAll` keep their whole-list semantics; the row's subset action is also public: `toggleAllVisible()`. The subset is computed by ONE public, overridable method, `getVisibleEnabledItems`, read by both the row (counts, tri-state, click) and `toggleAllVisible` - a subclass may narrow it (the tree-select demo narrows to leaf nodes) and the two stay in agreement.
- Ring position: the row is the FIRST OPTION, so with nothing chosen the initial `aria-activedescendant` lands on it at open (immediate keyboard discoverability; a chosen item still wins per the Focus rules). ArrowUp from the topmost item reaches it, through any leading action rows; Home lands on it (non-filter mode; in filter-active mode Home stays a caret move); up-actions clamp there; ArrowDown moves to the next ring entry: the first leading action row when there is one, else the first enabled item. It is never a tab stop - Tab keeps meaning "leave the select component" (the one-tab-stop contract of the library's own elements). The leading action rows sit between it and the first item (see Action rows).

## Action rows

`popupListLeadingActionRows` / `popupListTrailingActionRows` render app commands ("Restore defaults", "Clear all", "Add new...") as rows inside the listbox, above or below the items. This is the SECOND documented deviation from the APG option semantics, distinct from the choose-all row: a command borrows `role="option"` because the arrow-key ring forces it. The ring is the only keyboard path into the popup that keeps DOM focus on the combobox host, and WAI-ARIA 1.2 `aria-activedescendant` requires the active row to be an owned element of the element the combobox's `aria-controls` names, the listbox. WAI-ARIA 1.2 names `group` and `option` as the listbox's required owned elements, and the APG listbox pattern says a listbox provides no accessible way to present interactive elements such as buttons, so a command that screen-reader users must recognize as a command belongs in a header / footer slot as a real button (the README rule).

- Each row is `role="option"` with `aria-label` (or plain text) from its `textFn`, `aria-selected="false"`, and `aria-disabled` plus the disabled class when its `disabledFn` says so. `aria-selected` is required on every option, and an option's implicit value is false anyway, so a screen reader may say "not selected" (the manual pass checks the wording). It is never a tab stop and never contains a focusable control: the row itself is the control.
- Pinned blocks (`popupListLeadingRowsPinned` / `popupListTrailingRowsPinned`): the block is wrapped in a `div role="presentation"` that the library makes sticky at the listbox edge. The wrapper is transparent to the accessibility tree. Besides the role it carries only the theme class, the inline sticky style and the `data-edge-to-items` attribute the themes read. The rows keep `role="option"`, their ring position and their positional counts. DOM focus never moves. Scrolling an item into view accounts for the wrappers' measured heights, so a focused item never lands under a pinned block. A theme that also makes group labels sticky must offset their `top` by the leading wrapper's height itself.
- Ring order: choose-all row, leading action rows, items, trailing action rows. Home / End reach the ring's ends; PageUp / PageDown clamp across it; disabled rows are skipped in the travel direction.
- Positional counts: while the list holds a non-item row (the choose-all row or an action row), the library writes `aria-posinset` / `aria-setsize`, so the position a screen reader announces ("3 of 16") no longer counts the item rows and the non-item rows as one set. An item row outside a group counts among the item rows outside groups. An item row inside a group gets neither attribute: the browser counts the rows of its group, which holds item rows only. A row of the leading block (the choose-all row, then the leading action rows) or of the trailing block counts within its block. Without a non-item row nothing is written, and the browser's own count is already right. An in-place row rebuild copies the two attributes from the row it replaces.
- The popup never opens with the active option on an action row: the initial focus is the first chosen item, else the choose-all row, else the first enabled item, else nothing. A filter keystroke lands on the first matching item, never on a row; when nothing matches, the rows stay rendered (the item-only no-results status shows beside them - unlike the choose-all row, which hides itself when nothing is actionable) and the arrow keys reach them. When the focused item vanishes (`hideChosenRows`, `setItems`), the clamp stays on the items and never lands on a row. Typeahead never matches a row.
- Activation (Enter, Space while the filter is inactive, click) re-checks `disabledFn`, then runs the row's `onActivate` as a user change (`source: 'user'` for synchronous work). The library changes nothing else: it neither chooses nor closes for the row. A selection change made from a row is silent for screen-reader users unless the row's text or a live region reflects it.
- Rows are rebuilt on every list render and after every chosen change (right after `onChange`), so `textFn` / `disabledFn` are live. A focused row that disables itself keeps the active option, and Enter on it does nothing; the arrow keys leave it normally.
- While the filter is active, Home / End move the text caret, so a trailing row is reached only by arrowing past every match - put commands keyboard users need often in the leading rows.

## Disabled

Two axes, both using `aria-disabled` - never the native `disabled` attribute, which would suppress the pointer / focus events a "why is this disabled" tooltip needs.

- **Whole control** (`setDisabled(true)`): the trigger gets `aria-disabled="true"` and the trigger wrapper `data-disabled="true"`; the trigger's `tabindex` becomes `-1` (out of the tab order) unless `focusableWhenDisabled` is set, in which case it stays `0`. Opening is blocked (`open()` / `toggle()` / keyboard are no-ops) and an open popup closes. The buttons of the trigger buttons strip are blocked too: the clear button and the tag remove buttons do nothing while disabled, and none of them is a tab stop, whatever `focusableWhenDisabled` says (they stay visible, so a disabled control still shows its value). Keep it focusable when you want keyboard / AT users to be able to reach the disabled control to read its tooltip.
- **Individual item** (`itemDisabledFn(item)` returns true): the option gets `aria-disabled="true"` and the `*-popup-list-row-disabled` class, is not selectable by click or Enter, and is skipped by keyboard navigation - Arrow / Page / Home / End land on the nearest enabled option in the direction of travel, and focus stays put if there is none. When the row holding the focus itself becomes disabled (a rerender swapped or disabled the item in place), focus resolves backward to the nearest enabled option, then to the choose-all row when one is rendered (it is the option above the first item), then forward. An already-chosen item that becomes disabled stays chosen (selection is retained; clicking its row or pressing Enter on it does nothing; the paths that remove it are listed under "Clear button (clearable)" below). In `tags` mode that block covers the chip's x: a chosen-but-disabled item's remove button is inert and the chip is marked disabled (`aria-disabled` + `tagDisabledClass`, the theme greys it). Bulk actions (`chooseAll` / `unchooseAll` / `toggleAll` / `toggleAllVisible`) act on enabled items only; `unchooseAll` preserves disabled chosen items and clears enabled ones, listed or not; `chooseAll` keeps disabled chosen items in the current item list and removes every chosen item outside that list, disabled or not; `toggleAll` inherits the scope of the branch it calls: `chooseAll` when the list has no enabled item or an enabled item in the list is unchosen, `unchooseAll` otherwise; `toggleAllVisible`, the choose-all row's action, acts on the visible enabled subset and preserves every other choice, listed or not.

## Grouping (optgroup)

Set `itemToGroupKeyFn` to render groups. Grouping is a projection of the flat list, so it changes the DOM structure but not the navigation model.

- Each group is a `role="group"` container whose accessible name is the label (`aria-label`); the visible label element is `aria-hidden="true"` so the name is announced once, not twice. Matches the APG grouped-listbox pattern.
- A rich label (`createGroupLabelContentElFn`) fills only the visible, `aria-hidden` content (icon / count badge); the accessible name still comes from `groupKeyToString`, so a screen reader announces the plain group name.
- `groupKeyToLangFn` writes the group's BCP 47 code as `lang` on the container, where the `aria-label` lives, so the name is read in that language; the rows inherit it unless `itemToLangFn` gives a row its own.
- Group labels are NOT options and never enter the arrow-key ring: navigation moves option-to-option and skips labels with no special-casing (they are simply not in the focusable set / `itemEls`).
- A disabled group (`groupDisabledFn(key)` returns true) marks its container `aria-disabled="true"` + `data-disabled="true"` and disables every item in it, layering on the item-level disabled contract above (not selectable, skipped by keyboard, selection retained, bulk ops skip them).
- Items whose key is `null` render ungrouped, as direct options of the listbox.

## Trigger buttons strip

The clear button and the tag chips sit in `triggerButtonsEl`, a strip beside the trigger inside the trigger wrapper, never inside the trigger: inside a `combobox` their names would enter its value, and a `button` gives its children no roles (`DESIGN.md` "Trigger structure").

- Role: `toolbar` in tags mode, named by `uiTranslationPack.triggerButtonsAriaLabel` (English "Selection actions"); no role when it holds only the clear button. It carries `hidden` while nothing is chosen or while it is empty.
- Tab stop (roving `tabindex`, the APG toolbar pattern): one button of the strip is a tab stop - the button that last held focus while it is still in the strip, else the first button that is not `aria-disabled`, else the first. Only `button` elements take part. No button is a tab stop while the popup is open, while the select component is disabled, or while the strip is hidden.
- Keys inside the strip: Left / Right Arrow move focus to the previous / next button, Home / End to the first / last, clamped at both ends; Left and Right swap in right-to-left text; a key with Alt, Ctrl or Meta stays with the browser. Enter and Space activate the focused button natively. The trigger's keydown handler never sees these keys.
- Tab order while the popup is closed: trigger -> strip (once) -> out, and Shift+Tab the reverse.
- While the popup is open the strip is out of the tab order, so Tab from the open popup reaches the popup's slot controls, then leaves (Focus, "Slot controls"), and Shift+Tab from the filter input leaves the select component. This refines structure H's "Tab from an open popup closes the popup before entering the toolbar" (the review panel, 4:0): the strip precedes the popup in DOM order, so a tab stop there would take Tab from the trigger before any slot control and close the popup, and a slot control could never be reached by Tab while something is chosen.
- Focus that enters the strip while the popup is open, by script or a screen reader's cursor, closes the popup with the close reason `'trigger-buttons'`, and fires no `onBlur`, since the strip is inside the select component. When focus arrives there from outside the select component, `onClose` runs before `onFocus`.
- Focus after an action: removing a chip by keyboard moves focus to the next chip's remove button, else the previous one, else the trigger when no chip is left; clearing from the strip moves focus to the trigger; when the strip hides while it holds focus, focus moves to the trigger first. A pointer press on a strip button keeps DOM focus where it is (its `mousedown` is default-prevented), so the trigger or the filter input keeps focus and an open popup stays open.

## Tags (triggerDisplay: 'tags')

`LLSelectMultiple` with `triggerDisplay: 'tags'` renders each chosen item as a chip with a remove control, in the trigger buttons strip.

- The remove control is a `<button aria-label="Remove <itemToString>">` (text configurable via `uiTranslationPack.tagRemoveButtonAriaLabel`), reached through the strip's tab stop and arrow keys (Trigger buttons strip). Activating it removes the item and never opens the popup (the click is stopped from bubbling to the trigger wrapper). It does nothing when the whole control is disabled, and also when the ITEM itself is effectively disabled (`itemDisabledFn` or a disabled group) while still chosen: the x is inert and marked `aria-disabled`, the chip greyed - matching native `<select>`, where a disabled selected option cannot be removed by the user (see Disabled).
- Keyboard users remove a chosen item through the chips (Tab into the strip, an arrow key to the chip, Enter or Space) or through the popup (deselect the option). The chips sit outside the `combobox` trigger, so no focusable control sits inside it.
- The remove button default-prevents `mousedown`, like the popup: a click on the x keeps DOM focus where it is, so the combobox host keeps focus, an open popup stays open and no `onBlur` is reported. A click on the x of an enabled control and item focuses the trigger when no element inside the select component holds focus, then removes the item, unless an `onFocus` listener disabled the control or the item or removed the item; the inert x of a disabled control or item moves nothing.
- The chip's content - its default text span (`tagTextClass`, which carries the item's `lang` from `itemToLangFn`) or custom `createTagContentElFn` content - carries `aria-hidden="true"`: inside the toolbar only the buttons speak. The item reaches AT through the trigger's screen-reader text and through its remove button's `aria-label` (`itemToTagRemoveButtonAriaLabel`, default `Remove <itemToString>`), which custom chip content never changes. So chip content holds no control and no text meant only for screen readers.
- A custom remove-button icon (`createTagRemoveButtonContentElFn`) is decorative: the button keeps its `aria-label="Remove <itemToString>"` accessible name, mirroring how `createTagContentElFn` changes only visible content. (The built-in SVG helpers already set `aria-hidden`.)

## Vetoing a user change (`onBeforeChange`)

- The hook runs after the disabled checks: a disabled control, or a disabled item activated by its row or its chip, never reaches it. In multiple mode the clear button is the one user path whose `next` drops disabled chosen items, because a clear wipes them too; a toggle keeps them. In single mode a pick replaces the current choice whether it is disabled or not, and a clear empties it.
- A vetoed pick in single mode behaves like a pick of the current item: the popup closes and focus returns to the trigger, unless a handler already moved focus outside the select component, into a dialog for example.
- Except for the single-mode pick above, a veto causes no further change: the chosen state, `aria-selected`, the chips, the popup and DOM focus stay as they are after the activation itself. A click on an item row or on the choose-all row has already moved the active option there, as any click does; a keyboard activation, the chip's remove button and the clear button leave the active option where it was.
- A silent refusal is invisible to assistive technology; the handler owns the feedback, a status message or a dialog.

## Clear button (clearable)

`clearable: true` adds an x button beside the trigger that empties the selection.

- It is a `<button aria-label="Clear selection">` (text configurable via `uiTranslationPack.triggerClearButtonAriaLabel`), the last button of the trigger buttons strip: outside the trigger, so its name never enters the trigger's value and it composes with `createTriggerContentElFn`. Alone in the strip it is the strip's tab stop; in tags mode it is the toolbar's last button (Trigger buttons strip).
- Activating it empties the selection and never opens the popup (the click is stopped from bubbling). The library hides the strip, and with it the button, while nothing is selected. While the whole control is disabled the click does nothing (see Disabled).
- The wipe is TOTAL: already-chosen disabled items are cleared too, matching native `<select>` programmatic clearing (`selectedIndex = -1` ignores disabled). The enabled-only bulk op is `unchooseAll`, which preserves them.
- Tab reaches the button through the strip while the popup is closed. Enter and Space activate it natively: it clears, and focus moves to the trigger. A pointer press does not focus it: its `mousedown` is default-prevented, and a click on an enabled control focuses the trigger when no element inside the select component holds focus, then clears, unless an `onFocus` listener disabled the control; the click on a disabled control moves nothing. The focus hand-off below keeps focus on the rebuilt button through re-renders that leave it visible; when the strip hides while the button holds focus, a clear made by script for example, focus moves to the trigger first.
- For a chosen item that became disabled, activating its row (click or Enter) does nothing, and in `tags` mode its chip's remove button does nothing. It leaves the selection only through these paths:
  - the clear button clears it with the rest of the selection, when `clearable` is on and the control is enabled;
  - in a single select component, choosing another enabled item replaces it, and the app can call `setChosenItem()` with another item or `undefined`;
  - in a multiple select component, the app can call `setChosenItems()` with a selection that excludes it, or `toggleItem()` with it;
  - in both classes, the app can call `setItems()` with a list that no longer contains it;
  - in a multiple select component, if it is outside the current item list, `chooseAll()` removes it; so does `toggleAll()` when it calls `chooseAll()`, which it does when the list has no enabled item or an enabled item in the list is unchosen (`setChosenItems()` and `toggleItem()` accept items outside the list).
- Every trigger render swaps the button for a fresh one (built by `createTriggerClearButtonEl`). If the old button or its icon held DOM focus, the new button gets it - inside the select component, so an open popup stays open. If a subclass's `createTriggerClearButtonEl` returns the previous element, that element is kept and focus returns to the node that held it, if that node is still inside the button and can take focus; otherwise focus stays on the button. If the override returns a fresh element that cannot take focus, focus moves to the trigger instead of dropping to `<body>`.

## Open questions

- Tab-to-commit: Tab currently closes without changing the selection. A future option could make Tab commit the active row for single-select (native selects do this in some browsers). Off by default. With focusable slot content Tab enters the slot first, so such an option could apply only when no slot control follows.
