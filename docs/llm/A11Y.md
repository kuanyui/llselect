# Accessibility behavior

The keyboard, focus, and ARIA contract for llselect. This is the behavior that automated tests target. Naming / architecture rationale lives in `DESIGN.md`; code-style rules in `../../CLAUDE.md`.

## Pattern

llselect has two ARIA modes, picked by the `filterable` setting. Booleans fix the mode per instance; the predicate form (`filterable: (items) => boolean`) re-evaluates it each time the popup OPENS (never mid-open), and an inactive open cycle behaves exactly like `filterable: false`:

- **`filterable: true`** - W3C ARIA APG "Combobox with list autocomplete" (the same focus model select2 uses). The trigger is a `button` that opens the popup; focus then moves to the filter `<input role="combobox">` inside the popup, and the option list is driven from it through `aria-activedescendant`. The input is the only focusable element in the open state, so Tab behaves like a native `<select>` - one tab stop, Tab leaves the widget.
- **`filterable: false`** (default) - ARIA "Combobox (select-only)". The trigger itself is `role="combobox"` and keeps focus; `aria-activedescendant` lives on the trigger. The filter input is not displayed (it is present in the DOM with `hidden`; see `DESIGN.md`).

### Multiple selection deviates from the APG pattern

The APG combobox pattern is specified for single selection: the popup contributes ONE value to the combobox. `LLSelectSingle` follows it directly. `LLSelectMultiple` keeps the same keyboard / focus model but pairs it with an `aria-multiselectable="true"` listbox that stays open across toggles - the extension select2 and react-select also ship. There is no official APG pattern for a multi-select combobox, so this is a documented deviation, not an APG conformance claim; it needs assistive-technology validation (manual checklist in `TODO.md`).

> Status: Phase 8 has shipped. Both modes are implemented. `filterable: true` is pinned by `test/filterable.test.ts`; `filterable: false` is covered by the existing base / keyboard / outside-click / focus test files. The choose-all row is built (opt-in `chooseAllRow` multi setting, Phase 13); pinned by `test/select-all.test.ts`.

## Accessible name

WAI-ARIA 1.2 requires an author-supplied accessible name for the field; the library cannot invent one. Supply the `ariaLabelledBy` setting (space-separated id(s) of your visible label element(s) - preferred, keeps spoken and visible text in sync) or `ariaLabel` (a plain string). `ariaLabelledBy` wins when both are set. An empty or whitespace-only value of either counts as unset (the accname computation skips blank labels, so the ladder does too, and the unnamed-field warn still fires). The `labelEl` setting is the rung below both: with neither aria setting given, the label element's id becomes the resolved `ariaLabelledBy` (an id is minted from `classIdMap.labelId` when the element has none), and the table's first column applies. `labelEl` also emulates the behavior half native `<label for>` cannot deliver on these divs: clicking the label focuses the trigger - focus only, like a native `<select>` label, never opening - and `destroy()` unwires it (`label.test.ts`). `uiTranslationPack.filterInputAriaLabel` (default `"Search"`) is only a fallback for the filter input when neither is supplied - it names the operation, not the field. Wiring (`aria-name.test.ts`):

| Element | `ariaLabelledBy` set | only `ariaLabel` set | neither |
|---|---|---|---|
| Trigger, filter inactive (`combobox`) | `aria-labelledby`=ids (value = trigger content, per combobox role) | `aria-label` | unnamed - violates WAI-ARIA 1.2 |
| Trigger, filter active (`button`) | `aria-labelledby`="ids + value-span id" - name = field name + current value | `aria-label` + chain `"trigger-id value-span-id"` (accname substitutes the trigger's own `aria-label`, same effect) | name = content only (current value, no field name) |
| Filter input (`combobox`) | `aria-labelledby`=ids | `aria-label` | `aria-label` from `uiTranslationPack.filterInputAriaLabel` |
| Listbox | `aria-labelledby`=ids | `aria-label` | unnamed |

The "value-span" in the chains above is a `hidden` root-level span next to the trigger (`classIdMap.triggerValueId`; outside it, so `triggerEl.textContent` stays the visible content) mirroring the current value as PLAIN TEXT (chosen item text / `triggerCountSummary` / tag texts joined with `", "` / placeholder when empty). The chain references it instead of the visible content span so labelled controls inside rich trigger content - tag remove buttons, custom `createTriggerContentElFn` markup - never leak into the field's accessible name (e.g. a chip must announce as `Apple`, not `Apple Remove Apple`). Hidden-but-referenced elements are included by the accname algorithm by design.

## Elements, roles, ARIA

| Element | Role | Key ARIA | Focusable |
|---|---|---|---|
| Trigger, filter inactive (it IS the combobox) | `combobox` | `aria-haspopup="listbox"`, `aria-expanded`, `aria-controls`=listbox, `aria-activedescendant`=active row while open, field name via `aria-label` / `aria-labelledby` | yes - closed and open (it is the focus host) |
| Trigger, filter active (button that opens the popup) | `button` | `aria-haspopup="listbox"`, `aria-expanded`, `aria-controls`=listbox, name = field name + current value via `aria-labelledby` chain | closed: yes; open: no (`tabindex="-1"` for the open cycle) |
| Popup wrapper | none (generic) | - | no |
| Filter input | `combobox` | field name via `aria-label` / `aria-labelledby` (fallback: `aria-label` from `uiTranslationPack.filterInputAriaLabel`; no visible label), `aria-expanded="true"`, `aria-controls`=listbox, `aria-activedescendant`=active row, `aria-autocomplete="list"` | open: yes |
| Listbox | `listbox` | field name via `aria-label` / `aria-labelledby`; multi: `aria-multiselectable="true"` | no |
| Option | `option` | `aria-selected` | no |
| Choose-all row | `option` (first row of the listbox) | `aria-selected` = all-selected; tri-state via the counting name + `data-chosen-state` | no |
| Group container (optgroup) | `group` | `aria-label`=label; disabled: `aria-disabled="true"` + `data-disabled="true"` | no |
| Group label | none | `aria-hidden="true"` (name already on the container) | no |

- The filter input is always built into the popup DOM. When `filterable: false` it carries the `hidden` attribute and is not focusable; the focus host stays the trigger (which keeps `role="combobox"`). Always-build keeps a future runtime toggle (e.g. select2-style `minimumResultsForSearch`) a CSS flip rather than a DOM rebuild. See `DESIGN.md` for the architecture rationale.
- Choose-all is the first `option` in the listbox so it sits in the arrow-key ring rather than being a separate tab stop. ARIA `option` has no `mixed` state, so the indeterminate ("some selected") state is conveyed through the row's counting text (for example "Select all (3 of 10)") - visible text and accessible name alike - not a formal ARIA attribute.
- `hideChosenRows` (multiple): chosen items' rows are not rendered at all, so every rendered option carries `aria-selected="false"` even under `aria-multiselectable="true"`. The chosen state is perceived through the trigger (count summary or tags chips) instead of the listbox. When every item is chosen, the popup presents the empty listbox plus the `role="status"` no-results element, exactly like a zero-match filter. Needs the AT pass in `TODO.md`.

## Focus

- Open (`filterable: true`): focus moves to the filter input, and the trigger leaves the tab order for the open cycle (`tabindex="-1"`, restored on close) - the open widget is a single tab stop, so Shift+Tab exits the widget instead of landing on the trigger with the popup still open. `aria-activedescendant` points to the first chosen option, else the first option - which is the choose-all row when rendered (`chooseAllRow`).
- Open (`filterable: false`): focus stays on the trigger; `aria-activedescendant` lives on the trigger.
- Close, keyboard cancel (Esc; with the filter active, Esc on an already-empty filter) or single-select pick: focus returns to the trigger (filter active - the input held focus) or simply stays on it (filter inactive).
- Close, pointer / focus dismissal (outside click on a focusable element, Tab or any focus move leaving the root): focus follows the user's action and is NOT pulled back to the trigger. Only when DOM focus is still on the filter input at close time (e.g. an outside press on a non-focusable area) does it return to the trigger.
- The popup is not a focus trap.
- Mouse clicks in the popup never steal DOM focus: `mousedown` anywhere in the popup - an option, the no-results message, padding, or the list element itself - is default-prevented, so the combobox host (filter input / trigger) stays focused and keyboard input keeps working after mouse-toggling options. The one exception is the filter input's own subtree, which must take focus. Without this the browser's focus fixup would focus the `tabindex="-1"` listbox (keyboard dead) or blur the host (focusout would then close the popup). Native scrollbar dragging is unaffected - a scrollbar mousedown is not a cancelable content event.
- Opening never moves the window scroll (enforced in `open()`).
- Focus leaving the root (`focusout` whose `relatedTarget` is outside `rootEl`) closes the popup. The check is written against `rootEl.contains(next)`, so any in-popup control keeps the popup open while it holds focus.

## Keyboard - closed (focus on trigger)

| Key | Action |
|---|---|
| Enter / Space / ArrowDown / ArrowUp | open the popup |
| printable character (except Space) | prefix typeahead: open the popup, then move the active option to the first match - searching just after the chosen option when one is chosen (single mode; the native cycle rule, `computeTypeaheadClosedStartIndex`), from the top otherwise (the convenience focus `focusInitial` parks does NOT shift the search). The value does NOT change - typing never fires `onChange`; activation stays Enter / Space / click. Not intercepted when the impending open cycle would have the filter active (`filterable` predicate evaluated fresh, read-only) - typing belongs to the filter input there. |
| Tab / Shift+Tab | move to the adjacent page element (popup stays closed) |
| anything else | not intercepted |

## Keyboard - open, filter inactive (focus on trigger)

| Key | Action |
|---|---|
| ArrowDown / ArrowUp | move `aria-activedescendant` to the next / previous enabled row (clamped, no wrap; disabled rows are skipped). ArrowUp from the topmost item continues onto the choose-all leading row when present. |
| PageDown / PageUp | move the active row by a fixed page size (10) |
| Home / End | jump to the first / last enabled option. Home lands on the choose-all leading row when present. |
| Enter / Space | activate the active row. Multi: toggle it, keep the popup open. Single: select it and close. On the choose-all row: toggle all. (Space activates here - unlike filter-active mode, there is no text field to type into.) |
| Escape / Alt+ArrowUp | close the popup; focus stays on the trigger |
| Tab / Shift+Tab | not intercepted: the native focus move leaves the widget, and focus leaving the root closes the popup. Does not change the selection. |
| printable character (except Space) | prefix typeahead: move the active option to the next enabled option whose `itemToString` text starts with the typed buffer after the typeahead fold (each code point lower-cased on its own and the Greek final sigma normalized to sigma, on BOTH sides - `foldForTypeahead`; rationale in `DESIGN.md` "Prefix typeahead"). Keystrokes 1 s or less apart extend the buffer. A one-character buffer searches from just after the active option; repeating one initial keeps cycling through its matches (never a literal `"aa"` match - native rule); a longer mixed buffer searches from the active option itself, so extending it stays put while it still matches. The search wraps around the list (deliberately, unlike the clamped arrow navigation - a search means "anywhere", and cycling needs the wrap). Disabled rows are skipped; the choose-all row is never a match (its counting text mutates as the user selects). No match: active option and buffer stay put. Any mapped action key (arrows, Home / End, PageUp / PageDown, Enter, Space, Escape) resets the buffer; closing the popup resets it too, and so does an open that the hidden-anchor guard refuses. |

## Keyboard - open, filter active (focus on filter input)

| Key | Action |
|---|---|
| ArrowDown / ArrowUp | move `aria-activedescendant` to the next / previous row (clamped, no wrap). The choose-all row is the topmost row. |
| PageDown / PageUp | move the active row by a fixed page size (10) |
| Enter | activate the active row. Multi: toggle it, keep the popup open. Single: select it and close. On the choose-all row: toggle all. |
| printable character | append to the filter string -> live filter |
| Space | insert a space into the filter. Does NOT toggle selection - toggling is Enter or click. |
| Home / End | move the text caret, NOT first / last option. Option jumping via Home / End is intentionally not provided in this model. |
| Tab / Shift+Tab | close the popup and move focus to the next / previous page element. Does not implicitly change the selection. |
| Escape | if the filter string is non-empty, clear it (list resets to full); if already empty, close the popup and return focus to the trigger. |

Filtering is IME-aware: while an IME composition is in progress (`compositionstart` ... `compositionend`) the list is not re-filtered on each keystroke; it filters once on `compositionend`. Prefix typeahead exists only while the filter is inactive, and only for scripts typed without an IME (Latin, Cyrillic, digits, ...): an IME cannot compose on the non-editable trigger, so for CJK input the filter box remains the type-to-find mechanism (`filterable`). A key still counts as printable with AltGraph or macOS Option held - those chords produce characters, and the produced character arrives as the event's key. An Alt-carrying chord whose key is still a bare ASCII letter or digit produced nothing - that is a shortcut chord (Windows Alt menus, `accesskey`, VoiceOver's Ctrl+Option) and passes through. Ctrl-only and Meta chords are never intercepted. Rationale and the ratified rulings: `DESIGN.md` "Prefix typeahead".

## Mouse / pointer

| Target | Action |
|---|---|
| Trigger | toggle open / close |
| Option | multi: toggle that option (popup stays open); single: select + close |
| Choose-all row | toggle all |
| Outside the popup | close, per `outsideClickBehavior`: `pass-through` lets the outside action still fire; `block` swallows it |

## Filtering

- Each keystroke filters `items` through `filterFn`; the listbox renders only matches. `aria-activedescendant` resets to the first match; no match -> empty listbox with no active descendant, plus a `role="status"` no-results message BELOW the listbox (text from `uiTranslationPack.popupListNoResults`; rich content via `createPopupListNoResultsContentElFn(query)` - include real text, the status region announces its TEXT content; announced once when it appears - a keystroke that keeps the list empty does not rewrite the identical text, so it is not re-announced; never an option, so it stays out of the arrow-key ring).
- Filtering does not change the chosen set. A chosen item hidden by the filter stays chosen.

## Choose-all (tri-state)

- Opt-in: the `chooseAllRow` multi setting (default off). The row's label (visible text + accessible name) comes from `uiTranslationPack.chooseAllRowText`; the default row content is JUST that counting text - its numbers carry the tri-state, no default indicator is drawn (`data-chosen-state="none|some|all"` stays on the row as a CSS hook). Rich content replaces it via `createChooseAllRowContentElFn` (e.g. a `createOutlinedCheckboxSvgEl` tri-state SVG) - the accessible name then stays pinned to the counting text via `aria-label`, like custom item content. Why no default indicator: DESIGN.md "Choose-all default: plain counting text".
- none chosen -> unchecked; all chosen -> checked; some chosen -> indeterminate - all read from the counting text (`option` has no `mixed`).
- Activating: unchecked / indeterminate -> select; checked -> deselect.
- Scope (RULED, was an open question): the VISIBLE enabled subset - the matching subset while a query is active, disabled items excluded. Choices outside that subset (filtered-out or disabled) are preserved either way. The public `chooseAll` / `unchooseAll` / `toggleAll` keep their whole-list semantics; the row's subset action is also public: `toggleAllVisible()`. The subset is computed by ONE protected method, `getVisibleEnabledItems`, read by both the row (counts, tri-state, click) and `toggleAllVisible` - a subclass may narrow it (the tree-select demo narrows to leaf nodes) and the two stay in agreement.
- Ring position: the row is the FIRST OPTION, so with nothing chosen the initial `aria-activedescendant` lands on it at open (immediate keyboard discoverability; a chosen item still wins per the Focus rules). ArrowUp from the topmost item reaches it; Home lands on it (non-filter mode; in filter-active mode Home stays a caret move); up-actions clamp there; ArrowDown returns to the first enabled item. It is never a tab stop - Tab keeps meaning "leave the widget" (one-tab-stop combobox contract).

## Disabled

Two axes, both using `aria-disabled` - never the native `disabled` attribute, which would suppress the pointer / focus events a "why is this disabled" tooltip needs.

- **Whole control** (`setDisabled(true)`): the trigger gets `aria-disabled="true"` and `data-disabled="true"`; `tabindex` becomes `-1` (out of the tab order) unless `focusableWhenDisabled` is set, in which case it stays `0`. Opening is blocked (`open()` / `toggle()` / keyboard are no-ops) and an open popup closes. The trigger's embedded buttons are blocked too: the clear button and the tag remove buttons do nothing while disabled (they stay visible, so a disabled control still shows its value). Keep it focusable when you want keyboard / AT users to be able to reach the disabled control to read its tooltip.
- **Individual item** (`itemDisabledFn(item)` returns true): the option gets `aria-disabled="true"` and the `*-item-disabled` class, is not selectable by click or Enter, and is skipped by keyboard navigation - Arrow / Page / Home / End land on the nearest enabled option in the direction of travel, and focus stays put if there is none. When the row holding the focus itself becomes disabled (a rerender swapped or disabled the item in place), focus resolves backward to the nearest enabled option, then to the choose-all leading row when one is rendered (it is the option above the first item), then forward. An already-chosen item that becomes disabled stays chosen (selection is retained; only user re-toggling is blocked). In `tags` mode that block covers the chip's x: a chosen-but-disabled item's remove button is inert and the chip is marked disabled (`aria-disabled` + `tagDisabledClass`, the theme greys it). Bulk actions (`chooseAll` / `unchooseAll` / `toggleAll`) act on enabled items only.

## Grouping (optgroup)

Set `itemToGroupKeyFn` to render groups. Grouping is a projection of the flat list, so it changes the DOM structure but not the navigation model.

- Each group is a `role="group"` container whose accessible name is the label (`aria-label`); the visible label element is `aria-hidden="true"` so the name is announced once, not twice. Matches the APG grouped-listbox pattern.
- A rich header (`createGroupLabelContentElFn`) fills only the visible, `aria-hidden` content (icon / count badge); the accessible name still comes from `groupKeyToString`, so a screen reader announces the plain group name.
- Group headers are NOT options and never enter the arrow-key ring: navigation moves option-to-option and skips headers with no special-casing (they are simply not in the focusable set / `itemEls`).
- A disabled group (`groupDisabledFn(key)` returns true) marks its container `aria-disabled="true"` + `data-disabled="true"` and disables every item in it, layering on the item-level disabled contract above (not selectable, skipped by keyboard, selection retained, bulk ops skip them).
- Items whose key is `null` render ungrouped, as direct options of the listbox.

## Tags (triggerDisplay: 'tags')

`LLSelectMultiple` with `triggerDisplay: 'tags'` renders each chosen item as a chip with a remove control.

- The remove control is a `<button aria-label="Remove <itemToString>">` (text configurable via `uiTranslationPack.tagRemoveButtonAriaLabel`) with `tabindex="-1"` - out of the tab order. Clicking it removes the item and never opens the popup (the click is stopped from bubbling to the trigger). The click does nothing when the whole control is disabled, and also when the ITEM itself is effectively disabled (`itemDisabledFn` or a disabled group) while still chosen: the x is inert and marked `aria-disabled`, the chip greyed - matching native `<select>`, where a disabled selected option cannot be removed by the user (see Disabled).
- Keyboard users remove selections through the popup (deselect the option), not through the chips - matching select2. This keeps focusable controls out of the `combobox` trigger, which would otherwise fight `aria-activedescendant`.
- The item's name for AT is guaranteed by the remove button's `aria-label` (`itemToTagRemoveButtonAriaLabel`, default `Remove <itemToString>`), which custom chip content never changes. The chip itself is a generic `<span>` (no role), and ARIA prohibits naming `generic` elements, so the library cannot pin a name on it the way it pins `aria-label` on options. If `createTagContentElFn` renders icon-only content, include your own (visually hidden) text when the chip must be announced as more than its remove button.
- A custom remove-button icon (`createTagRemoveButtonContentElFn`) is decorative: the button keeps its `aria-label="Remove <itemToString>"` accessible name, mirroring how `createTagContentElFn` changes only visible content. (The built-in SVG helpers already set `aria-hidden`.)

## Clear button (clearable)

`clearable: true` adds an x button in the trigger that empties the selection.

- It is a `<button aria-label="Clear selection" tabindex="-1">` (text configurable via `uiTranslationPack.triggerClearButtonAriaLabel`) in its own trigger slot (not inside the content, so it composes with `createTriggerContentElFn`). Out of the tab order, like the tag remove buttons.
- Clicking it empties the selection and never opens the popup (the click is stopped from bubbling). It is hidden while nothing is selected (`data-empty`). While the whole control is disabled the click does nothing (see Disabled).
- The wipe is TOTAL: already-chosen disabled items are cleared too, matching native `<select>` programmatic clearing (`selectedIndex = -1` ignores disabled). The enabled-only bulk op is `unchooseAll`, which preserves them.
- Keyboard users clear via the normal selection controls (deselect in the popup); the button is a pointer convenience, matching the tag remove buttons.
- Every trigger render swaps the button for a fresh one (built by `createTriggerClearButtonEl`). If the old button or its icon held DOM focus, the new button gets it - inside the widget, so an open popup stays open. If a subclass's `createTriggerClearButtonEl` returns the previous element, that element is kept and focus returns to the node that held it, if that node is still inside the button and can take focus; otherwise focus stays on the button. If the override returns a fresh element that cannot take focus, focus moves to the trigger instead of dropping to `<body>`.

## Open questions

- Tab-to-commit: Tab currently closes without changing the selection. A future option could make Tab commit the active row for single-select (native selects do this in some browsers). Off by default.
- Focusable tag remove buttons: a future flag could make chip x buttons keyboard-operable (focusable + Delete = full grid-pattern chip nav). Off by default - APG has no standalone tag pattern and it conflicts with the combobox focus model. (Deliberately deferred; see "Tags".)
