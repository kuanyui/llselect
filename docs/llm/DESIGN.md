# Design notes

Architecture and API conventions for llselect. Code-style rules (braces, language, dash characters, etc.) live in `../../CLAUDE.md`; the keyboard / focus / ARIA behavior contract lives in `A11Y.md`. This file documents **what** to build and **why**, not how to write each line.

## API naming conventions

### Item vocabulary

`item` is one entry of the data list, the type parameter `T`. Unqualified `items` is the full list the user chooses from; every qualified form (`chosenItems`, `getVisibleItems`) is a subset of it. A row is the `role="option"` element the popup list builds for an item. Which names carry a side prefix is ruled under "Element family naming" below; the full ruling is `naming-conventions.md` s7a rule 10.

### Function-typed settings

Different categories of callbacks use different markers so callers can tell at a glance how the library will use the function. The marker is part of the **field name**, not the type alias.

| Category | Marker | Example |
|---|---|---|
| Event callback | `on*` prefix | `onChange`, `onOpen`, `onClose` |
| Other function (comparator, renderer, transformer) | `*Fn` suffix | `compareFn`, `createTriggerArrowContentElFn` |

Rationale:

- **`on*`** prefix is universally recognized in the JS ecosystem (DOM events, React props) as "callback the library invokes when an event happens". Use this for things the library fires AT the caller in response to user actions.
- **`*Fn`** suffix disambiguates settings whose value is a function the library invokes proactively (to compute, format, or produce DOM). Without the suffix, names like `renderArrow` read as a verb / method, creating doubt about whether the setting is a function or a config flag.
- The two prefixes/suffixes are mutually exclusive and have different semantic flavors (reactive vs. invertive), so combining them (e.g. `onChangeFn`) is never necessary.

Apply this rule to all new function-typed settings.

- **`this` is `undefined` inside every function-typed setting and every action-row function** (ruled in the callback-context review; reasons in `popup-rows-and-callbacks.md` section 4.10). The library calls them through a local reference, never as a method of the settings object or of the descriptor. The parameters are the only input; the instance is reached through the closure recipe (`let sel; sel = new ...`), never through `this`. The one exception is the translation pack: its message functions are called as methods of the pack (`pack.chooseAllRowText(...)`), so inside them `this` is the pack, and a pack may read its own other messages that way.

### Settings vs methods

llselect splits surface area by mutability:

- **Settings** (constructor argument, frozen after): immutable configuration - `filterable`, `compareFn`, `onChange`, `createTriggerArrowContentElFn`, `outsideClickBehavior`, `cssClassPrefix`. Behavior knobs.
- **Methods** (mutate state, fire side effects): `setItems`, `setChosenItem` (single) / `setChosenItems` + `toggleItem` (multi), `open`, `close`, `rerender`, `destroy` (tear-down; REQUIRED before discarding an instance that might be open, e.g. a framework wrapper's unmount). The data the component currently holds, plus lifecycle actions.

Never put mutable state (`items`, `chosen`, etc.) in settings as a "convenience". Dual write channels caused subtle bugs in select2 / choices.js that we deliberately avoid.

At runtime there is ONE resolved settings bag: `this.settings` holds base + variant fields, defaults applied, with `null` (never `undefined`) uniformly meaning "not set". The VALUE side deliberately differs: an empty single selection is `undefined` (`getChosenItem()`, `setChosenItem(undefined)`), which keeps `null` usable as a real item value for `T` and matches JS's absent-return convention (`Array.prototype.find`). A variant that adds settings resolves its own fields and passes them through `super(..., subclassSettings)` - the base constructor merges them so the bag is complete before any construction code (e.g. `createFilterInputEl` reading the pack) can read it. The channel is typed by each class's third generic param `S`, defaulted to its own settings type: `this.settings` is `S` with no re-typing, and each `subclassSettings` param accepts exactly the extra fields (`Omit<S, keyof OwnSettings>`), so an extender's typo or missing field is a compile error. One commented cast per constructor remains - TS cannot prove "own fields + Omit<S, own keys>" reassembles a generic `S`. No variant setting lives in a loose instance field, and the exported `LLSelect*Settings` types describe the actual runtime object. The bag is frozen by convention, not `Object.freeze` - the library never mutates it after construction (two exceptions, both text chrome: `setUiTranslationPack`, which replaces `uiTranslationPack` and re-resolves `placeholder` - see "Texts (i18n)" - and `setPlaceholder`, which replaces the explicit placeholder), but extenders stay free to hang extra data on it.

The freeze boundary is a rule, not a per-field judgment call: **state and copy move at runtime; capabilities do not.**

- State is what a native `<select>` also mutates live: the items, the value, `disabled`. It never lived in the settings bag - `disabled` is an instance field behind `setDisabled()`, while `focusableWhenDisabled`, the capability DESCRIBING disabled behavior, stays frozen.
- Copy is locale-owned text: the pack and `placeholder`. Language switching changes it at runtime in real apps, and swapping it touches no structure - these are the only two true freeze exceptions.
- Everything else is a capability: it decides what DOM exists and how it is wired at construction. `clearable` gates whether the clear-button element exists; `filterable` decides which element carries `role="combobox"`; `cssClassPrefix` mints every class name. A capability setter would be a mini-rebuild (DOM, ARIA, focus) plus a permanent API surface, so the sanctioned change paths are: rebuild the instance (one build measures ~0.2 ms), or, where runtime variation is genuinely common, a function-valued setting evaluated per use - `filterable`'s predicate form re-evaluates on every open, so `filterable: () => flag` IS the runtime toggle. If a capability ever earns promotion, the filter input is the precedent: it is ALWAYS built and hidden by CSS, so the future toggle is a CSS flip, never a settings write channel.

### Item identity: `compareFn`, no key function

Reviewers ask for an `itemKeyFn` beside `compareFn`. REJECTED: one rule for "the same item" - a key function beside the comparator is a second rule that can disagree with it, and a comparator also expresses what a key cannot (field-by-field structural equality). Cost, documented on `compareFn`: a custom comparator cannot be hashed, so the `Set` fast paths go linear - keep it cheap. The default is SameValueZero (`a === b || (a !== a && b !== b)`), so `NaN` items and group keys compare equal to themselves.

### Customization model: settings configure, subclassing extends

User-facing guide (when to pick which, with examples): README "Customization". Two layers, not two competing mechanisms:

- **Settings configure; subclassing extends.** A normal user configures one instance via `*Fn` settings (no `extends`). Subclassing is for *extending* the library - a new select type, a framework wrapper, a core behavior change.
- **Each customization point is a `protected` method whose default reads its `*Fn` setting.** The library calls the method directly:
  - `itemToString(item)` - default `= itemToStringFn(item) ?? String(item)`.
  - `renderTriggerContent()` (single / multiple) - default reads `createTriggerContentElFn(ctx)` first, else the variant's label / count. `ctx` is variant-specific (`chosenItem` for single, `chosenItems` for multi).
- **Override = replace.** Overriding the method replaces its default (setting included); the override wins, by plain OO. There is no resolver forcing the setting to win - that machinery was removed, it fought the low-level design. An extender who still wants the setting reads it / calls `super`.
- **The capability line: settings stop at CONTENT.** Every `create*ContentElFn` fills what an element SHOWS; the element itself (e.g. the `role="option"` row: its attributes, its structure) plus the ARIA the library pins on it stays library-owned. Changes to the library-built elements deliberately have no setting (a setting must not be able to break the ARIA contract); they go through the `create*El` overrides, i.e. subclassing. Demo section 13 shows the split side by side.
- **Construction-time overridable methods read only base state.** The constructor renders the trigger once (`renderTrigger()` in the `LLSelectSingle` / `LLSelectMultiple` constructor, right after `super()`), so the trigger `create*El` / `renderTriggerContent` methods run BEFORE a further subclass's own field initializers - JS runs those only after the super constructor returns (the classic virtual-call-in-constructor). An override of a trigger method that reads its OWN subclass fields therefore sees them `undefined` on that first render. The recipe: construction-time CONFIGURATION goes into the typed `subclassSettings` channel, which is complete before any construction code runs (the tree-select demo's `defaultExpandDepth`); genuine instance STATE either tolerates defaults during construction (read the field with a fallback) or is repainted by `rerender()` at the end of your own constructor. The popup-list methods (`createPopupListItemEl`, `getVisibleItems`, `createPopupListChooseAllRowEl`) do NOT run at construction - they wait for the first `open()` - so an override that reads fields only there (the tree-select demo) needs nothing. The clear-button methods (`createTriggerClearButtonEl` / `createTriggerClearButtonContentEl`) are ordinary trigger methods: that first render builds the button, every later trigger render swaps it in place (unless the override returns the same element, which is then kept, and owned, by the override), and the same recipe repairs them. The popup slot builders (`createPopupHeaderEl` / `createPopupFooterEl` and their content methods) run in the BASE constructor, before even the trigger render, and no later render repaints them - so an override reads the typed `subclassSettings` channel, never its own fields.

So: configure with settings (the common path); override `protected` methods only when extending. The two coexist with no precedence fight.

### Element family naming

Element refs and the CSS classes that style them share a prefix so the relationship is obvious from the name alone:

```
rootEl              .llselect-root
triggerEl           .llselect-trigger
  triggerContentEl  .llselect-trigger-content
  triggerArrowEl    .llselect-trigger-arrow
popupEl             .llselect-popup
  popupListEl       .llselect-popup-list
                    .llselect-popup-list-row
                    .llselect-popup-list-row-focused
                    .llselect-popup-list-row-disabled
                    .llselect-group        (phase 10)
                    .llselect-group-label  (phase 10)
```

Direct children of a major family get the family's prefix (`triggerContentEl`, `popupListEl`). A noun that exists on one side of the widget only stands on its own without the prefix, because the name cannot be misread as the other side: `group` and `chooseAllRow` live only in the popup list, `tag` only in the trigger. A noun that exists on both sides carries the prefix whenever the name means one side's DOM. `item` is such a noun: the popup lists item rows and the trigger shows chosen items, so the popup row family is `popupListItem*` (`createPopupListItemEl`, `createPopupListItemContentElFn`, `onPopupListItemActivated`). The row classes are `popupListRow*` because they mark every option row, not only item rows.

### ARIA roles vs JS names

ARIA role attribute values (`"combobox"`, `"listbox"`, `"option"`, `"group"`, `"searchbox"`, `"checkbox"`) are spec strings and stay verbatim in `setAttribute` calls. JS-side names are independent and follow the rules above (e.g. our `role="listbox"` element is called `popupListEl`).

The row `aria-activedescendant` points to is "the active row" in prose and in new names; the existing `focused*` identifiers keep their word (`naming-conventions.md` "Focus, active, activated ruling"). The full keyboard / focus / ARIA behavior contract is in `A11Y.md`. The `combobox` role sits on the filter input when `filterable: true` (the trigger demotes to a `button`); with `filterable: false` the trigger itself is the `role="combobox"` host. Both modes shipped with Phase 8 and are final by design, not transitional.

## Library scope

llselect is a **low-level** select library. It provides:

- DOM scaffold + ARIA wiring
- Positioning, keyboard navigation, lifecycle (open/close/rerender)
- Stable CSS class hooks for every structural slot

It does **not** provide:

- Default visual styling (themes are opt-in, shipped separately)
- Item content beyond the configured `itemToString` (no built-in icon / description / avatar slots inside items)
- Arbitrary trigger markup out of the box - the built-in multi-select displays are `'count'` and `'tags'` (`triggerDisplay`); `createTriggerContentElFn` takes over the trigger entirely. See "Tags (triggerDisplay)".
- A second change channel (`subscribe()`, DOM `CustomEvent`) - REJECTED. One typed callback per event (`onChange`, `onOpen`, `onClose`); the framework wrapper is the layer that calls several listeners from it, and a `CustomEvent` dispatched on a plain `div` cannot be typed.

When in doubt, the answer is "lib provides a structural slot; the user fills it". This keeps API surface tight and avoids feature creep.

## `<form>` integration (ruled out of core)

RULED: no form-integration setting; the library never creates form controls. README "`<form>` integration" ships a hidden-`<input>` recipe instead. A "minimal hidden `<select>` + `<option>` mirror" setting was considered and rejected:

- **Form compatibility is an iceberg, not a serializer.** Honest parity needs: a `name` setting, an item-to-submit-string mapping (a new setting - `itemToString` is display text, "Taiwan" not "TW"), `form.reset()` re-sync, constraint validation, `<label for>` focus redirection (this one half DOES ship standalone as the `labelEl` setting - see A11Y.md "Accessible name"), autofill reverse-sync, and the multi `name` spelling the backend dictates (`countries[]` for PHP / Rails, bare repeated `name` for Go / Python - no correct library default exists). Shipping only the submission tip turns a documented limitation into surprise bugs; shipping it all is framework-wrapper territory ("Library scope") - the AngularJS package already gets full form semantics via `ngModel` / `form.$valid` with zero hidden DOM.
- **A hidden `<select>` is the worst mirror shape.** Everything a `<select>` offers over hidden inputs requires the FULL option list plus focusability: autofill needs options to pick and a `change` listener syncing back; `required` on a `display:none` control blocks submit with a console-only "not focusable" error (select2 resorts to sr-only hiding to keep the bubble reachable); `<label for>` sends clicks/focus to the hidden element. A chosen-values-only "minimal" select keeps all of those traps and adds nothing over `<input type="hidden">`, which is inert by spec: unfocusable, no tab stop, outside the a11y tree, excluded from constraint validation.
- **Full-option mirror (the Radix / React Aria shape) also rejected.** It is O(items) resting DOM per instance - the node count the benchmark tables lead with - plus the reverse-sync / reset / validation contract above. Those libs sit inside component frameworks where that contract is cheap to maintain; llselect is the layer such wrappers are built on.
- **A shipped `llselect/form` helper would degenerate into the recipe.** `onChange` is a single callback slot: an attach-style helper fights the app for it, and a helper the app must call from its own `onChange` is just the recipe with a dependency. Revisit only on real demand.
- **`formdata` event rejected as the recipe mainline**: `form.addEventListener('formdata', ...)` would need no hidden DOM at all, but it is Safari 15+, above the Safari 14.1 floor. Hidden inputs are floor-safe.

## Texts (i18n)

All chrome strings (AT labels + generated text) live in ONE base setting `uiTranslationPack` (contract: the `LLSelectUiTranslationPack` interface atop `src/i18n.ts`): input is `Partial<LLSelectUiTranslationPack>`, resolved against the English defaults (`en` - the same object the `@llselect/core/i18n` subpath exports). Static strings are plain strings; parameterized messages are functions taking RESOLVED primitives (`itemText: string`, counts) - never `T` - so a language pack can implement them without knowing the item type. Per-`T` control stays on the protected methods (e.g. `itemToTagRemoveButtonAriaLabel`). Key naming rules: naming-conventions.md s7a.4.

The `placeholder` SETTING stays app copy - an explicit value always wins and packs never set it. But its library DEFAULT (`'Please select'`) is chrome, so it lives in `uiTranslationPack` as `triggerPlaceholder` and localizes with the pack; resolution is `settings.placeholder ?? uiTranslationPack.triggerPlaceholder`. (select2 has no such key only because it ships no default placeholder at all; llselect does, so the default must be translatable.)

The resolved bag is publicly readable via `getUiTranslationPack()` (defaults + pack + overrides merged), so app code can reuse the library's translations - e.g. an app-owned tooltip on a remove button - instead of keeping a second translation source.

The pack is one of the two settings fields mutable after construction: `setUiTranslationPack(pack: Partial<LLSelectUiTranslationPack>): void` re-runs the constructor's resolution (merged over the built-in `en`, NOT over the previous pack; an explicit `placeholder` keeps winning), re-applies the pack-owned attributes `rerender()` cannot reach (filter input placeholder / fallback `aria-label`; the clear button is rebuilt by the re-render and reads the new pack), then re-renders - so switching language needs no re-`new` and chosen state survives. The other is the placeholder: `setPlaceholder(placeholder: string | null): void` replaces the explicit placeholder with immediate effect (`null` = revert to the pack default, mirroring an unset constructor `placeholder`; the explicit value keeps winning over later pack changes). These two are the only settings with runtime setters - both are copy, per the freeze rule in "Settings vs methods" (`setDisabled` changes state, which never was a setting, so it is not an exception).

Language packs are pure data under `@llselect/core/i18n` (50+ locales; `uiTranslationPackByLocale` indexes them by minimal BCP 47 tag): opt-in, tree-shakeable, zero behavior, so bundling translations does not violate "low-level". Layout: one file per pack under `src/i18n/<export>.ts` (`en` included - it is just the built-in pack), and `src/i18n.ts` as the barrel (the contract interface + re-exports + the locale index; pack files type-import the barrel - erased at compile time, so no runtime cycle). `base.ts` imports exactly `src/i18n/en.ts`, never the barrel, so the main bundle carries exactly one pack. Usage: `uiTranslationPack: zhTW`, or a per-key override on top: `uiTranslationPack: { ...zhTW, filterInputPlaceholder: '...' }`.

## Item language (`itemToLangFn`)

A mapping setting, `itemToLangFn: ((item: T) => string | null) | null`, gives the library each item's BCP 47 code, written as the HTML `lang` attribute where the library shows that item's text. RULED by the veto-hook committee (`change-veto-committee.md`, 6:0 for a setting) and the owner:

- Why a setting: when custom row content is used, the row carries `aria-label = itemToString(item)`, and the accessible name's language is the `lang` in effect on the row, never on the app's inner content, so an app could not fix the voice without subclassing `createPopupListItemEl`; the plain-text row has the same gap. The setting closes it in one place for every element that shows an item's text.
- Where it is written: the option row in both content branches, the single trigger's content slot and its hidden value mirror whenever an item is chosen (the slot is what AT reads while the filter is inactive, the mirror while it is active; custom trigger content inherits the slot's code and its own `lang` wins, so the library never touches the app's element there), and a tag chip's text, which the default branch wraps in a span of its own (`tagTextClass`) so the chip's remove button, whose name mixes pack text with the item's text, stays outside; custom chip content gets the attribute set on the app's element, never removed, because wrapping it in the span would change the chip DOM under existing `createTagContentElFn` CSS; that is why the chip rule overwrites while the trigger rule lets the app's `lang` win. Not the multiple count summary, which is pack copy in the page's language, nor its value mirror while it joins several item texts, which are mixed-language (with exactly one chip the mirror shows that item's text and carries its code), not action rows, which are app copy in the page's language. A group gets its code from the sibling setting `groupKeyToLangFn: ((groupKey: GroupKey) => string | null) | null`, written on the group container (`role="group"`): that is where the `aria-label` naming the group lives, and the `aria-hidden` visible label and the group's rows inherit from it; a row's own code from `itemToLangFn` wins, and custom label content from `createGroupLabelContentElFn` keeps its own `lang`, never touched. The single select's trigger sits outside the group DOM and reflects only the item's own code, never the group's. Groups are rebuilt per render, so the attribute is set or absent per render like the rows'.
- Not automatic: copying the content element's `lang` to the row was rejected as implicit, and it cannot help the plain-text branch, which is the language-picker case.
- The name: `itemToLangFn`, HTML's own attribute name, as `ariaLabel` names the value written into `aria-label` (owner ruling against the committee's `itemToLanguageTagFn`; the i18n docs call the full value a BCP 47 tag and use "language id" for the primary subtag, so "Id" was out). The docstring opens by saying the value is a code such as `'de'`, not a language name, and carries the smallest example, because the need is rare.
- `null` from the function or as the setting writes no attribute; the empty string writes `lang=""`, HTML's "language unknown". Rows and chips are rebuilt per render; the single trigger's content slot and value mirror persist, so every trigger render sets or removes their attribute. An element the app returned from `createTagContentElFn` has the attribute set or overwritten when the function returns a code and never removed, so a memoized element keeps a code the library wrote earlier when the answer later turns `null` (an accepted limit); the single trigger needs no such write because its library-owned content slot carries the code above the app's element, the one place where a library wrapper exists.
- A `lang` attribute does not establish pronunciation by itself; the screen-reader pass stays under manual verification in TODO.md.

## RTL

Zero new API: the component inherits the environment's direction (`dir` attribute / CSS `direction`) exactly like a native element. There is deliberately no `rtl` / `dir` setting (react-select's `isRtl` prop exists to service its CSS-in-JS pipeline; a DOM library has no such constraint).

Two layers, owned by different parties:

- **Chrome direction (the library's layer).** The trigger is a flex row, so the slot order (content | clear button | arrow) mirrors automatically under `dir="rtl"` - the arrow lands on the LEFT, matching the native `<select>`. (Libraries whose arrow stays on the right in RTL are carrying un-mirrored physical CSS, not making a design choice.) Shipped themes use logical properties only (`padding-inline`, never left/right), and `text-overflow: ellipsis` truncates at the logical end for free. The single direction-aware piece of JS is the `'fit-content'` popup width policy: in RTL it right-aligns to the trigger and grows LEFTWARD (direction read from `getComputedStyle(triggerEl).direction` once per open); `'match-trigger'` is position-identical in both directions.
- **Data direction (the app's layer).** Mixed RTL/LTR item texts are handled by the Unicode Bidi Algorithm per item; items and chips are separate blocks / flex items, so labels never reorder across each other, and the trigger's layout never changes because of a chosen label's script (same as native). The remaining caveat is WEAK characters (digits, parentheses, punctuation): their placement follows the element's base direction, which is inherited, never content-detected. The fix is per-item `dir="auto"` or a `<bdi>` wrapper, supplied by the app via `createPopupListItemContentElFn` - the app knows its data, and the library does not force `dir="auto"` because it also flips per-item text alignment, making mixed lists ragged.

Demo: section 17 (the ar / he packs set `dir="rtl"` on the mounts and use a mixed-direction item list, weak-character examples included).

## Rendering model

- State setters (`setItems`, `setChosenItem`, `setChosenItems`, `toggleItem`, `chooseAll`, ...) trigger the needed re-render automatically and fire `onChange` only when the value actually changed (compared via `compareFn`).
- **Render granularity matters at scale.** Rebuilding the whole popup list is O(n) DOM work; for large lists that dominates. So:
  - Bulk changes (replace the whole set, select/deselect all, `setItems`) rebuild the list via `renderPopupList` / `rerender`.
  - Single-item changes (multi-select `toggleItem`) use `replacePopupListItemElInDom(item)`, which replaces just that one item's element. DOM work stays O(1) regardless of list size, so toggling one selection in a 10k-item list does not recreate 10k nodes. (The lookup to find the item is O(n), but a comparison loop is negligible next to DOM mutation + reflow.) A vdom framework would instead diff the list render on each state change; llselect skips that by knowing exactly which item changed. (No published benchmark - this is an implementation description, not a measured comparison.)
- External mutation of an item object's properties (e.g. `users[0].name = 'X'`) is **not** auto-detected. Call `rerender()` to reflect the change in the DOM. `rerender` is a pure visual refresh: it does not fire `onChange` and does not run `onItemsChanged`.

## Popup DOM lifecycle (construction vs open)

The popup's PERSISTENT elements are built in the constructor and stay in the DOM for the instance's whole life, hidden while closed; the option ROWS are lazy (built on `open()`, cleared on `close()` - Phase 3). Per instance the persistent part is five nodes: `popupEl` (`hidden`), `popupListEl` (the listbox), `filterInputEl`, the no-results element, and the hidden value-mirror span next to the trigger. A header / footer container joins them only when its content setting (or a subclass override) returns an element - see "Popup header / footer slots".

- The costly axis is the rows (O(n)) and that axis IS lazy; the persistent part is O(1), so pre-building trades five hidden nodes for the guarantees below.
- ARIA needs the listbox to exist while CLOSED: the trigger carries `aria-controls` -> `popupListId` in both states (see the `A11Y.md` role table), and an ID reference to a nonexistent element is a defect that audit tooling flags - and closed is the state nearly every audit sees. The value-mirror span is referenced by the accname chain while closed for the same reason.
- The filter input's always-built rule has its own recorded rationale below ("Filter box (Phase 8) architecture").
- `setUiTranslationPack` re-applies pack-owned attributes (filter placeholder / fallback `aria-label`) while closed; if these elements were lazily built, every such path would need "if built yet" guards.
- Subclass contract stability: the `create*El` element builders are protected extension points with ONE defined call time (construction), not "whenever first open happens".
- The constant child list is also what makes open / close structurally side-effect-free for the host page - see "In-place popup (no body portal)", host sibling-safety.

## In-place popup (no body portal)

`popupEl` stays a child of the component root; it is never appended to `document.body`. Escaping ancestor clipping is `position: fixed`'s job instead: a fixed element's containing block is normally the viewport, so ancestor `overflow` never clips it (demo 2.1 shows the popup working inside a scroll container). What staying in-subtree buys - each point is load-bearing code, not taste:

- Outside-click and focus-out classify inside-vs-outside with `rootEl.contains(target)`; the popup being inside the root makes clicks / focus in the popup "inside" with zero extra cases. A portal would need every such check duplicated against a second subtree.
- `destroy()` is one `rootEl.replaceChildren()`; nothing can be orphaned in `body`. (The benchmark docs record the real-world version of this failure in portaling libraries: leftover containers in `body`, selectors hitting the wrong widget's dropdown.)
- Inherited context is right for free: themes set font / color on `.llselect-root`, and direction comes from the environment's `dir` (see "RTL" - there is no RTL setting). A portaled popup inherits BODY's context and must copy all of it over.
- Reading order: the popup sits immediately after the trigger for AT virtual cursors.
- Top-layer compatibility: inside an open native `<dialog>`, an in-subtree popup renders within the dialog's top-layer context, while a body-portaled popup renders UNDER the dialog and its `::backdrop` - the classic portal-in-dialog failure. In-place is the arrangement that keeps working there.
- Host sibling-safety: the caller's element BECOMES the root (nothing is ever inserted next to it), and the root's child list is invariant from construction to destroy - the popup element exists from the start, `hidden` while closed, out-of-flow (`position: fixed`, set BEFORE unhiding) while open. So sibling-dependent CSS in the host layout (`:nth-child`, `.btn + .btn`, `:first/last-child` - the uib-tooltip-in-a-btn-group / select2-inserted-container breakage class, where SHOWING the popup inserts an element next to the trigger and reflows the host) never flips on open / close. Pinned by `test/structure.test.ts`.

Accepted costs - two classes, both solved by the planned top-layer enhancement (`TODO.md` "Popup top layer via Popover API"), neither fully by a body portal:

- **Displacement**: an ancestor that creates a fixed-position containing block (`transform`, individual `translate` / `scale` / `rotate`, `filter`, `perspective`, `will-change: transform`, `contain: paint` / `layout` - including via `content-visibility`) re-scopes `position: fixed` to itself, so the positioner's viewport coordinates land displaced.
- **Paint trapping**: the themes' `z-index: 1000` on the popup is local to whatever stacking context the ROOT sits in (any ancestor with `z-index` on a positioned element, `opacity < 1`, `mix-blend-mode`, `isolation`, ...). Overlapping content in a higher-ordered context - classic case: a sticky header with a root-level `z-index` painting over a popup that flipped upward out of a low-z-index card - covers the popup even though it is positioned correctly. This is the residual form of the append-to-body-era landmines: `position: fixed` already removed ancestor-overflow clipping and offsetParent coordinate math, the two big ones that forced absolute-positioned popup libraries (UI Bootstrap tooltips / dropdowns etc.) into blanket `appendToBody: true`, but paint order stays context-trapped.

The fix is IMPLEMENTED as a feature-detected top-layer enhancement (constructor + `open()` / `close()` in `base.ts`): where the Popover API exists, the popup carries `popover="manual"` from construction and `open()` calls `showPopover()` - the top layer paints above ALL stacking contexts and has no fixed-position containing block, and the element does NOT move in the DOM, so every in-subtree invariant above keeps holding; the positioner keeps supplying the inline `position: fixed` coordinates unchanged. Browsers without the API run the plain `position: fixed` path unchanged - for them the two failure classes remain the accepted limitation (`TODO.md`). Details locked in:

- `'manual'`, not `'auto'`: `auto` brings the browser's light dismiss (outside click / Esc close), which would fight `outsideClickBehavior` and the library's own Esc handling. `manual` takes only the top-layer painting; behavior authority stays with the library.
- UA `[popover]` stylesheet interactions: `inset: 0` would over-constrain the box (and in an RTL containing block an over-constrained `left` LOSES to `right: 0`), so `open()` pins inline `right/bottom: auto` and `close()` clears them. `showPopover()` must run BEFORE the positioner measures (a popover not in showing state is `display: none !important`). The UA popover chrome (`border` / `padding` / `color` / `background`) is beaten by explicit author declarations in every shipped theme (vanilla gained explicit `color` / `padding` for this); custom themes must set popup chrome explicitly or the UA popover look leaks in top-layer mode.
- Force-hide resilience: `dialog.showModal()` hides all popovers behind the library's back; the paired `hidePopover()` in `close()` then throws `InvalidStateError` and is caught - state resyncs there, and the next open recovers.

A body portal, by contrast, fixes only displacement - a body-appended popup still loses paint order to root-context competitors above its own `z-index`, renders UNDER an open `<dialog>` and its `::backdrop`, and forfeits the invariants above - so it stays rejected.

## Prefix typeahead (Phase 7, revived)

Native-`<select>`-style prefix typeahead while the filter is inactive. Phase 7 was DROPPED in `archive/roadmap-v0.0.1.md` on the ground "useless for CJK / IME input"; that drop is superseded - the argument only rules typeahead out as a REPLACEMENT for the filter box, not as an addition for scripts typed without an IME (Latin / Cyrillic / digits; the motivating case is long year / country lists). Maintainer-ratified rulings, panel-reviewed:

- Closed + printable character: OPEN the popup and move the active option to the first match. Typing never commits a value (native `<select>` mutates the value per keystroke while closed - that fires `onChange` once per transient prefix, typing "1985" = four changes, and has no multiple-mode meaning, so the APG select-only model wins for both modes); activation stays Enter / Space / click.
- The closed-state search starts relative to the COMMITTED selection (`computeTypeaheadClosedStartIndex`: single overrides with the chosen item's index; default -1 = from the top), never relative to the convenience focus `focusInitial` parks - anchoring on that focus skips the first match (`['apple','avocado']` + "a" landed on avocado; HIGH-95 in `FIXME.md`).
- Space always activates; it never joins the buffer. Native folds Space into an active buffer; rejected because multiple-mode Space is the toggle key, and an invisible timeout must not change what a key does. Multi-word prefixes are a `filterable` use case.
- The typeahead search wraps around the list; arrow navigation stays clamped. Search and relative motion are different operations, and same-character cycling needs the wrap.
- Match = `itemToString` folded per code point, then `startsWith` - same text source as the filter's default compare (that compare is substring `includes`; this one is prefix). The fold (`foldForTypeahead` in `keyboard.ts`) lower-cases each code point on its own and maps the Greek final sigma to sigma on BOTH sides: whole-string `toLowerCase` applies the Final_Sigma rule, which folds a trailing sigma differently at the end of the buffer than mid-word in the text (QUALITY-101). No diacritic folding, no `toLocaleLowerCase` (host-locale-dependent), and never `filterFn` (its contract is substring / user-defined; a fuzzy one would make everything match the first key).
- A repeated-character buffer ("aa") always cycles like its single character - the native rule. The W3C APG example instead tries the literal doubled prefix first; rejected for native parity and simplicity (a text really starting "aa" is still reached by the cycle). The repeated-character test compares code points folded one by one, so the Turkish dotted capital I (lower-case form expands to two code units), astral-plane characters, and a mid-repeat Shift ("aA") all still cycle.
- Any other multi-character buffer searches from the active option INCLUSIVELY, so extending the prefix stays put while the current option still matches (also the native rule).
- Always on while the open cycle's filter is inactive; no setting. While closed, the `filterable` predicate is evaluated fresh (the cached per-open flag can be stale); a would-be-filterable open leaves printable keys alone - they belong to the filter input.
- The choose-all row is never a typeahead target: its counting text mutates as the user selects, so it cannot be a stable match.
- Buffer expiry is a timestamp delta checked on the next keystroke (1 s, matching native implementations) - deliberately not a `setTimeout`, so there is no timer to clean up and nothing time-dependent in tests.

Behavior contract (key tables, buffer reset points): `A11Y.md`. Pure matching logic: `findTypeaheadIndex` in `src/keyboard.ts`.

## Filter box (Phase 8) architecture

Locked decisions for the filterable variant. Keyboard / focus / ARIA contract is in `A11Y.md`.

- **`<input>` is always built** into `popupEl` above `popupListEl`, even when `filterable: false`. The non-filterable case carries the `hidden` attribute (not `disabled`, not `readonly`). Cost: one unused element when not needed. Benefit: future runtime toggle (select2-style `minimumResultsForSearch`, setItems crossing a threshold, ...) is a CSS flip rather than a DOM rebuild.
- **Focus host branches by current filterable state**, not by DOM existence:
  - `filterable: true`: trigger becomes `role="button"` (`aria-haspopup="listbox"`), focus moves to the input on open, `aria-activedescendant` lives on the input.
  - `filterable: false`: trigger stays `role="combobox"`, focus stays on the trigger, `aria-activedescendant` lives on the trigger. Identical to the pre-Phase-8 behaviour - non-filter selects regress nowhere.
- **No subclass split.** Filtering is a capability setting on the existing `LLSelectSingle` / `LLSelectMultiple`. Subclassing per feature would multiply combinatorially (filter x optgroup x ...); a setting composes.
- **Settings:** `filterable: boolean | ((items: readonly T[]) => boolean)` (default `false`). The predicate form is the conditional-display knob (select2's `minimumResultsForSearch`, rewritten as a caller-authored predicate so the condition is self-documenting and not count-only): evaluated against the full item list on every `open()`, never mid-open - crossing the threshold via `setItems` applies on the next open, so the focus host is never yanked while the popup is up. Also: `filterFn: ((item, query) => boolean) | null` (default `null` = case-insensitive substring on `itemToString`); `uiTranslationPack.filterInputAriaLabel` (default `'Search'` - a FALLBACK accessible name for the input, used only when the app supplies neither `ariaLabel` nor `ariaLabelledBy`; the field name replaces it otherwise) and `uiTranslationPack.filterInputPlaceholder` (default `'Filter (Esc to clear)'` - also teaches the Esc-clears-filter behavior; `null` = no placeholder) - see "Texts (i18n)" below. IME-aware filtering (composition-guarded) is part of the contract; see `A11Y.md`.

### Query-match highlighting (helper, not a setting)

`createHighlightedTextEl(text, query, createMatchElFn?)` (query-highlight.ts) builds a detached `<span>` with each case-insensitive `query` occurrence wrapped in `<mark>` (or the caller's element). Decisions:

- Exported pure helper, NOT a boolean setting: the customization point already exists - `createPopupListItemContentElFn` re-runs per rendered row per render (filter keystrokes included), so core carries no highlight state. A setting could only affect the default text path and would silently stop the moment a custom content fn takes over; the helper composes with any content fn. Same packaging as `gatherItemsByGroupKey` / the icon builders.
- Mirrors the built-in matcher exactly (`toLowerCase` both sides, no trim): the marks must agree with what filtering kept. A custom `filterFn`'s ranges are unknowable to the library; the docstring says to mark your own.
- Accessible names are immune by construction: when a content fn returns an element the option's `aria-label` comes from `itemToString`, so `<mark>` never leaks into what AT speaks.
- Offsets are found on the lower-cased pair and applied to the original string; when lower-casing changes a length (a Unicode expansion, e.g. U+0130) it degrades to unmarked plain text rather than marking wrong ranges.
- Default mark is a bare `<mark>`: native styling works with zero CSS; themes may restyle. `createMatchElFn` returns a fully built element inserted as-is.
- The ctx-param question is settled: no settings function receives the instance; the closure recipe is the contract, and only the header / footer content functions get a narrow `LLSelectConstructionContext`. The full reasoning is in `popup-rows-and-callbacks.md` section 4. A `query` context for `createPopupListItemContentElFn` stays open as its own question.

## Disabled (Phase 9)

Two independent axes, modelled differently on purpose.

- **Control-level** (the whole select): runtime *state*, set imperatively.
  - `setDisabled(boolean)` + `isDisabled(): boolean`. Whole-control disabled is universally a boolean (a `disabled` prop in React libs; a method like choices.js `.disable()` / select2 in vanilla ones) - never a predicate. The method form matches both those vanilla libs and llselect's own state-via- method pattern. NOT a setting - disabled is mutable state like `items` / `chosenItems`, and this design keeps mutable state out of settings. Default enabled; to start disabled, call `setDisabled(true)` after construction.
  - `focusableWhenDisabled: boolean` setting (default `false`) - the only knob; controls whether a disabled trigger stays in the tab order.
  - Disabled trigger: `aria-disabled="true"`, `data-disabled="true"`, `tabindex` = `focusableWhenDisabled ? 0 : -1`. `open()` / `toggle()` / keyboard are no-ops; an open popup is closed by `setDisabled(true)`.

- **Item-level** (individual options): derived *property*, read declaratively.
  - `itemDisabledFn: ((item: T) => boolean) | null` setting (default `null` = nothing disabled). Matches react-select `isOptionDisabled` / MUI Autocomplete `getOptionDisabled` - the flat-generic-options libraries closest to llselect. A predicate is the only generic-`T` option: the data-field approach (native / Ant / choices / select2 carry `disabled` ON the option) needs the option to be an object with a known field, which is impossible when `T` is unknown. `protected isItemEffectivelyDisabled(item): boolean` is the internal helper (also for subclasses overriding `createPopupListItemEl`); not public. NO `setItemsDisabled`: a predicate subsumes it (it can read an external set and you call `rerender()`), keeps a single source of truth, avoids reconciling a disabled-set across `setItems`, and is faster - item identity is `compareFn`-based, so a maintained set is O(n*d) membership vs the predicate's O(1) property read. Evaluated once per item per render, never cached across renders (avoids react-select's stale-disabled-between-renders bug).
  - Disabled item: `aria-disabled="true"`, `.llselect-popup-list-row-disabled` class, no click selection - selection is truly blocked, not merely `aria-disabled` (avoids MUI's disabled-options-still-selectable bug) - and skipped by keyboard nav (arrows / Home / End / Page land on the nearest enabled item; if none in the travel direction, focus stays).

Why the asymmetry (method for control, predicate for item): control-disabled is an app decision not derivable from any item, and is universally a plain boolean; item-disabled is typically intrinsic to the item (out-of-stock, no permission) and, for a generic-`T` flat-options library, can only be asked via a predicate - exactly what react-select and MUI Autocomplete do.

Cross-cutting:

- **Never the native `disabled` attribute - always `aria-disabled`.** Native `disabled` suppresses pointer + focus events, which blocks the hover / focus tooltip that would explain *why* a control is disabled. A custom control keeps the element perceivable. The library only exposes hooks (`aria-disabled` / `data-disabled` / `.llselect-popup-list-row-disabled`); it never ships or wires a reason / tooltip itself (that would fight tooltip libraries' own `aria-describedby`).
- **Themes** convey disabled with `cursor: not-allowed` + opacity, never `pointer-events: none` (which would re-block hover tooltips).
- **Selection retention:** an already-chosen item that becomes disabled stays chosen (matches native: disabling a selected `<option>` keeps it selected; `select.value` and `selectedOptions` still report it, the collapsed control still shows it). Native form behavior has no counterpart here: a form omits a selected option that is disabled when it submits, while `required` still counts it as chosen; llselect does not submit form values, so the README form-integration section tells the app to remove or disable the hidden input of a disabled item before the form submits, items in a disabled group included. `setChosenItem(s)` is unrestricted - programmatic selection ignores disabled.
- **Bulk ops skip disabled:** `chooseAll` chooses every *enabled* item of the current item list and preserves an already-chosen disabled item that is in that list (a chosen item outside the list, which `setChosenItems` and `toggleItem` accept, is dropped when the selection is rebuilt from the list, disabled or not); `unchooseAll` clears enabled choices and preserves disabled-chosen, listed or not; `toggleAll` runs `unchooseAll` when the list holds an enabled item and every enabled item is chosen, otherwise `chooseAll` (a list with no enabled item takes the `chooseAll` branch); `toggleAllVisible`, the choose-all row's action, acts on the visible enabled subset and preserves every other choice, listed or not.

Group-level disabled (a disabled optgroup disabling its items) is specified in "Optgroup (Phase 10)" below; it layers on this item-level disabled.

## Optgroup (Phase 10)

Decided: grouping is a **derived projection of the flat `items` list**, not a nested data structure. `items` stays `T[]`; a setting maps each item to a group *key*, and the group's label + disabled state are derived from that key. Design research (how native / select2 / choices / react-select / MUI / Downshift model it) is in `archive/optgroup-research.md`.

### Data model: flat + derived, mirroring the item layer

Rejected: a nested shape (`(T | { label, items: T[] })[]` or a second `setGroups()` channel). Chosen: flat items + `*Fn`s that derive the group. The group layer is a **complete mirror of the item layer** - same four concerns, same shapes:

| concern  | item layer               | group layer                             |
|---|---|---|
| identity | `T`                      | `GroupKey` (grouping key; class `<T, GroupKey = string>`) |
| equality | `compareFn(a, b)`        | `groupKeyCompareFn(a, b)`               |
| display (text) | `itemToStringFn(item)` | `groupKeyToStringFn(key)`             |
| display (rich) | `createPopupListItemContentElFn(item)` | `createGroupLabelContentElFn(key, itemsInGroup)` |
| full control (subclass) | `createPopupListItemEl` (protected) | `createGroupEl` (protected) |
| disabled | `itemDisabledFn(item)`   | `groupDisabledFn(key)`                  |

Items must be UNIQUE under `compareFn` - it defines item identity and the selection is a set, so compareFn-equal items get stale selection DOM. `setItems` warns once per page under the DEFAULT `compareFn` (an O(n) Set check); a custom `compareFn` is not scanned (an O(n^2) check would tax large lists, per PERFORMANCE-31) and keeping its identity unique is the caller's job. `GroupKey` mirrors this under `groupKeyCompareFn`.

Why this shape, in this codebase specifically:

- **Single source of truth.** `items` stays the only data channel. A nested shape is a second write channel - exactly the select2 / choices.js dual-write pattern this project already rejects ("Settings vs methods" above).
- **Identity, not display, drives behavior.** `itemDisabledFn` takes the item `T` (identity), never `itemToString(item)` (display). Grouping obeys the same rule: membership and group-disabled are keyed on `GroupKey`; the human label is a separate `GroupKey -> string` projection. So renaming a label (i18n) never changes which items group together or which group is disabled.
- **`GroupKey` is fully generic, mirroring `T`.** The class is `<T, GroupKey = string>`; the default leaves every existing `LLSelect*<T>` call unchanged. A number / object key is allowed exactly as `T` is - equality is asked via `groupKeyCompareFn` (default: identity - `===` plus `NaN` equals `NaN`, the same rule as the default `compareFn`), the same way `compareFn` handles arbitrary `T`. This dodges the hard-coded-string-key trap where widening the key type later would be a breaking change.
- **`GroupKey` never touches the DOM.** Group containers get an index-based id (`-group${index}`, like items' `-item${index}`); the `aria-label` comes from `groupKeyToStringFn` (visible content optionally from `createGroupLabelContentElFn`), disabled state from a computed boolean. So an object key needs no `String(key)` serialization anywhere.
- **Settings compose; no subclass split.** Same reasoning as the filter box: a capability that combines with others (filter x optgroup x ...) must be a setting, not a subclass, or the class count multiplies.
- **Nested's unique wins are out of scope.** A nested shape is only strictly needed for empty groups (a label with no items), one item in multiple groups, or group order decoupled from item order. Native `<select>` supports none of these and neither do we ("Library scope"), so we give up nothing real.

Honest cost, since softened: rendering works on contiguous runs. By default the library derives the DISPLAY order by gathering non-contiguous groups (`gatherGroups: true`, see contiguous-run below); the DATA (`items` / `getItems()`) is never reordered. `gatherGroups: false` restores the strict pre-sorted requirement.

### Settings

All live on `LLSelectBaseSettings<T, GroupKey>` (single + multiple; `GroupKey = string` default). Named by return type per the callback convention ("Function-typed settings"; `naming-conventions.md` s3). All but the boolean `gatherGroups` are `| null`; each `null` documented per CLAUDE.md:

- `itemToGroupKeyFn: ((item: T) => GroupKey | null) | null` (default `null`). The one setting that turns grouping on; returns the key of the group an item belongs to. Two distinct `null`s:
  - **setting `null`** (default): grouping off entirely - flat list, no labels, zero behavior change from today. (A subclass `itemToGroupKey` override can still turn grouping on: the method is authoritative - render, gather, and the disabled layer all resolve keys through it.)
  - **fn returns `null`** for an item: that item is in no group and renders ungrouped (like an `<option>` outside any `<optgroup>`); consecutive ungrouped items are not gathered into one group. Backed by `protected itemToGroupKey(item)` (Customization model: override to replace).
- `gatherGroups: boolean` (default `true`). Gathers non-contiguous groups into display order before rendering; `false` = strict pre-sorted mode (duplicate label + `console.warn` on violation). The gather itself is the exported pure function `gatherItemsByGroupKey(items, itemToGroupKeyFn, groupKeyCompareFn?)` - the instance runs the same function internally, so a caller opting out can pre-gather with it.
- `groupKeyCompareFn: ((a: GroupKey, b: GroupKey) => boolean) | null` (default `null` = identity, `===` plus `NaN` equals `NaN`, like the default `compareFn`). Decides whether two adjacent items share a group (see contiguous-run). Mirrors `compareFn`; only worth setting when `GroupKey` is an object without usable reference identity.
- `groupKeyToStringFn: ((groupKey: GroupKey) => string) | null` (default `null` = `String(groupKey)`). The `GroupKey -> display text` projection; the i18n customization point. Backed by `protected groupKeyToString(key)`.
- `groupDisabledFn: ((groupKey: GroupKey) => boolean) | null` (default `null` = no group disabled). `true` = every item in that group is treated as disabled. Backed by `protected isGroupDisabled(key)`.
- `createGroupLabelContentElFn: ((groupKey: GroupKey, itemsInGroup: readonly T[]) => HTMLElement | null) | null` (default `null`). The rich-label customization point, mirroring `createPopupListItemContentElFn`: fills the label's visible content (icon, count badge; cf. react-select `formatGroupLabel`, MUI `renderGroup`). `null` (setting or returned) = plain text from `groupKeyToString`. The accessible name stays `groupKeyToString` (container `aria-label`); the label element stays `aria-hidden`. `itemsInGroup` (the group's items) is what makes counts / summaries possible without recomputing the grouping. Backed by `protected createGroupLabelContentEl(key, itemsInGroup)`.

The full-control escape hatch mirrors `createPopupListItemEl`: `protected createGroupEl(key, index, itemsInGroup, itemEls)` builds the whole group container (id, `role="group"`, `aria-label`, label element, items) and is overridable for a custom group element.

### Grouping semantic (gather + contiguous-run)

Consecutive visible items whose keys are equal (per `groupKeyCompareFn`) form one group; a differing key opens a new group label. Items whose key is `null` are ungrouped. This preserves the visible-list order and the `itemEls[i] <-> getVisibleItems()[i]` index alignment exactly.

Display order is derived BEFORE rendering: with `gatherGroups: true` (default) the base list runs through `gatherItemsByGroupKey` - groups gather at their key's first appearance, within-group relative order kept, `null`-key items in place; already-contiguous input is detected in one scan and returned as the same array, so sorted data behaves byte-identically to strict mode. The gather is memoized and lazy: `setItems` only invalidates; it materializes at first need (open, or a filter recompute) and the DATA (`items` / `getItems()`) is never reordered - the gather is display-only. Filtering runs over the gathered base, so filter keystrokes never re-gather and a group's position cannot jump while typing (pinned by first appearance in the FULL list).

`gatherGroups: false` is the strict mode for callers who guarantee pre-sorted data (pre-gathering with the exported function counts): the known trap (same as MUI's `groupBy`) returns - a key reappearing after a gap produces a second label for the same group - and the render pass `console.warn`s once, surfacing the broken sort instead of silently fixing it. Two visually separate sections with the same label text stay expressible in both modes: two distinct keys mapped to one display string by `groupKeyToStringFn`.

### Interaction with existing machinery

- **Keyboard / index alignment: free.** Group labels are NOT added to `itemEls`, so `getVisibleItems()` stays a flat `T[]` and keyboard nav skips labels with no extra logic.
- **Filtering: composes for free.** The base list is gathered once (memoized per `setItems`); the filter then runs over that gathered base per keystroke. Filtering preserves contiguity, so regrouping the survivors at render needs nothing extra, and a group whose every item was filtered out emits no label (empty groups vanish).
- **Disabled layering.** `isItemEffectivelyDisabled(item)` also returns `true` when the item's group is disabled (`isGroupDisabled(itemToGroupKey(item))`) - so every existing item-disabled behavior (no click selection, keyboard skip, `aria-disabled`, selection retention, bulk-op skipping with the per-op scope stated under "Bulk ops skip disabled") covers group-disabled automatically, with no new code paths. This is the layering the Phase 9 design deferred here.
- **Render granularity unchanged.** Toggling one item's selection does not change its group membership, so multi-select `replacePopupListItemElInDom` stays O(1) DOM work; the group structure is untouched.

### ARIA

Matches the APG grouped-listbox example. Each group is a container `role="group"` with `aria-label` set to `groupKeyToStringFn(key)`; the visible label element carries `.llselect-group-label` and `aria-hidden="true"` (its text is already the group's accessible name via `aria-label`, so it must not be announced twice). A disabled group's container gets `aria-disabled="true"` + `data-disabled`. The keyboard / focus contract is in `A11Y.md` ("Grouping").

### Implementation note (resolved)

`ensureVisibleInScroll` (keyboard.ts) uses `getBoundingClientRect`-delta math (offsetParent-independent), NOT `offsetTop`, so it stays correct when items nest inside group containers regardless of theme CSS - including a `position: relative` group. Measured on a 10k list in Firefox + Chromium (`demo/bench-reflow.html`): rect and offsetTop cost the same per keyboard move (< 0.15% of a 60fps frame), and offsetTop was confirmed correct ONLY while groups stay `position: static` (289575px off once a group is positioned) - exactly the theme fragility rect removes at zero cost.

## Tags (triggerDisplay)

`LLSelectMultiple` shows chosen items two ways, picked by the `triggerDisplay` setting: `'count'` (default, a "3 / 10 selected" summary) or `'tags'` (one removable chip per chosen item). Tags is a capability ON `LLSelectMultiple`, not a subclass - same rule as filterable.

### Why on LLSelectMultiple, not a subclass

- **Not a new kind of select** - still a multi-select, just a different trigger display. `renderTriggerContent` already owns the trigger's look (it renders the count summary); tags is another branch of it, not a new type.
- **Capability = setting** (DESIGN "Filter box"): tags must combine with filterable / optgroup; a subclass would explode into `LLSelectTags` x `LLSelectFilterable` x ... A setting composes.
- **Single has no tags** (one chip is meaningless), so it lives on Multiple, not Base.

### Two-layer content, mirroring the item layer

The overlap with `createTriggerContentElFn` is resolved the same way item / group content is - two granularities:

| granularity | item | trigger-tags |
|---|---|---|
| take over the whole element | `createPopupListItemEl` | `createTriggerContentElFn` (whole trigger) |
| fill only the visible content | `createPopupListItemContentElFn` | `createTagContentElFn` (one chip) |

- Precedence: `createTriggerContentElFn` (full control) > `triggerDisplay: 'tags'`
> `'count'`. Same as `createPopupListItemEl` over `createPopupListItemContentEl`.
- `createTagContentElFn: (item) => HTMLElement | null` fills one chip's visible content; the library owns the chip container, the default text span (`tagTextClass`, which carries the item's `lang`), the remove button, and aria. `null` = plain `itemToString`. The remove button's icon is separately fillable via `createTagRemoveButtonContentElFn` (see "Remove button" below).
- Protected chain (each overridable): `renderTriggerContent` -> `createTagsEl` (chip strip) -> `createTagEl(item)` (one chip; assembles content + remove) -> `createTagContentEl(item)` / `createTagRemoveButtonEl(item)` (each fills one half and reads its `*Fn` setting).

### Remove button + ARIA (select2-style MVP)

Each chip's remove control is `<button aria-label="Remove <itemToString>" tabindex="-1">` (label text from `uiTranslationPack.tagRemoveButtonAriaLabel`, via `itemToTagRemoveButtonAriaLabel`); its click `stopPropagation`s (so it never toggles the popup) then calls `toggleItem`, which re-renders the trigger - unless the whole control or the item itself is effectively disabled, in which case the click is a no-op and the item stays chosen (see A11Y.md Tags / Disabled). `tabindex="-1"` keeps it out of the tab order - keyboard users remove via the popup (deselect), matching select2. Full chip keyboard nav (grid pattern) is deferred: APG has no standalone tag/token pattern and it would fight the combobox `aria-activedescendant` model. See A11Y.md "Tags". By default the button is empty and the x is a CSS glyph (`.llselect-tag-remove-button:empty::before { content: '\00d7' }`), so the theme owns the look and the accessible name stays the `aria-label`. `createTagRemoveButtonContentElFn: (item) => HTMLElement | SVGElement | null` optionally fills a custom icon (mirrors the clear button's `createTriggerClearButtonContentElFn`; the icon is decorative, never the accessible name); `protected createTagRemoveButtonEl(item)` builds the whole button and is the full-control override, mirroring `createTriggerClearButtonEl`.

## Clear button (clearable)

`clearable: boolean` (default false) shows an x button that empties the selection. It lives in its OWN trigger slot, next to the arrow:

    triggerEl > [ triggerContentEl | clearEl (.llselect-trigger-clear-button) | triggerArrowEl ]

### Own slot = no collision with createTriggerContentElFn

Same trick as the arrow: clear and arrow are separate slots, so `createTriggerContentElFn` (which only replaces the content slot) never touches them. This is why the arrow never needed conflict resolution - it was never in the content slot - and clear copies that exactly.

### What the library owns vs what you fill

- Library owns: the `<button>`, its click (`stopPropagation` so it never toggles the popup, then `clearSelection`), `aria-label="Clear selection"`, `tabindex="-1"`, and hide-when-empty (theme hides it under `.llselect-trigger[data-empty='true']`). A core-side hide was REJECTED: the library writes the state attribute, the theme decides the look, like every other visual state; a custom theme hides the button with one CSS rule.
- You optionally fill the icon via `createTriggerClearButtonContentElFn: () => HTMLElement | SVGElement | null` (mirrors `createTriggerArrowContentElFn`); `null` = theme CSS glyph (`.llselect-trigger-clear-button:empty::before { content: '\00d7' }`).
- `protected clearSelection()`: base no-op; single -> `setChosenItem(undefined)`, multiple -> `setChosenItems([])`. Both go through the normal setters, so `onChange` fires with the empty value - no separate `onClear`. Clear means "back to empty / placeholder", not "back to some default option" (do that yourself in `onChange` if wanted; `meta.reason === 'clear'` marks the firing).
- A configurable cleared value (`clearTo: T` and the like) was considered and REJECTED. Survey: nobody offers one - react-select and MUI clear to `null`, antd and ui-select to `undefined`, Select2 / Slim Select / native return to a placeholder `<option>` whose value is `''` (there, "empty" is itself an option). The type argument is decisive: "nothing chosen" exists at construction, before any clear, so `getChosenItem(): T | undefined` cannot lose the `| undefined` whatever clear returns - a `clearTo` buys no type safety and conflates clearing with choosing a default. The plain-`string`-model recipes live in the `clearable` docstring (a real "none" item, or coerce in `onChange`).

## Choose-all default: plain counting text (no indicator)

The choose-all row's default content is JUST the counting text (`uiTranslationPack.chooseAllRowText`, e.g. "Select all (3 of 10)"). No icon, no glyph. RULED:

- Consistency: the library ships no default visual indicator anywhere - no trigger arrow, no per-item checkboxes; selected state is theme styling off `aria-selected`. A choose-all-only indicator was the single exception, and nothing ever required one.
- The counting text already encodes the tri-state: "0 of 10" / "3 of 10" / "10 of 10". Any indicator restates the numbers.
- The hooks stay: `data-chosen-state="none|some|all"` on the row for CSS, `createChooseAllRowContentElFn` for real content (e.g. `createOutlinedCheckboxSvgEl`). Batteries-included defaults live a layer up - the AngularJS package's `ll-checkboxes` does exactly that.
- History, so this is not re-litigated: the default indicator was first a theme `::before` glyph gated by `:not(:has(*))` (a gate above the browser support floor, so it silently died on floor browsers, and generated content lands in the accessible-name computation), then a core-rendered `createOutlinedCheckboxSvgEl` (couples `icons.ts` into every multi bundle and makes the core pick outlined vs filled), then a core-rendered aria-hidden text glyph (redundant with the numbers, font-dependent look). Each step fixed the previous mechanism's defect; the actual answer was that the indicator itself was never needed.

## hideChosenRows: chosen rows leave the popup list (multiple)

`hideChosenRows: true` (LLSelectMultiple, default `false`) removes chosen items' rows from the popup list; unchoosing puts them back. RULED:

- A setting, not a new default: ui-select (`remove-selected`) and react-select (`hideSelectedOptions`) hide by default, while select2 and native `<select multiple>` keep chosen rows listed. Both camps are legitimate, so the flag defaults to llselect's shipped behavior (keep).
- Multiple only. A single's chosen row staying listed is universal.
- The subtraction is a `getVisibleItems()` override, so every consumer of "visible" (rendering, keyboard nav, `toggleAllVisible`, the choose-all counts, the no-results state) agrees for free. The enabled-filtered variant is its own public, overridable method, `getVisibleEnabledItems` (multiple): the choose-all row (counts, tri-state, click) and `toggleAllVisible` read that one method, so a subclass narrowing the bulk-selection scope overrides it once (the tree-select demo narrows it to leaf nodes). The default `compareFn` gets a Set lookup; a custom `compareFn` costs O(visible x chosen). Either cost is paid once per change: the result is cached, and validity is two reference checks (every upstream layer and the chosen set replace their arrays on change, never mutate in place).
- `toggleItem` keeps its O(1) single-row DOM swap only while the flag is off. With it on, the toggled row leaves or re-enters the list and shifts the indexes, so it falls back to a full `renderPopupList`.
- chooseAllRow + hideChosenRows is ALLOWED, not a throw. Recorded design intent: chooseAllRow is designed for checkbox-style multiples - rows that stay listed and show their chosen state. Combined with hiding, the visible subset is always fully unchosen: the row degrades to "choose everything still listed", its tri-state never reaches all-chosen, and it disappears with the last actionable row (the standing no-actionable -> no-leading-row rule).
- Why permissive here, unlike the AngularJS ll-highlight + ll-popup-list-item-content-fn throw: that conflict has no coherent behavior (two owners of one content slot), while this combination has exactly one well-defined behavior that falls out of the standing visible-subset semantics. Core stays low level and does not forbid an unusual-but-coherent UI choice.
- When every item is chosen, the popup shows the regular no-results element. No new translation key.

## chosenItemsOrder: chosen order follows the choice or the list (multiple)

`chosenItemsOrder` (LLSelectMultiple, default `'as-chosen'`) sets the order of `chosenItems`, which tags, `getChosenItems`, `onChange` and framework models all read. RULED:

- `'as-chosen'` stays the default and the stored state: it is the richer information. From it the app can derive list order by sorting; from list order the choice order is gone.
- `'as-listed'` normalizes in the places chosen arrays enter (`setChosenItems`, the `toggleItem` add path, the `setItems` reconciliation), so every reader agrees. A reorder counts as a change: `onChange` fires, matching the order-sensitive equality of `setChosenItems`.
- Chosen items the list does not hold go last, in chosen order; the next `setItems` drops them anyway.
- Prior art: Slim Select `keepOrder` (default list order, opt into choice order) and Choices.js `shouldSortItems` (default choice order, opt into a sorter). Both camps exist. A custom sort function is not offered: the item list itself carries the app's preferred order.

## Change reason (`meta.reason`, `meta.item`)

`onChange` receives, beside `source` (who started the change), what the change did to the data: `meta.reason`, the closed union `'choose' | 'unchoose' | 'clear' | 'set' | 'items'`, and for the two single-item reasons the item itself in `meta.item`. RULED (the veto-hook committee, `change-veto-committee.md`, plus the owner's rulings on the shape):

- `reason` names the operation, `source` names the initiator; neither encodes the other. A programmatic `toggleItem` that adds is `{ source: 'api', reason: 'choose', item }`; the clear button is `{ source: 'user', reason: 'clear' }`.
- The operation decides, not the control, and only a whole-value write or a bulk op reads its result: a single-item toggle is `'choose'` or `'unchoose'` even when it empties the selection; in multiple mode a whole-value write or a bulk op (a `choose*` method, the choose-all row) is `'clear'` when its result is empty and `'set'` otherwise, so `setChosenItems(['a'])` from empty is `'set'` with no `item`, while in single mode setting an item is `'choose'` and the empty write is `'clear'`; the `setItems` reconciliation is `'items'` even when it empties the selection. Minimal on purpose: a control-level vocabulary (`'tag-remove'`, `'choose-all'`, ...) would describe UI structure, not data, nobody asked for it, and `source` plus `item` already tell the single-item cases apart.
- A plain string union, not a `const` object and not an enum (owner ruling, against a 4:2 committee vote for the object): the value meanings live as bullets on the type alias and on the `reason` field docstring, which editors show on hover; a bare literal shows no docs under any representation; a string enum rejects the plain literal; a published `const enum` is the handbook's library hazard under this `isolatedModules` build.
- A discriminated union on `reason` (owner ruling: the type itself states when `item` exists): `LLSelectItemChangeMeta<T>` (`'choose'` / `'unchoose'`, `item: T`) and `LLSelectWholeValueChangeMeta` (`'clear'` / `'set'` / `'items'`, `item?: never`), both extending `LLSelectBaseChangeMeta`, which carries the `source` and `reason` docstrings once; the TypeScript 5.9 language service shows those docstrings on `meta.reason` and `meta.item` before and after narrowing, which inline union members with docs on one member do not. The type test pins `meta.item` as `T` after narrowing and `T | undefined` before.
- `LLSelectChangeMeta<T = unknown>`: the defaulted type parameter keeps every bare annotation compiling (the defaulted-generic rule).
- First consumer: the ui-select bridge fires `on-select` / `on-remove` straight from `meta.item` for a toggle and keeps its diff for the bulk reasons.
- `'clear'` is also the answer to the rejected separate `onClear` (the clear button above): branch on `meta.reason`.

## Vetoing a user change (`onBeforeChange`)

An app can stop one user change at the moment it happens, for a decision that depends on live state: a confirmation, a business rule, a count cap. RULED by the veto-hook committee (`change-veto-committee.md`) and the owner:

- Shape: an `on*` event setting, `onBeforeChange(next, previous, event)`, whose `event` is `LLSelectBeforeChangeEvent<T>`: the `LLSelectChangeMeta<T>` facts, read-only, with `source` narrowed to `'user'` and `reason` never `'items'`, plus `preventDefault()` and a readable `defaultPrevented`. The return value is ignored. Chosen over a boolean predicate, where `return false` versus `return` versus `return undefined` is implicit (SlimSelect's source checks `=== false` on one path and `=== true` on another), and over a value-returning change function, which puts veto and rewrite in one function. `preventDefault()` is the web platform's word (`beforeinput`, `beforetoggle`); the setting takes the platform's `before` prefix and the after-the-fact events keep their names (`onChange` stays).
- Scope: user only. The hook runs for the library's own pointer and keyboard paths, the row activation by click or Enter / Space, the tag chip's remove button, the clear button and the choose-all row, and never for programmatic setters, the `setItems` reconciliation or an action row's own setter calls, which are the app's own command. Kendo UI scopes the same way; gating every setter would route the AngularJS model write-back through the app's hook and desynchronise `ngModel`.
- Gate at the entry layer, not inside the setters: each user path computes the next value, returns when it equals the current one (a no-op pick never asks), dispatches, then calls the untouched `void` setter. The next value comes from the same pure helpers the setters use (`nextAfterToggle`, `nextAfterToggleAllVisible`, `normalizeChosen`), so the hook sees exactly what would be committed. Inside the setters the gate would have to report "vetoed" back, against the `void` ruling, and the user attribution is consumed by the first change of a gesture, so a source check there is unreliable for a second change.
- A vetoed change writes nothing, renders nothing and fires no `onChange`. In single mode a vetoed pick still closes the popup, like any pick while the popup is open (owner ruling after a 4:2 committee vote in two rounds; the premise that staying open desynchronises a modal was refuted: the `focusout` handler closes the widget when a dialog takes focus). The clear button, the chip remove button and multiple mode leave the popup as it is.
- The protected `onChosenChanging` hook and the setting both run, hook first, even when the hook already cancelled; a cancel cannot be undone, so no `super` discipline is needed, unlike a predicate whose override would replace the setting.
- `preventDefault()` counts only while the handlers run; afterwards the event is sealed. A setter called synchronously inside a handler, `setItems` included, wins and the pending change is dropped: the gate compares a change revision, bumped by every chosen-state change and every `setItems`, before and after the dispatch, so a handler that writes and then restores the previous value drops the pending change too; the choose-all row commits the value it announced, not a recomputation after the handlers; that change reports `source: 'user'`, being the first change of the interaction, while the confirmation recipe's later setter reports `'api'`.
- The confirmation recipe is veto now, setter later; the later change reports `source: 'api'`. The hook is synchronous, as every surveyed veto hook is.

## Widget focus events (`onFocus` / `onBlur`)

Two base settings report DOM focus entering and leaving the whole widget. RULED by the events committee (`events-committee.md`) and the owner:

- Shape: `onFocus: (() => void) | null` and `onBlur: (() => void) | null`, the DOM's own words for focus arriving and leaving; `null` = no consumer listener. `onFocusIn` / `onFocusOut` were rejected because the DOM pair fires on every move inside the widget and these settings do not; `onFocusChange(boolean)` because one setting per event is the `onOpen` / `onClose` idiom. No `focus()` method: `triggerEl` is public and is already the label click's focus target.
- Enter and leave mean the whole widget: a `focusin` / `focusout` pair on `rootEl` for the instance's whole life, with `relatedTarget` inside `rootEl` meaning an inside move and `null` meaning outside, the test the focus-leaving close already used. The `focusout` listener is always attached, since it also closes an open popup; the `focusin` listener is attached only when `onFocus` is set. Before this change the closing listener lived only from `open()` to `close()`.
- Order when focus leaving closes the popup: `onClose`, then `onBlur` (owner ruling, after a 4:2 committee vote for this order). The blur observer then sees a settled widget, `isOpened()` false, so the AngularJS touched flag and validation run once; on a pointer or keyboard open, `onFocus` already precedes `onOpen`. The minority wanted cause before effect. One open path runs the other way: a programmatic `open()` on an unfocused widget whose filter is active fires `onOpen`, then `onFocus` when the filter input takes focus.
- No `onBlur` from `destroy()` or `setDisabled(true)`, because neither moves focus out of the widget while a listener can see it. `destroy()` detaches the focus listeners as its first step, before its own `close()` and `replaceChildren()` can move focus. `setDisabled(true)` writes `aria-disabled` and `tabindex`, never `blur()`; a focused element keeps focus under `tabindex="-1"`, and an open popup closes with focus returning to the trigger, inside `rootEl`.
- `close()` returns focus to the trigger before hiding the popup and before `onClose`: hiding the focused filter input first would let the browser drop focus to `<body>`, an artificial blur / focus pair. The return runs trigger focus handlers before the teardown, so `open()` refuses while it runs; an app that opens on trigger focus therefore does not reopen the popup it just closed.
- A chip's remove button default-prevents `mousedown`, like the popup does, so a click on the x never moves focus onto a button the click then destroys. Before this change a focused remove button was destroyed by the chip-strip rebuild and focus dropped to `<body>`, which engines report differently (`TODO.md`). The clear button follows the same rule (round one of the review). Both clicks then focus the trigger when no element inside the widget holds focus (round two): a native control takes focus on a click inside it, and an unfocused widget would otherwise never report `onFocus` nor, later, the `onBlur` a form's touched state needs.
- With `outsideClickBehavior: 'block'` an outside mousedown while open is default-prevented, so focus never moves and no `onBlur` fires; `'pass-through'` blurs. A click on a non-focusable area blurs with `relatedTarget: null`.
- AngularJS: `ll-on-focus` / `ll-on-blur` event expressions; the three ngModel directives, `<ui-llselect>` included, mark the control touched on the widget blur, before `ll-on-blur` and in the same digest, as ngModel does for a native control's blur. `angularjs/API.md` states this as the contract, with no behavior-change note: the committee's 5:1 was for the same commit with such a note, and the owner kept the same commit and dropped the note, since the package is pre-0.1.0 and the docs carry no history.
- Naming: "focus" in a public event name is DOM focus; the row the arrow keys move is "the active row"; the protected `focused*` family keeps its name (`naming-conventions.md` "Focus, active, activated ruling").

## Active item change (`onActiveItemChange`)

One base setting reports the active row, the row `aria-activedescendant` points to and the arrow keys move, whenever it lands on another item or on no item. RULED by the events committee (`events-committee.md`) and the owner:

- Shape: `onActiveItemChange: ((item: T | undefined) => void) | null`; `null` = no consumer listener. `undefined` means no item row is active: the popup is closed, nothing matches the filter, or the choose-all row or an action row is active.
- Q: Why `item | undefined`, not a discriminated union over the row kinds (`{ kind: 'item', item }` / `{ kind: 'choose-all' }` / `{ kind: 'action', row }`)?
  - A: Because the one use anyone named, a footer that describes the active item, needs the item and nothing else; a union makes every handler branch on `kind` before it reaches the item, and exports a type and a `kind` vocabulary for a consumer nobody has; and a second parameter can carry the row's identity later without breaking a one-argument handler (Opus 5's framing: A now, extended through a second parameter if a real consumer appears). The union side, Codex Astra and Codex Sol: non-item rows exist today, so representing them is not speculative, and `undefined` merges "nothing is active" with "a non-item row is active". Owner ruling for `item | undefined` after the 4:2 vote; the union's name would have been `onActiveRowChange`, since its payload is a row.
- Q: Why fire on open and on close too, not only on keyboard moves?
  - A: Because a consumer that mirrors the row must fill on open and clear on close, and the committee dropped no firing point: open with the initial placement, close with `undefined`, every navigation and typeahead key, a filter keystroke or data re-render that moves the row, and a click, which moves the row before it requests the change.
- Q: Why compare items with `compareFn`, not by index or by element?
  - A: Because an in-place rebuild keeps the item while the element changes (a toggle repaints one row, `rerender()` rebuilds all, a reload replaces objects that compare equal), and an index keeps its number while the item under it changes (a filter keystroke). Only the item is the thing the consumer shows.
- Q: Why one dispatch at the tail of `syncFocusedIndexToDom` plus one in `close()`, not one per navigation method?
  - A: Because every active-row move ends in that sync: `setFocusedIndex`, `focusChooseAllRow`, `focusActionRow`, and the render clamp in `renderPopupList`, which assigns `focusedIndex` directly; its former four exits were folded into one write (`resolveActiveRowEl`) so the report has one tail. `close()` resets the row by assignment and reports on its own. The filter keystroke sets the landing index before its render instead of after it, so the one sync inside the render reports once and no transient `undefined` leaks while the list rebuilds (Codex Astra, Codex Sol). The report is stored before the listener runs, so a listener that closes or re-renders the widget re-enters against the right baseline.
- Order: the report is the last step of `open()` and of `close()`, after `onOpen` and after `onClose`; the committee left the open-side order free.
- Q: Why last, not first, when a hook that already sees the row would be handy?
  - A: Because a listener may close or reopen the widget (Codex Astra); as the last step, that nested transition runs after the outer one completed, so no step of the outer transition runs on a stale popup. A hook of `onOpened` / `onOpen` that closes the popup ends `open()` there, before the focus move into the filter input. The three row clicks (item row, choose-all row, action row) take a stamp before their active-row move, the transition generation (`open`, `close`, `rerender`, `destroy`) plus the change revision (`setItems`, every chosen-state change), and activate nothing when a listener moved either: the row they meant belongs to a popup state that is gone. The other user paths re-check the one thing they need, because the stamp stopped them wrongly (review round four): the filter keystroke reports its query change unless a close reset the query, since a rebuild or a value change under it keeps the query in effect; the clear button clears unless an `onFocus` listener disabled or destroyed the control, since one that opens the popup or loads items does not change what a clear means; the chip remove button removes unless such a listener disabled or destroyed the control, removed the item, or reloaded it as a disabled object, which it reads from the chosen entry as it stands after the listener, since a reload swaps the stored object for a compare-equal one; a toggle of a removed item would add it back. An emptied query that a close reset reports nothing, since the popup is closed; a close followed by a reopen under that same keystroke leaves the query empty either way, and the keystroke reports `''`, a true value, rather than tracking an open-cycle revision for it (Codex Sol's round-five ask; a third counter for a report that is true as it stands).
  - Codex Sol's round-three position, in its words: "`onClosed` or `onClose` can reopen and coalesce required `item -> undefined -> item` reports. Add transition/render generations, abort obsolete continuations, and queue reports in transition order." The generation and the aborts are the stamp above. The queue is not built: a close followed by a reopen inside `onClosed` or `onClose` that lands on the same item reports nothing, because the item did not change and a consumer mirroring the row is right at every point it can observe; the three reports would tell such a consumer nothing it can act on.
- No cause parameter (6:0): nobody asked, and a second argument is non-breaking for an ordinary handler.
- Name: `onActiveItemChange` (4 votes) over `onActiveRowChange` (the payload is an item, not a row) and `onActiveOptionChange` (ARIA role words stay out of JS names, "ARIA roles vs JS names" above). "Active" is the word A11Y.md already uses for this row; "focus" stays DOM focus.
- AngularJS: `ll-on-active-item-change` with `$item`, the raw item from the `ll-options` collection. The ui-select bridge maps ui-select's `on-highlight` onto the event for item rows, with the `repeat` locals and `$select` (5:1, owner ruling); the five asked the docs to name two differences, "no hover" and "no non-item row"; Opus 5 held that the same attribute with a narrower contract misleads, since ui-select's takes a row scope. The hover premise was wrong: ui-select 0.19.8 never moves its highlighted row on hover, its `mouseenter` gone since 0.13.0 (`REFS/ui-select-0.19.8/CHANGELOG.md`, found by Opus 5 in review round six), so `angularjs/API.md` names the three real differences: once per change rather than once per digest; nothing for a non-item row; and the item click, which moves llselect's active row and so runs the expression before the pick, where ui-select's click selects without running it for the clicked row (review rounds seven to ten, Opus 5 and Codex Sol). The owner asked `angularjs/API.md` to spell out ui-select's two uses of "highlight" (its `| highlight:` filter marks matched text, its `on-highlight` attribute reports the row change) and why the bridge keeps the attribute name: the bridge's contract is ui-select's markup as written, so a migrating template changes nothing; the word stays ui-select's, mapped once, and llselect's own API says "active". Not a unification of vocabulary: outside the bridge the name never appears.

## Open and close reasons (`meta.reason` on `onOpen` / `onClose`)

`onOpen` and `onClose` take one argument, `meta`, whose `reason` names the path that opened or closed the popup. RULED by the events committee (`events-committee.md`) and the owner:

- Shape: `onClose: ((meta: LLSelectCloseMeta) => void) | null` with `LLSelectCloseReason = 'choose' | 'escape' | 'outside' | 'blur' | 'toggle' | 'api' | 'disabled' | 'destroy' | 'hidden'`, and `onOpen: ((meta: LLSelectOpenMeta) => void) | null` with `LLSelectOpenReason = 'toggle' | 'keyboard' | 'typeahead' | 'api'`. The value meanings live as bullets on each alias, the shape the change reason set. A handler stored as `() => void` still fits; only code that calls the exported callback type itself sees the new parameter.
- Reason only, no `source` (5:1; owner ruling after asking whether `source` can join `meta` later): each close path names its own mechanism, a focus or layout close has no truthful initiator, and no consumer asked. `meta` is an object so that `source` can be added later without breaking a handler. Opus 5's minority held that "Change reason" above rules reason as the operation and source as the initiator, so `onClose` should carry both for consistency with `onChange`. One value does not imply its initiator: `'toggle'` covers the trigger click and a `toggle()` call alike, as five members wanted; Opus 4.8 wanted `'pointer'` for the click and `'api'` for the call.
- Values, one per close path: `'choose'` is the single-mode pick (four members; Sonnet 4.6 wanted `'pick'`, Codex Astra `'itemActivate'`), vetoed or not, since the veto stopped the value and not the close (6:0 on that); `'escape'` covers Escape and Alt+ArrowUp on the trigger and the filter input, and Escape on a slot control, said in the docstring (Codex Sol wanted its own value for Alt+ArrowUp); `'outside'`; `'blur'` for focus leaving, over `'focusout'` on a 3:3 tie, because one word names one concept once `onBlur` ships; `'toggle'`; `'api'` for `close()`; `'disabled'` for `setDisabled(true)`; `'destroy'`; `'hidden'` for the positioner's hide. The first close that takes effect reports its reason; a later `close()` while it runs is a no-op (Codex Astra, Codex Sol).
- The open reason ships with the close reason (owner ruling, against the committee's 4:2 deferral: the owner wants the two events to read alike). Four values, one per open path: `'toggle'` for the trigger click and `toggle()`, `'keyboard'` for ArrowDown, ArrowUp, Enter and Space on the closed trigger, `'typeahead'` for a printable character on the closed trigger, `'api'` for `open()`. The values are the implementer's proposal, ratified by the owner; the committee did not vote on them.
- `'keyboard'` stays as the open-keys value (owner ruling, after a panel round: Opus 5, Opus 4.8 and Codex Sol, fresh read-only sessions at highest effort, one brief). The owner asked why the open side names a device when the close side rejected device names twice, asked for rename options, and asked whether `'user' | 'api'` would have been enough. The positions, in the members' own terms:
  - The value set. Keep the four values and rename only the open-keys value: Opus 4.8, Codex Sol (2); Codex Sol: once `reason` exists, path detail is the coherent model. Three values, `'toggle' | 'typeahead' | 'api'`, the open keys folded into `'toggle'` because a click, an open key and a `toggle()` call are one mechanism, the trigger activated: Opus 5 (1), naming its own cost, that ArrowDown never closes, so `'toggle'` would name the activation rather than the key's effect, with change-nothing as the fallback because the rename has no good word; Codex Sol rejects the fold as misleading, since the keys never close an open popup. `'user' | 'api'`: no member; those words are `LLSelectChangeSource`, "Change reason" rules that reason names the operation and source the initiator, and one `toggle()` call would report `'api'` on open and `'toggle'` on close. Channel names, `'pointer' | 'keyboard' | 'typeahead' | 'api'`: no member; Opus 4.8 held that position in the committee and drops it against the 5:1 precedent and the owner's ruling.
  - The word, if the value stays. `'expand'`: Opus 4.8, Codex Sol (2), from `aria-expanded`: the four keys only ever expand the closed combobox and never collapse it, unlike the two-way `'toggle'`, and `getActionFromKey` maps all four to `LLSelectKeyboardAction.Open`, the shared operation the word names; Opus 4.8 adds that if the owner finds `'expand'` forced, the honest fallback is `'keyboard'`. Against `'expand'`: Opus 5, because it invents a synonym for "open", the word the API itself uses in `open()`, `opened` and `onOpen`; Opus 5 would fold the path into `'toggle'`, and if a value must stay, `'key'`, the least bad but still the device. Rejected by all three: `'activate'`, false for the arrow keys and taken by the action rows' `onActivate`; `'navigate'`, false for Enter and Space; `'keypress'`, still the device and a deprecated DOM event name; `'key'`, still the device.
  - Need. No consumer code branches on anything finer than user-vs-api: Opus 5, Opus 4.8; Opus 5 adds that the shipped set cannot answer even that, since `'toggle'` merges the click with a `toggle()` call, and that the shape for it is a `source` field, which `meta` was kept an object for. Codex Sol finds narrow but realistic uses: analytics that separate toggling, explicit expansion and search-first intent; presentation that suppresses the opening motion or changes help text for a search-first open; coalescing expensive active-item work, since a typeahead open moves the active option twice; no selection or data-change logic needs it. The owner's guess that `'typeahead'` lets a consumer with async items prefetch the typed range fails, all three: `meta` carries no character, and the search runs synchronously over the items present at open time; Opus 5 adds that `handleTypeaheadKeydown` steps aside when the impending open would have the filter active, the usual shape of an async-items widget, so `'typeahead'` never fires there.
  - Ruling: none of the alternatives was better than the shipped word, so the four values and `'keyboard'` stand. The brief's own case for keeping it: on the open side every path leaves the widget in the same state, so there is no mechanism to name and the input channel is the only truthful difference.
- Mechanism: a private pending field per direction, default `'api'`, that an internal path sets right before calling the public method (`openWithReason` / `closeWithReason`); the method reads and resets it first thing, so a call from outside reports `'api'` and a refused call leaves nothing behind. The single select's pick closes through the `@internal` protected `closeWithReason('choose')`. The trigger click goes through the public `toggle()`, which sets `'toggle'` for both directions.
- Deferred (6:0): a cancelable `onBeforeClose`. The focus-leaving close can never be vetoable, since A11Y.md rules that focus leaving the root closes the popup and that the popup is not a focus trap, and the veto committee's "a vetoed pick still closes" ruling rests on that invariant. A veto on the pick would recreate "keep open after a pick"; if that need arrives, it is a boolean setting such as `closeOnChoose` on the single select, which the ui-select bridge could then map from `close-on-select` (Opus 4.8).
- AngularJS: `ll-on-open` and `ll-on-close` expose `$reason`.

## Popup header / footer slots

Two pinned slots around the option list: `popupHeaderEl` between the filter input and the listbox, `popupFooterEl` after the no-results message. Filled by `createPopupHeaderContentElFn` / `createPopupFooterContentElFn` under the Container-Content law (the library owns the `div`, its class and its place; the app owns the content). RULED after the survey and committee rounds in `archive/popup-slots-research.md`:

- **Outer, never inner.** A listbox may own only options and groups (WAI-ARIA 1.2), and pinned content must not scroll away with the items. Rows inside the list are a separate feature (action rows).
- **Built only when content exists.** No resting node otherwise - the benchmark's node count is a headline metric - and gated on the METHOD result, so a subclass that overrides only `createPopupHeaderContentEl` still gets a container.
- **Content is built ONCE, in the base constructor, and never rebuilt.** The content fns receive `LLSelectConstructionContext` (`classIdMap`, `uiTranslationPack`), the only settings functions to get a context, because the closure recipe can never serve them (`popup-rows-and-callbacks.md` section 4.9). `LLSelectMultiple.setChosenItems` calls `rerender()`, so a per-render rebuild would destroy a footer button from inside its own click handler and drop focus to `<body>`; the clear button's focus-preserving swap cannot help because the library cannot preserve focus across an app-built subtree. Live state ("3 chosen") is the app's job from `onChange` / `onOpen`. The call happens before any subclass field initializer runs ("Construction-time overridable methods").
- **Order [filter input, header, list, no-results, footer].** The input is the combobox host, so forward Tab runs host -> header -> footer -> out, and the assistive-technology reading order is button -> combobox -> header -> listbox. A header above the input is one line in a subclass constructor (`if (this.popupHeaderEl) { this.popupEl.prepend(this.popupHeaderEl) }`; the library never rewrites the child list), and such a header holds no focusable controls, or Shift+Tab from the input lands in it instead of leaving the widget.
- **Pointer.** The popup `mousedown` default-prevention covers the slots: a slot button is clicked without moving DOM focus off the combobox host, so keyboard input keeps working. A text field in a slot calls `stopPropagation` on its own `mousedown` to take focus.
- **Recipe rules (README).** Slot buttons carry `type="button"` and an accessible name, use `aria-disabled` rather than native `disabled` (a focused button that becomes natively disabled loses focus), and stay compact (a long unwrapped line widens a `'fit-content'` popup; a tall slot squeezes the list, the only child that flexes). Slot text is never announced while focus stays on the combobox, so a hint screen-reader users need is not a slot's job.
- **Rejected.** A documented `popupEl.append` recipe alone (invisible in the type surface, no theme class, and the Esc / focus-return gaps stay); always-built containers (two resting nodes per instance for nothing); per-open or per-render content rebuilds (the self-rebuild defect above); a wrapper hook in the Ant Design `popupRender` style (hands out the positioner's measured element and lets a setting restructure the ARIA tree).

## Action rows (commands inside the list)

`popupListLeadingActionRows` / `popupListTrailingActionRows` (both variants, default `[]`) render app commands as `role="option"` rows inside the listbox, in the arrow-key ring, above or below the items. The descriptor is `LLSelectPopupListActionRow { textFn; createContentElFn?; disabledFn?; onActivate }`; the library builds the element (id, role, classes, `aria-label`, `aria-disabled`, click, Enter) through `createPopupListLeadingActionRowEl` / `createPopupListTrailingActionRowEl` (Container-Content law: `createPopupListActionRowContentEl` fills content, `isPopupListActionRowDisabled` reads the state, `onPopupListActionRowActivated` is the reaction hook). RULED after the committee rounds in `archive/popup-slots-research.md`:

- **Why rows and slots both exist.** A pinned header / footer never scrolls but is outside the combobox focus model; a row scrolls with the items but is keyboard-native - DOM focus stays on the host and `aria-activedescendant` moves onto it. Rule for the README: a row for a command a keyboard user must reach with the arrow keys; a slot for pinned content nobody runs.
- **Why `role="option"`.** A listbox may own only options and groups (WAI-ARIA 1.2). The cost is the announced semantics ("Restore defaults, 2 of 14", no selected state) - the same tolerated stretch the choose-all row carries, recorded in A11Y.md as a second, distinct deviation.
- **Two builders, one per position.** The reader thinks in places (header, footer, leading rows, trailing rows - four places, four builders), and no builder in this codebase is multiplexed by a kind parameter (`createTriggerClearButtonEl` and `createTagRemoveButtonEl` are two names). The round-3 majority's only argument for one builder with a `position` parameter was the duplicated override, a brevity argument that loses to "explicit beats brief" (CLAUDE.md). The two builders share one private body; the per-row methods are shared because they are per-row, not per-slot.
- **`index` stays.** The builders take `(row, index)` like `createPopupListItemEl(item, index)` / `createGroupEl(key, index, ...)`: the builder owns the whole element including its id, and the position is the id source; a subclass forwards it to `super`.
- **Descriptor shape.** An array of plain objects per slot (flat one-row-per-slot settings could not hold "Restore defaults" plus "Clear all"; a generic row type would add a class type parameter for a few closures). Function-valued fields carry the `Fn` marker (`textFn`, `disabledFn`, `createContentElFn`); the activation callback is present-tense like `onOpen` / `onChange` (`onActivate`); `createContentElFn` needs no container word because the descriptor type names the container. The arrays are copied at construction (frozen settings). `text` is a function so copy can follow state and language.
- **Rebuilt freely.** Rows are rebuilt on every list render and after every chosen change (right after `onChange`, so a row's text may show what the handler wrote), through `replacePopupListActionRowElsInDom` - a no-op without rows, so instances without rows keep their O(1) paths. Rebuilding is safe here, unlike the pinned slots: DOM focus never sits on a row.
- **One ring.** Navigation is one walk over [choose-all row, leading action rows, items, trailing action rows] (`ringLength` / `ringPosition` / `ringEntryAt`), replacing the choose-all row's special-cased branches; the protected `focusedIndex` / `setFocusedIndex` / `focusChooseAllRow` keep their item-based meaning. One visible change against the old special case: Page keys now clamp onto the choose-all row directly instead of stopping on the first item first.
- **Never the initial active option, never the vanish-clamp target, never a typeahead match** (owner rulings): a double Enter right after opening must not run a command, the clamp after `hideChosenRows` empties the list must not land on "Clear all", and a command is not a match.
- **Choose-all stays its own setting** (round 4, 6:0; re-confirmed unanimously by the unframed two-stage review in rounds 13-14, long-form reasons in `popup-rows-and-callbacks.md` section 3): its tri-state, self-hiding, public and overridable visible-enabled subset, pack text and AngularJS checkbox mode do not fit the generic descriptor; folding it in would grow the descriptor for one consumer. Revisit if creatable rows ever force a `visibleFn` in.
- **Pinned blocks** (`popupListLeadingRowsPinned` / `popupListTrailingRowsPinned`, default `false`): per block, never per row (`popup-rows-and-callbacks.md` section 5). Mechanism: one `div role="presentation"` per pinned block (`popupListPinnedLeadingRowsEl` / `popupListPinnedTrailingRowsEl`), built once, in the listbox only while the block has rows; `position: sticky` and the edge offset are set inline so a boolean setting works in any theme; the themes own the opaque background, the `z-index` and the block's edge line (the top wrapper draws `border-bottom`, the bottom one `border-top`, both only while the wrapper's `data-edge-to-items` is `"true"`, set by the library on every render, so two blocks that touch draw no line; the sibling divider rules keep serving unpinned blocks). `ensureVisibleInScroll` takes the wrappers' measured heights as insets, never a theme-declared number, and ignores them when they cover the whole scrollport. The choose-all row pins with the leading block; a subclass reaches the wrapper through the public field, there is no builder to override (pure structure, like `popupEl` and `popupListEl`).
- **Deferred.** Creatable rows (`visibleFn(query)`, exact-match test, Enter precedence), per-slot row classes (the themes draw the boundaries through sibling combinators), any ctx param (the callback-context review in `TODO.md`).

## Popup width policy

Two policies, chosen by the `popupWidthPolicy` setting; `'fit-content'` is the default.

- `'fit-content'` (default): the popup grows to its content's natural width, never narrower than the trigger (`max(trigger, natural)`), shifted and clamped against the viewport (details under Rationale, point 5).
- `'match-trigger'` (opt-in): the positioner sets `popupEl.style.width` to the trigger's measured width on every reposition (`positioning.ts`). Long items wrap (themes default to `white-space: normal`).
- The natural width is the popup's computed `width` under `width: max-content`, a fractional border box, rounded up; `offsetWidth` rounds to the nearest pixel and left a 249.375px list half a pixel short, wrapping CJK text (owner report). The committee record and the measurements: `popup-width-committee.md`.

Under either policy, long chosen text in the trigger is ellipsized (`overflow: hidden; text-overflow: ellipsis` on `.llselect-trigger-content`), and the library never touches the trigger's own width.

The default was `'match-trigger'` originally; it flipped to `'fit-content'` for native parity - per the table below, a content-sized popup is what the native control does (Chromium / macOS), while `'match-trigger'` is select2's convention, not the native control's. The two render identically whenever the widest item fits inside the trigger (`max(trigger, natural) = trigger`), so the flip only shows in the case where labels overflow the trigger - exactly where `'match-trigger'` wraps them. Cost accepted with the flip: `'fit-content'` re-measures the popup's max-content width on every reposition, one extra forced layout per scroll tick while open; caching it per content change is an open item in `TODO.md`.

### Empirical baselines

Tested 2026 against the native control and select2 on Firefox + Chromium. Captured here so future width / overflow discussions have a shared reference.

| implementation | trigger width | popup width vs trigger | long items in popup | long chosen in trigger |
|---|---|---|---|---|
| native `<select>`, no CSS width | grows to fit widest item | Chromium: = trigger, can overflow viewport (popup escapes). Firefox: popup content gets trimmed (render anomaly observed). | n/a (trigger is already wide) | n/a |
| native `<select>`, CSS width set | fixed by CSS, overflow clipped (no ellipsis) | Chromium: independent of trigger, can overflow viewport. Firefox: popup content gets trimmed. | n/a / depends on browser | clipped |
| select2, no CSS width | grows to fit widest item | matches trigger (with an internal JS cap around ~1021px; appears built-in) | wrap; trigger gets ellipsis if wider than the cap | n/a / ellipsis past cap |
| select2, CSS width set | fixed by CSS, overflow ellipsized | matches trigger | wrap (potentially many lines) | ellipsis |
| **llselect** | fixed by CSS only - library never auto-fits to widest item | default `fit-content`: content's natural width, never narrower than trigger, viewport-clamped; opt-in `match-trigger`: = trigger width (positioner inline `width`) | full width shown (default); wrap under `match-trigger` | ellipsis (default theme) |

### Rationale

1. **Predictable trigger.** Trigger width is whatever the user's CSS says it is; the library never measures items to auto-resize the trigger. The popup does size to content by default - that is the point of `fit-content` - but it is a fixed-position overlay, so its width never reflows the page.
2. **No viewport-overflow surprise.** The native content-sized popup can escape the viewport (Chromium); `fit-content` instead shifts left when the right edge would overflow (so `popup.x` can become smaller than `trigger.x`) and clamps width to `viewport - 2 * VIEWPORT_PADDING`. Opt-in `match-trigger` never sticks out past the trigger's footprint at all.
3. **Long-text full-fidelity by default.** Under the default the full item text simply shows (the popup grows); under `match-trigger` items wrap rather than truncate. Either way no information is hidden behind a hover tooltip.
4. **Users opt in to other policies via their own CSS** - e.g. set `.llselect-popup-list-row { white-space: nowrap; overflow: hidden; text-overflow: ellipsis }` (pair it with `match-trigger`: a content-fitted popup never overflows its labels, so ellipsis would stay dead). The library deliberately does NOT auto-set a `title` attribute on items so it never fights third-party tooltip libraries (Tippy / Floating UI / etc.). Users who pick ellipsis-on-items pick their own tooltip mechanism (subclass adding `el.title`, or a custom tooltip lib, or none at all).
5. **The edge-aligned look stays one setting away**: `popupWidthPolicy: 'fit-content' | 'match-trigger'` (default `'fit-content'`). `'match-trigger'` pins the popup to the trigger's measured width - the select2-style aligned-edges convention. The setting NEVER touches the trigger's width - that stays entirely CSS-driven.

The trigger ellipsizes its chosen-text by default in every shipped theme (`.llselect-trigger-content { white-space: nowrap; overflow: hidden; text-overflow: ellipsis; }`). This is non-negotiable in the default themes because a wrapping trigger looks broken; user themes can override if they genuinely want a multi-line trigger.

## Color scheme (light / dark) in the themes

Status: approved by the owner (committee round and decisions in `color-scheme-committee.md`) and implemented: the five themes carry the variables, the dark blocks and the built-in marks; `src/color-scheme.ts` holds the resolver; the setting, `getColorScheme()`, `refreshColorScheme()` and the AngularJS attribute `ll-color-scheme` exist; demo section 16 and the README recipe document it. Verified in headless Chromium; the headed-browser, Firefox and Safari passes are listed in TODO.md.

Vocabulary (naming-conventions.md 7a.11): a "theme" is one of the five stylesheets under `src/themes/`. A "color scheme" is either light or dark. A "mark" is a class name or an HTML attribute from the list under "Built-in marks", placed on the widget root or on an ancestor of the widget root. A built-in CSS rule turns each mark into the CSS variable `--llselect-color-scheme` with the value `light`, `dark` or `auto`; a host page may also set this variable directly. "The widget root" is the element the library mounts on, class `.llselect-root`. "The resolver" is the shared JavaScript that decides the widget's color scheme.

### What a host page can do (the integration contract)

- Nothing. When the `colorScheme` setting is omitted, no built-in mark applies, and neither `--llselect-color-scheme` nor `color-scheme` is declared on the widget root or on any of its ancestors, the widget uses its light colors regardless of the OS preference. This matches a native `<select>` on such a page.
- The standard way: declare `color-scheme: light dark` or `color-scheme: dark` on `<html>` or on an ancestor element that contains the widget, as a page should already do for its native controls. The resolver reads the computed `color-scheme` of the widget root and applies the rule under "How the resolver decides".
- The one-line way, for any other mechanism: set `--llselect-color-scheme` to `dark`, `light` or `auto` on any ancestor of the widget root. In CSS: `.night { --llselect-color-scheme: dark; }`. In JavaScript: `ancestorEl.style.setProperty('--llselect-color-scheme', 'dark')`. `auto` means "follow the OS preference here". When several ancestors set it, the nearest one wins, by CSS inheritance.
- A built-in mark: the marks listed below set `--llselect-color-scheme` through rules shipped in every theme file, so they need no extra rule.
- Full control over the colors: declare the color variables listed under "The color variables" on the widget root, in a rule placed after the theme stylesheet, for example `.night .llselect-root { --llselect-bg: #222; }`; the cascade conditions are under "Public API". A rule on an ancestor alone (`.night { --llselect-bg: #222; }`) does not work: the theme's own declaration on `.llselect-root` beats an inherited value.
- Per instance: the setting `colorScheme`. `'light'` or `'dark'` forces that scheme for the instance. The default `'auto'` resolves the scheme from `--llselect-color-scheme`, the widget root's computed `color-scheme` and the OS preference, in the order under "How the resolver decides". Note the two different `auto` values: for the `colorScheme` setting, `'auto'` means "apply the resolver's variable and property rules"; for `--llselect-color-scheme`, `auto` means "dark when the OS prefers dark, otherwise light".

### Built-in marks and their origins

- Dark marks: `.dark` (Tailwind CSS class-mode dark variant, per its documentation; VitePress's default theme uses it, per its CSS), `.theme-dark` (Bulma 1, per its CSS), `.dark-mode` (the Nuxt color-mode module's default class, per its documentation; not verified against a CSS file), `[data-theme="dark"]` (daisyUI, Pico CSS 2 and Bulma 1, per their CSS; daisyUI allows arbitrary theme names, only the literal `dark` is recognized), `[data-bs-theme="dark"]` (Bootstrap 5.3 color modes, official; Halfmoon 2 reuses it), `[data-color-scheme="dark"]` (this project's page contract, `demo/color-scheme.js`; also the attribute a host may put on any element).
- Light marks: `.theme-light`, `.light-mode`, `[data-theme="light"]`, `[data-bs-theme="light"]`, `[data-color-scheme="light"]`.
- The OS mark: `[data-color-scheme="auto"]` sets `--llselect-color-scheme: auto`.
- Each built-in CSS rule sets `--llselect-color-scheme` on the element that carries the matching mark. Dark example: `.dark, .theme-dark, .dark-mode, [data-theme="dark"], [data-bs-theme="dark"], [data-color-scheme="dark"] { --llselect-color-scheme: dark; }`.
- Marks on different ancestors resolve by inheritance: the nearest ancestor wins. Marks on one element resolve by rule order: the last matching rule supplies the value. Every theme file writes the mark rules in this order: dark class rules, light class rules, `[data-theme]` dark then light, `[data-bs-theme]` dark then light, `[data-color-scheme]` dark, light, then auto. Among built-in marks on the same element, an attribute rule overrides a class rule, and a `[data-color-scheme]` rule overrides every other built-in mark rule.

### How the resolver decides (shared JavaScript)

- Inputs, four: the instance setting `colorScheme`; the CSS variable `--llselect-color-scheme`, read as `getComputedStyle(rootEl).getPropertyValue('--llselect-color-scheme').trim()`; the computed CSS property `color-scheme` of the widget root; the OS preference, `matchMedia('(prefers-color-scheme: dark)').matches`.
- Order: (1) if the setting is `'light'` or `'dark'`, use it. (2) Otherwise, if the variable is `light` or `dark`, use it; if it is `auto`, use dark when the OS prefers dark, else light. (3) Otherwise (the variable is empty or holds any other text), read the computed `color-scheme` as a list of whole keywords. Choose dark when the list contains `dark` and either omits `light` or the OS prefers dark. Choose light in every other case, including `normal` and an empty value (Firefox 78-95 has no `color-scheme` property).
- Output: the resolver sets the attribute `data-llselect-color-scheme` on the widget root to `light` or `dark`. The theme keys its dark colors on this attribute. Hosts must not write `data-llselect-color-scheme`; a host uses one of the inputs under "What a host page can do".
- The resolver knows no framework. It reads the four inputs above and nothing else. Everything framework-specific (Bootstrap's `--bs-*` variables, Tailwind's palette variables, the mark names) lives in the theme files.
- When the resolver runs: once after construction (the batched first decision above); on `open()`; when the OS preference changes (one shared `matchMedia` change listener per document); when an attribute of `<html>` or `<body>` changes, or the child list of `<html>` changes, for example when a `<body>` appears or is replaced (one shared, batched `MutationObserver` per document, watching the attributes of `<html>` and of the current `<body>` plus the child list of `<html>`; no subtree; a batch in which every record is the library's own output attribute, written on a widget mounted on `<html>` or `<body>`, starts no pass, so such a widget does not trigger itself); on `refreshColorScheme()`. The shared listener and observer hold no instance: subscribers live in a `WeakMap` keyed by the root element, and a pass finds roots through the document. A CLOSED instance therefore stays reachable only through its mount element and `labelEl`, as it already does through its own DOM listeners; once those elements leave the document and the application drops its references, it is collectable, with or without `destroy()`. An OPEN instance holds document listeners until `close()` or `destroy()`. This is the guarantee the `destroy()` docstring gives.
- Cost: when `colorScheme` is `'auto'`, the first decision is not made inside the constructor. The constructor queues it; one microtask runs every queued decision, so all widgets built in one task share one style flush, and the attribute still lands before the page paints again. `getColorScheme()` and `open()` make a pending decision at once. Measured on a 1000-widget construction loop in Chromium: construction inside the constructor cost 2.5 times the forced-setting baseline (one style flush per widget); the batched decision costs about 1 percent. A cache keyed by the parent element was tried and rejected: a widget built after a page change under the same parent read the stale sibling value.
- Cost of one automatic pass: one `querySelectorAll` over the document, then one resolver run per subscribed widget that query finds. The shared observer and the OS-preference listener queue the pass in a microtask (their triggers are under "When the resolver runs" above); triggers that arrive before it runs share it. A resolver run reads the computed style once, queries the OS preference once through `matchMedia`, and writes the output attribute only when the result changed. A widget in a shadow root or in a detached tree is not found, so it costs nothing and is not re-decided. The runs go one widget at a time: during a scheme switch with N widgets, each of the first N-1 attribute writes leaves that widget's style dirty, so the next run's style read makes the browser recompute it first, and the last widget's restyle waits for the next rendering update. Any design pays the restyle and the repaint of every widget; this order adds the overhead of N-1 separate recomputations.
- That overhead, measured by an emulation on the table's page with widgets whose setting is forced, so that no library pass runs: per switch, a script loops over the widget roots, calls `getComputedStyle` on each root twice to read `--llselect-color-scheme` and `color-scheme`, and sets the output attribute on that root; the batched variant does every read before any write. After the loop, it reads the computed `color` of the first root. It calls no `matchMedia`, waits for no timer between its ten switches, and its time spans the script only, not the painting that follows. Medians of five runs of ten switches: 2.40, 21.21 and 59.24 ms per switch for 100, 1000 and 3000 widgets in the pass's order, against 1.82, 15.70 and 51.41 ms in the batched order. These absolute times are not the pass's cost: the script reads each root's computed style twice where the resolver reads it once, and its time includes the forced recomputation at the end. Only the difference between the two orders carries over to the pass.
- The table's measurement: headless Chromium 151.0.7922.34 (Playwright build) on an Intel Core i9-13900HX devcontainer with 4 vCPUs. Page: the vanilla theme, `color-scheme: light dark` on `<html>`, and N widgets in one container, each an `LLSelectSingle` with three items and the default `colorScheme: 'auto'`. Workloads: the unrelated change sets `data-x` on `<html>`, alternating `1` and `2`, 60 times; the scheme switch sets `data-color-scheme` on `<html>`, alternating `dark` and `light`, 20 times; each change waits for one `setTimeout(0)` before the next. Each figure is the median of five runs; a run's figure is the loop's elapsed time divided by its number of changes, so it includes each `setTimeout(0)` wait. The timer alone costs 3.81 ms per change, so the column "the pass alone" is the column "unrelated attribute change" minus 3.81 ms. The column "scheme switch, timer included" holds the same 3.81 ms per change.

| widgets | unrelated attribute change | the pass alone | scheme switch, timer included |

### The color variables

- Every color in every theme is one of these 32 variables, declared on `.llselect-root` with the theme's light value (the audit of the five themes produced this list; each theme declares all 32, a few as aliases of another variable where its own look needs no distinct value): `--llselect-fg` (text inside the popup: header and footer slot content), `--llselect-control-fg` (text of the trigger and of the filter input), `--llselect-fg-soft` (the arrow and the group labels), `--llselect-fg-muted` (the placeholder, the no-results text, the clear button at rest), `--llselect-bg` (surface of the trigger, the popup, the filter input, the pinned rows), `--llselect-bg-muted` (surface of the group labels), `--llselect-trigger-line` (border of the trigger), `--llselect-trigger-hover-line` (border of the hovered trigger), `--llselect-popup-line` (border of the popup), `--llselect-filter-line` (border of the filter input), `--llselect-divider` (dividers before and after action rows and the choose-all row; Shadow variables hold the color component only; offsets, blur and spread stay in the `box-shadow` declaration.
- Outside the variable declarations, every CSS declaration that supplies a color obtains it from a variable. Literal colors appear only in the variable declarations and in the palette comment required below.

### Rules for every theme file

- The dark block: `.llselect-root[data-llselect-color-scheme="dark"] { ... }` redefines every color variable above with the theme's dark value. Variables it does not list keep their light value or their alias. It does not touch `--llselect-color-scheme`. The dark values were chosen against the contrast floor under "Verification before shipping"; bootstrap-5's dark values are Bootstrap 5.3's own dark-mode variables with those values as fallbacks, so under `data-bs-theme="dark"` its trigger and filter-input borders are Bootstrap's `--bs-border-color` (#495057) and its popup border is Bootstrap's `--bs-border-color-translucent`, about 1.9:1 and 1.6:1 on Bootstrap's dark body background (#212529), as Bootstrap ships them. Its focused trigger border in the dark block is Bootstrap's own `#86b7fe`, which Bootstrap keeps in dark mode and exposes through no CSS variable; the light block derives that border from `--bs-primary-rgb`, so a page with a custom primary color sees the change in the light scheme only, while Bootstrap's own `.form-control:focus` uses the literal in both schemes. Its dividers read `--bs-body-color-rgb` in both blocks, so a page whose Bootstrap variables stay light while the widget resolves dark still gets visible dividers; its shadow reads that variable in the light block and is plain black in the dark block.
- Browser-painted parts (the popup scrollbar, the filter input's caret) follow the resolved scheme through two descendant rules. For dark: `.llselect-root[data-llselect-color-scheme="dark"] .llselect-trigger, .llselect-root[data-llselect-color-scheme="dark"] .llselect-popup { color-scheme: dark; }`. For light: the same rule with both attribute values and the `color-scheme` value replaced by `light`.
- Never declare the CSS property `color-scheme` in a rule whose selector targets `.llselect-root` itself: the resolver reads the computed `color-scheme` there and would read its own output.
- Theme rules must not declare `--llselect-color-scheme` with a selector that explicitly selects the `.llselect-root` class: it would hide the value an ancestor set. A built-in mark rule may still set the variable on a widget root that carries a mark, and a host may set it on the widget root through its own rule or inline style.
- Theme files must not contain any `@media` condition that uses `prefers-color-scheme`, whatever value it queries: pure CSS cannot tell a light-only page from an OS-following page.
- `bootstrap-5.css` keeps Bootstrap's variable references in both schemes: light fallbacks in the `.llselect-root` declarations (`--llselect-bg: var(--bs-body-bg, #fff)`), dark fallbacks in the dark block (`--llselect-bg: var(--bs-body-bg, #212529)`). With `colorScheme: 'auto'` and no higher-priority input, `data-bs-theme="dark"` on the widget root or on an ancestor selects the dark scheme; Bootstrap's variables supply the colors where Bootstrap defines them, and the fallbacks apply elsewhere.

- `scripts/check.mjs` rejects, in every theme file: a rule that declares `color-scheme` on the widget root; a rule that declares `--llselect-color-scheme` on the widget root; an `@media` rule whose condition contains `prefers-color-scheme`; a hex or color-function literal in any declaration other than the `--llselect-*` variables; a named or system color keyword in a declaration of a color-bearing property (the list in `scripts/check.mjs`: `color`, `background*`, `border*`, `outline*`, the shadows, `text-decoration*`, `text-emphasis*`, `caret-color`, `accent-color`, `fill`, `stroke`, `stop-color`, `flood-color`, `lighting-color`, `column-rule*`, `scrollbar-color`, `filter`, `backdrop-filter`, `mask*`, `list-style`, `list-style-image`, `content`, `text-fill-color`, `text-stroke*`, `tap-highlight-color`, each also with a `-webkit-` prefix) or of a custom property other than `--llselect-*`; `transparent` and `currentColor` are allowed; comments, strings and `url()` are masked first, escape-aware, so a `;` or `}` inside them splits neither a declaration nor a rule; a `#hex` or `%23hex` inside a `data:` URL of any declaration other than the `--llselect-*` variables is rejected too, since an embedded image color follows no scheme, while `url(#id)` and `url(file.svg)` point elsewhere and are not scanned. Check each selector of a selector list separately. "On the widget root" means a selector that explicitly selects the `.llselect-root` element itself, such as `.llselect-root` or `.llselect-root.foo`; a selector that only contains `.llselect-root` as an ancestor, such as `.llselect-root .llselect-popup`, is not rejected.

### Public API

- Setting `colorScheme?: LLSelectColorScheme` with `type LLSelectColorScheme = 'auto' | 'light' | 'dark'`, default `'auto'`. The docstring explains the resolver order and names its four inputs: the setting, the CSS variable `--llselect-color-scheme`, the computed CSS property `color-scheme`, the OS preference. Both AngularJS directives expose the setting as the attribute `ll-color-scheme`, an expression evaluated once at link time like the other enum-literal attributes, quoted: `ll-color-scheme="'dark'"`.
- `getColorScheme(): 'light' | 'dark'` returns the result of the most recent resolver run; while the batched first decision is still queued, it runs the resolver now. It never returns `'auto'`.
- `refreshColorScheme(): void` runs the resolver again. Call it on each affected instance after a change that reaches neither the library's OS-preference listener nor its attribute observer on `<html>` and `<body>`: a replaced stylesheet, or a mark toggled on a wrapper element below `<body>`.
- No function that refreshes every widget in a region. The follow-up committee round in `color-scheme-committee.md` chose docs only, 7 of 7, and the owner ratified it. A page that switches the scheme on an element below `<body>`, or hosts widgets in a shadow root, calls `refreshColorScheme()` on each affected instance; the README recipe says so. A batch export can come later without breaking anyone; that round records its constraints.
- No `setColorScheme`. With `colorScheme: 'auto'`, a host changes the scheme through a mark or through `--llselect-color-scheme`; a forced setting keeps precedence over both. A second write channel would cut against "Settings vs methods". No change event: the scheme is presentation, and the output attribute is observable.
- Precedence, restated: an explicit `colorScheme: 'light'` or `'dark'` wins. Otherwise each resolver run reads the widget root's computed `--llselect-color-scheme` value and applies the rules above. CSS has already resolved the declarations and the inheritance; the resolver does not search ancestors.
- A host rule that targets the widget root and declares a color variable overrides the theme's dark block when the host selector has higher specificity, or equal specificity and later source order (the host's stylesheet comes after the theme's in the document). Same cascade origin, importance and layer are assumed. That is intended.

### Known limits

- The resolver cannot infer the scheme from a page that only changes its own, unrelated CSS variables, or that only has media-query rules without a `color-scheme` declaration or a mark. Such a page sets `--llselect-color-scheme` to `light`, `dark` or `auto` on an ancestor of the widget.
- A widget built on an element that is not in the document reads no computed style and decides light; nothing re-decides it on insertion. The page calls `refreshColorScheme()` after inserting it, or it opens.
- The bootstrap-5 theme takes its colors from Bootstrap's own variables (decision 5). On a page that sets `data-bs-theme="dark"`, a widget resolved light (a forced `'light'`, or a nearer light mark) still shows Bootstrap's dark colors; only the values Bootstrap does not define follow the widget's scheme.
- The variable names, `--llselect-color-scheme` and `data-llselect-color-scheme` are fixed names; `cssClassPrefix` renames the classes only. A host that renames the prefix and writes its own theme keeps those names.
- A replaced `<html>` element (`document.open()`, `documentElement.replaceWith()`) is not observed again, so the automatic re-decision on `<html>` / `<body>` attribute changes does not resume for that document; the OS-preference listener and `open()` still work, and such a page calls `refreshColorScheme()` on its widgets after each later scheme change.
- Two instances on one element: the newer constructor claims the element, so the older instance's pending first decision and subscription are dropped. The supported order is `destroy()` first, then build. An older instance's `destroy()` after a rebuild empties the element under the newer widget; that call is the host's error and is not guarded.
- Firefox 78-95: the `color-scheme` property path resolves light. The variable path and the marks work.
- Shadow DOM: `--llselect-color-scheme` and `color-scheme` inherit across a shadow boundary; the theme stylesheet must be inside the shadow root. A built-in mark outside the shadow root counts only when the outer document also loads a theme stylesheet, since a mark rule must match the element that carries the mark (verified in headless Chromium). The shared pass finds widgets through the document only, so a widget inside a shadow root misses the two automatic re-decisions (OS change, `<html>` / `<body>` attribute change); it re-decides on `open()` and on `refreshColorScheme()`.
- A page that already uses a built-in mark name for something else, for example a dark hero section with class `dark`, gets that scheme for the widgets inside it. The host opts out with a rule that beats the theme's mark rule on that element: `--llselect-color-scheme: inherit` passes the parent's value through, so a computed `color-scheme` that lists dark can still select dark; `light` or `dark` fixes the scheme there; the setting `colorScheme` fixes one instance. Verified in headless Chromium; the README recipe documents the opt-out.
- Iframes: CSS values do not inherit from the containing page into an iframe document; set the mark on the widget root or on one of its ancestors inside the iframe document.
- Forced colors (Windows high contrast) and print: before changing the themes, record the widget's appearance in Windows high-contrast mode and in print preview; repeat both checks after the changes and compare.

### Verification before shipping

- Native comparison: put a native `<select>` and a widget in the same container; omit the widget's `colorScheme` setting; make sure neither the widget root nor any ancestor carries a built-in mark or a `--llselect-color-scheme` declaration; declare `color-scheme` on the container with each of `normal`, `light`, `dark`, `light dark`, under both OS preferences, on Chrome 87, Firefox 78, Safari 14.1 and each browser's current release. Both controls must show the same scheme. On Firefox 78-95 both controls show light, and constructing or refreshing the widget throws no exception.
- Each host mechanism listed in `color-scheme-committee.md`; a light region inside a dark region and the reverse; conflicting marks on one element; a shadow root; an iframe; scheme changes while the popup is open and while it is closed; `refreshColorScheme()` after a stylesheet swap; `destroy()` removes the instance from the shared listener and observer; the 1000-widget and 10k-item benchmark pages before and after.
- In a browser with a visible window, verify that the popup scrollbar and the filter caret use the resolved scheme, that the popup keeps the theme's colors, borders and shadow in the Popover top layer, and that every visual state listed in the committee record's verification section is checked. Contrast of all five dark palettes: text at least 4.5:1 against its surface; the borders that outline a control (the trigger, the filter input, the popup) and the focused control's border at least 3:1 against the surface they sit on. Dividers between rows or sections and the tag outline are decorative, sit near 1.4:1 in every dark palette, and are exempt. The translucent ring shadow that bootstrap-4, bootstrap-5 and tailwind draw around the focused border follows each framework's own halo, sits between 1.3:1 and 2:1, and is exempt as decoration beyond the border; bootstrap-3's denser halo passes on its own. bootstrap-5 under `data-bs-theme="dark"` uses Bootstrap's own border colors, as noted under "Rules for every theme file".
