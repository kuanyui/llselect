# CLAUDE.md

> This CLAUDE.md is forked from https://github.com/multica-ai/andrej-karpathy-skills/blob/main/CLAUDE.md , which is MIT License

Behavioral guidelines to reduce common LLM coding mistakes. Merge with project-specific instructions as needed.

**Tradeoff:** These guidelines bias toward caution over speed. For trivial tasks, use judgment.

## 1. Think Before Coding

**Don't assume. Don't hide confusion. Surface tradeoffs.**

Before implementing:
- State your assumptions explicitly. If uncertain, ask.
- If multiple interpretations exist, present them - don't pick silently.
- If a simpler approach exists, say so. Push back when warranted.
- If something is unclear, stop. Name what's confusing. Ask.

## 2. Simplicity First

**Minimum code that solves the problem. Nothing speculative.**

- No features beyond what was asked.
- No abstractions for single-use code.
- No "flexibility" or "configurability" that wasn't requested.
- No error handling for impossible scenarios.
- If you write 200 lines and it could be 50, rewrite it.

Ask yourself: "Would a senior engineer say this is overcomplicated?" If yes, simplify.

## 3. Surgical Changes

**Touch only what you must. Clean up only your own mess.**

When editing existing code:
- Don't "improve" adjacent code, comments, or formatting.
- Don't refactor things that aren't broken.
- Match existing style, even if you'd do it differently.
- If you notice unrelated dead code, mention it - don't delete it.

When your changes create orphans:
- Remove imports/variables/functions that YOUR changes made unused.
- Don't remove pre-existing dead code unless asked.

The test: Every changed line should trace directly to the user's request.

## 4. Goal-Driven Execution

**Define success criteria. Loop until verified.**

Transform tasks into verifiable goals:
- "Add validation" → "Write tests for invalid inputs, then make them pass"
- "Fix the bug" → "Write a test that reproduces it, then make it pass"
- "Refactor X" → "Ensure tests pass before and after"

For multi-step tasks, state a brief plan:
```
1. [Step] → verify: [check]
2. [Step] → verify: [check]
3. [Step] → verify: [check]
```

Strong success criteria let you loop independently. Weak criteria ("make it work") require constant clarification.

---

**These guidelines are working if:** fewer unnecessary changes in diffs, fewer rewrites due to overcomplication, and clarifying questions come before implementation rather than after mistakes.

## 5. Project-Specific Rules (llselect)

- All source code, identifiers, file names, comments, and documentation are English only.
- Use only the ASCII hyphen-minus character `-`. Do not use em dash, en dash, smart quotes, or other non-ASCII punctuation anywhere in code or docs.
- Exception to the two rules above, limited to user-visible or behavior-verifying DATA: i18n resource STRINGS (the translated values in the `src/i18n/` per-language pack files, and demo data that exists to demonstrate i18n / RTL), test fixtures that verify Unicode behavior (CJK search / IME filtering inputs, bidi labels), and intentional visual glyphs (e.g. a theme's `\00d7` close cross). Identifiers, comments, and surrounding explanations in those files stay English/ASCII. Typography inside translations: zh-TW puts a space between CJK and half-width characters (Pangu spacing); ja follows Japanese convention (no such spacing).
- Markdown: do NOT hard-wrap prose to a fixed column. Write each paragraph, list item, and blockquote as ONE physical line and let the renderer wrap it; wrapping is the reader's / renderer's job, not the author's. This repo lives on GitLab, whose Flavored Markdown (like GitHub issues / PRs / comments) turns every in-paragraph newline into a `<br>`, so column-wrapping renders as a wall of unwanted line breaks. Only fenced code blocks, table rows (one per row), and headings keep their own physical lines.
- No dates in docs: never stamp the date of writing into documentation, headings, or decision-log entries - `git log` / `git blame` own the when. A date that is itself content (e.g. "the abandoned 2024 draft") is fine.
- Never hardcode a runtime-generated `#anchor` (e.g. the demo pages' section slugs, derived from heading text) in a cross-page link - renumbering or rewording the heading silently breaks it and nothing checks it. Link the page and name the target section in plain text; `#anchors` are only for ids stable by construction (hand-written ids, or same-file anchors `npm run check` verifies).
- Comments should be terse. Skip anything obvious from the code; only note non-obvious intent, invariants, or workarounds.
- Docstrings and human-facing docs (TSDoc in src/, README, angularjs/API.md) are written for fast scanning - a reader with mild dyslexia must be able to follow them. Precise, short sentences; complete but never long-winded. Short never means telegraphic: when a fact is conditional, spell the connective out (if / when / while / otherwise) - write "If no query is active, every item is visible", never a fronted fragment like "No query active: every item is visible". Colon-fronted labels are for defining a term or introducing a list, not for carrying an if. Lead with ONE short sentence saying what the thing is, then put every further fact in its own bullet, one fact per bullet. Never glue several clauses into one sentence with dashes and nested parentheses. When one word bundles several conditions (e.g. which items count as "visible" for an operation), define it with a nested list: an intro bullet like "acts on items that satisfy all of the following:", then one condition per sub-bullet. For an overridable method (`protected`), the FIRST bullets say who calls it, where each parameter comes from, what each parameter means and - when a confusion is likely - what it is NOT, and the usual override shape (call `super`, edit the returned element); a reader must never have to guess whether they fill a parameter or the library does (the `createPopupListItemEl` `index` incident). Implementation and internals notes (what a method composes, complexity, subclass wiring) go LAST, at the tail of the docstring, after every reader-facing fact. TSDoc renders verbatim into the generated API reference, so docstrings are user-facing documentation held to this rule, not internal comments. Measurable limits for reader-facing explanations (README prose, Q&A / FAQ answers, demo hints), ruled after a rejected README section: the reason is the FIRST sentence; an answer is at most 3 bullets and 45 words in total; every sentence stays under 20 words; no parentheses in prose - an aside becomes its own sentence or is cut; a "why" answer carries no how-to, the recipe lives in the section that teaches the API; a question only a code reviewer would ask goes to DESIGN.md, not the README; at most two code names per line, since every backticked identifier is a decoding stop. Count before shipping. (Agent-facing docs under docs/llm/ keep their dense house style.)
- Event documentation (owner rulings): covered are the event callbacks of the settings interfaces (the `@group Events` members of `LLSelectBaseSettings`, `LLSelectSingleSettings` and `LLSelectMultipleSettings`), the protected `on*` hooks of the select classes, their overrides in the variants, the README section "Confirm before a change" (its prose; the README's tables and code examples are not covered), and in `angularjs/API.md` the `ng-change` entry and the `ll-on-*` entries; not covered are callbacks that are fields of other objects, such as `LLSelectPopupListActionRow.onActivate` and `PositionerOptions.onHide`, and the agent-facing docs under docs/llm/. The lead sentence names the side: it says **before** or **after**, never a bare "when" or "on", which leaves the reader guessing which side of the event the callback runs on. In the covered text the timing words **before** and **after** are bold where they say when the callback or hook itself runs, in absolute terms or relative to another callback or hook (`onClose` fires **before** `onBlur`), so a reader with dyslexia sees the timing at a glance; the timing of an effect the callback triggers (a re-render, a write), the order of steps inside a hook's own body ("after asking `onBeforeChange`") and a non-temporal "after" (type narrowing after an `if`) stay plain. Right after the lead paragraph (one sentence in a rule-conforming docstring; in `angularjs/API.md` the binding-mode line with its sentences), before the bullets if any, every covered docstring or entry carries one blockquote naming its before / after counterpart, the declaring docstring and every override with its own docstring alike, in one of three template shapes; the names, the links and the object of the timing clause follow the context (`angularjs/API.md` links its attributes and says "reached the model"), the shape stays, and the opening words stay exactly, since the site renderer (`scripts/build-site.mjs`) recognizes these lines by them and draws them as a note card: on the after-side ``> Pairs with `onBeforeChange`, which runs **before** a user change and can stop it.`` (for the core `onBeforeChange` / `onChange` pair the before-side fires for user changes only while the after-side fires for every change, and the after-side says so), on the before-side ``> Pairs with `onChange`, which runs **after** the change was written.``, and where no counterpart exists ``> No **before** counterpart: there is no `onBeforeOpen`.`` (the mirror "No **after** counterpart" serves a before-side without an after-side; none exists today). When the platform rules the counterpart out, the absence line says why in a trailing clause: ``, and the `focusin` / `focusout` events the library observes are not cancelable, so none could stop the move.`` on `onFocus` / `onBlur`. The absence line is deliberate: it keeps the naming pattern visible from every entry (`onBeforeX` pairs with `onX`; for hooks `onXChanging` with `onXChanged` and `onXing` with `onXed`) and records which hooks could still be added. Attribution: the owner ruled the callbacks, the README and the directive entries, then ratified the protected hooks (activation hooks included; the panel had split two to one on those three), the reason clause on the focus pair, and the blockquote on overrides.
- Settings documentation (owner rulings, after three six-model committee rounds): every function-valued setting that is not an event callback, the predicate form of a union-typed setting such as `filterable` (there, the first sub-bullet under the predicate form), and every setting that holds an object, an array or an element (`labelEl`, `uiTranslationPack`, the action-row arrays) carries, as its first bullet after the lead sentence, one line saying when the library calls it or how it holds the value, with the word that answers "how often" or "how held" in bold: ``Called **once**, inside the constructor, before `new` returns.``, ``Called on **every** full trigger render (`renderTrigger`: ...); nothing is kept for a later call.``, ``Copied **once** at construction, as a shallow copy: ...``, ``Kept **by reference**: ...``. When two frequencies meet ("once per visible row on **every** full list render"), the outer moment carries the bold. The line names the moments by the library's own public or protected methods at the point of use, never by a bare term and never by a private method, which the generated reference does not show: a full trigger render is `renderTrigger` (construction in the shipped classes, a selection change, `rerender()`, `setPlaceholder()` with a changed argument, `setUiTranslationPack()`, and a `setItems` that drops or reorders chosen items); a trigger content render is `renderTriggerContent` (every full trigger render, plus every `setItems`); open and close re-render, within the trigger, the arrow slot only; a full list render is `renderPopupList` (only while the popup is open: open, each filter input event outside an IME composition, once at the composition's end, the Esc that clears the query, `setItems`, `rerender()`, a bulk selection write of the multiple select, which is `setChosenItems` and the choose-all methods and runs `rerender()`, and `toggleItem` while `hideChosenRows` is on); an in-place row rebuild is what `setChosenItem` and `toggleItem` do to the affected rows while the popup is open. The two trigger moments are never merged, nor the two list moments: the clear button runs on the full trigger render only and the arrow on the full trigger render plus open and close; the group label functions (`groupKeyToStringFn`, `groupKeyToLangFn`, `createGroupLabelContentElFn`) run on the full list render only, `itemToGroupKeyFn` also in the gather and in disabled checks, `groupKeyCompareFn` also in the gather but never in disabled checks, and the disabled predicates never in the gather. A term such as "a bulk selection write" is spelled out with its methods where it is used. A line in a base settings interface whose moments differ by mode names the mode. When a line splits into a lead and sub-bullets, the bold stays on the sub-bullet that carries the moment. A line that holds for one mode only (single or multiple, `'count'` or `'tags'`) says so. "Nothing is kept for a later call" means the library does not memoize what your function returned, while an element it returned stays in the DOM until the next build replaces it; where the library reuses a derived structure (the group gather until `setItems`, `rerender()` or a bulk selection write; the multiple select's `hideChosenRows` subtraction; the filtered subset until the next recompute) the line names it and what invalidates it, and a default-value fast path that skips the function is named. A function called more than once per moment (the gather's two passes, the lookahead read) says so without false precision. A copy line states its depth (shallow) and that the entries' own functions still run live, and where. Each condition goes in its own sub-bullet when there is more than one. The line replaces an existing timing sentence, keeps every fact that sentence carried, and moves to the first position. Plain scalar settings carry no line: the README states that settings are frozen after construction. Event callbacks follow the event-documentation bullet above; callbacks that are fields of other objects, such as an action row's `onActivate`, carry no line.
- Plain language everywhere an explanation lives: docs, code comments, demo copy, and replies to the user. Never invent a term or lean on a vague metaphor when the concrete thing has a name - say "the option element the library builds", not "shell". A niche term is acceptable only if the same sentence defines it. When an existing doc uses an invented term, replace it with the concrete wording. The test for any term (user ruling): it must be either standard industry vocabulary a typical web developer knows without looking it up, or a term this project's own docs already define (README, DESIGN.md, naming-conventions.md). Everything else gets the concrete wording, in docs and in replies alike - "seam" (Feathers' legacy-code jargon for an overridable method) failed that test and was purged; say "overridable method" / "customization point". Replies to the user are held to the same fast-scanning standard as the docstring rule above (short sentences, one fact per bullet, a reader with mild dyslexia can follow them), and every reply must stand on its own: a reader with none of the earlier conversation must still follow it - name the thing, never "the issue above" or "as discussed". Context comes FIRST, before any tally, verdict or option label (user ruling, after a reply said "pin the whole block" without ever saying what the block was): define every noun the reply leans on in one plain sentence each - what the thing is, where it sits, what it does - and restate each option as a full sentence before its vote count; a label like "O3" or a shorthand like "the block" means nothing on its own. When in doubt, over-explain the context and cut the rest.
- Records of what someone else said or ruled are faithful (user ruling): a committee or panel member's position, the owner's ruling, or a spec's requirement is stated in that party's own terms, never a paraphrase that shifts the claim, never a clause cut from the condition it came with; a tally names who voted for what, and a member whose position does not fit the options cleanly is recorded in the member's own framing; a reader who checks the record against the source must find no surprise. A reply that reports such positions to the user follows the same rule.
- Replies to the user are dyslexia-friendly, ALWAYS (user ruling, after a decision list the user could not follow): short sentences; simple sentence shapes (subject, verb, object); precise nouns, never a bare "list" / "items" / "entries" / "signal" / "hook" / "token" for a thing that has a full name - write "the Linux user account list", "the dark-color-scheme mark on an ancestor element", "the CSS variable named --llselect-bg"; a layout whose structure is clear at a glance (numbered decisions, each with the same labelled parts in the same order); no word that could make the user ask what it means - if a term needs defining, define it in the sentence before it is used. A pronoun or a pointing phrase such as "it", "this one", "the former", "that line" or "the record" is replaced by the full noun it stands for, every time (user ruling). A decision the user must ratify is written as: one sentence naming the thing decided, each option as one complete sentence with its vote count, the recommendation in one sentence, and the exact answer the user can give ("A" / "B" / "as recommended"). Invented shorthand such as "D1" or "M3" never appears without the full sentence next to it.
- One word, one concept - STRICT. Never reuse a word that already names one thing in this project for a second, confusable thing. Reserved: "label" appears in a name only where HTML itself calls the concept label (`<label>` -> `labelEl`, `aria-label` -> `ariaLabel`, `<optgroup label>` -> the groupLabel element family) - the canonical string machinery is `*String` / `toString` (JS's idiom; it also drives search and accessible names), while UI-facing copy and "what this item shows" are `*Text`. External vocabulary (ng-options' `label` clause, ui-select's `tagging-label`) may be quoted in backticks as the other project's term, mapped once to ours. Full ruling: `docs/llm/naming-conventions.md` s7a.7-8.
- Demo example titles say what the example SHOWS, in plain words. Never a bare mechanism tag like "(settings)" or "(subclass)" - if the mechanism matters, name the actual API in the title or the first hint sentence.
- Demo hint copy stays short. Every sentence must help a reader understand the example faster; cut anything that only records agent reasoning. When editing an example, the hint should usually get SHORTER, not longer.
- Demo section order (user ruling: an earlier reorder had moved the i18n section to the end, and the color-scheme section was then added after it): on each examples page the i18n section is the last example section, so the color-scheme section and every new section go before it. On the AngularJS examples page the "Full source" section, which shows the directive and app sources, always stays the very last section, after the i18n section. Renumbering a section updates every reference to its number anywhere in the repo; `git grep` the old numbers in every form, such as "16.2", "section 16" and "(16)". The references include the `data-demo` / `data-demo-css` ids with the matching `#region` markers in `demo/main.js` and `demo/style.css`, text on either examples page, comments in `demo/`, README, `docs/llm/` and `src/` docstrings. Two kinds stay as written: `docs/llm/archive/`, which is history, and verbatim quotes of old commit subjects.
- When a demo mimics a native control behavior, reproduce the native presentation - no invented decoration beyond the ask. If the platform reference is uncertain, say so instead of asserting. Styling library-built elements from a demo goes through the public API (`triggerEl`, angularjs `instance()`).
- Interactive controls (buttons, toggles) keep a stable position across state changes: never relocate the control itself on open/close; only the content it reveals may move or reflow.
- demo/style.css has NO global `box-sizing: border-box` reset. To fill a container in demo CSS, use flex or block auto width - never `width: 100%` plus padding (content-box math overflows and grows a horizontal scrollbar).
- Default UI content is rendered by the library as real text / DOM, never via CSS generated content (`::before` + attribute gating). CSS glyphs are only for styling-layer decoration on EMPTY elements the theme owns the look of (the `\00d7` close crosses).
- Browser support floor (fixed baseline, update deliberately - never let it drift with the calendar): Firefox 78+, Chrome/Edge 87+, Safari 14.1+. This is the floor where the JavaScript runs (`replaceChildren`, ES2020 output per tsconfig `target`) and the base CSS applies (flex `gap`, the `padding-block` / `padding-inline` / `inset` shorthands). A CSS feature above the floor may be used when the browsers between the floor and that feature's first version still get a recognizable, working widget (user ruling): a purely cosmetic difference is acceptable there and is not patched - people who want more handle it in their own CSS; a difference that hides state the user needs (which row has keyboard focus, whether the trigger is focused) is not acceptable and gets a fallback declaration the old browser understands, written on the line before the newer one. Current uses above the floor and their status: `:has()` on the tag-wrapping rule (cosmetic: tags stay on one line), `:focus-visible` listed next to `:focus` (cosmetic: the themed focus style gives way to the browser's default outline in Firefox 78-84 and Safari 14.1-15.3), unprefixed `user-select` (cosmetic: Safari allows text selection on the trigger); `visualViewport` and scroll anchoring degrade gracefully. Do not add polyfills, vendor prefixes, or workarounds beyond such fallback declarations; raising the floor for a new API is fine if it is called out in the commit.
- TypeScript: write explicit, precise types. Do not use `any` unless genuinely unavoidable; when you must, add a short comment explaining why.
- Start identifier/key-like API types as a defaulted generic param, never a hard-coded concrete type - widening later cascades through internals and is a breaking change, so it never happens. When such a type opens to objects, pair it with an equality fn and keep it off the DOM (index-based ids, no `String(key)`). Worked example: the `GroupKey` bullets in DESIGN.md "Data model".
- Always wrap the body of `if` / `else` / `while` / `for` / `do` in `{ }`, even when the body is a single statement, and even when written on the same line. Example: `if (x) { return }` not `if (x) return`. This avoids the "next line gets accidentally added but isn't actually in the body" class of bugs.
- Document authority: CLAUDE.md governs agent behavior and enforceable code-style constraints. `docs/llm/DESIGN.md` owns API / architecture decisions (naming conventions, module boundaries, settings vs methods, ARIA mapping, etc.). `docs/llm/A11Y.md` owns the keyboard / focus / ARIA behavior contract. When these disagree, the owning document wins; fix the others to match it.
- Doc placement: `docs/llm/` holds agent-facing material (contracts, specs, findings logs, decision archives); `docs/` itself is for human-facing documentation only. New agent-facing docs go under `docs/llm/`, never the docs/ root. Human API reference is GENERATED (TypeDoc -> `public/api/`, from the TSDoc in src/) - do not hand-write a parallel core API doc; the AngularJS directive reference is hand-written in `angularjs/API.md` (narrative stays in `angularjs/README.md`). `docs/llm/OPTIMIZE.md` is the performance log for the library itself (benchmark measurements, regressions, optimization work); the benchmark page's own spec and findings stay in `docs/llm/SPEC_BENCHMARK.md` and `docs/llm/FIXME_BENCHMARK.md`.
- Rules live in this repo, never in the assistant's memory (`~/.claude/**/memory/`): memory does not travel across machines or collaborators, so a rule stored only there is invisible to everyone else. Write to memory only when the user explicitly asks. When the user states a durable rule or convention, write it into the governing doc (this file, or the owning `docs/llm/` doc) FIRST, then do the work it governs.
- When asking the user to decide a name (method / function / setting / type), ALWAYS give its full TypeScript signature (param + return types) and one line on what it actually does. Never ask for a naming decision on insufficient information - the user should not have to go look it up.
- Any callback / setting whose type includes `null` must have its docstring state exactly what `null` means; it differs per case (e.g. "fall back to the default text" vs "render nothing") and is never self-evident.
- When explicit naming / structure conflicts with brevity or "fewer abstractions" (including s2 Simplicity First), prefer explicit. The cost of guessing while reading the API outweighs a few extra methods or longer names.
- Do not ask permission for work that is already agreed, has no decision in it, and is going to happen either way - just do it, and report what was done. s1's "if something is unclear, ask" is about things that are actually UNCLEAR: a question earns its place only when the answer changes what gets built - a name, a boundary, a semantic, a tradeoff only the user can weigh. "Shall I also do the obvious remaining item?" / "which of these two agreed things first?" / "shall I continue?" are not that; they cost a round trip and hand back a decision that was never the user's to make. When in doubt, prefer doing it and saying so over asking - a wrong-but-reported action is cheap to correct, an unnecessary question is pure latency. Splitting work into separate commits is the way to keep it reviewable, not asking first.
- Hold a position by the strength of the argument, not by the user's tone. Change it when genuinely refuted - that change is honest, not soft; hold while the arguments stand, even against displeasure. Serious or casual phrasing must not enter the decision. State verifiable facts plainly, but never give absolute guarantees about what cannot be guaranteed (e.g. security claims).
- Never flip a shipped library default in the same turn it is questioned. Deliver a tradeoff discussion first: short plain sentences (no dense tables), separate "the architecture is wrong" from "the implementation has a bug", give a recommendation, and wait for the pick. Demo-level iteration stays act-then-report.
- "Update the data" means the data ONLY (benchmark numbers, versions, tables). Never reword the user's own prose alongside - not even for vocabulary consistency. After such an edit, diff and confirm every hunk is data; if a wording change genuinely seems needed, propose it in one sentence and let the user decide.
- REVIEW / TODO / FIXME finding ids must be descriptive (the `[SEVERITY-N]` format below), never cryptic invented codes like `R20` / `F7` / `REVIEW 1.2`. Refer to a finding by what it is ("the off-screen-open listener leak") - in docs, in commit messages, and when reporting to the user - with the id at most a trailing reference; a bare code forces the reader to look it up. This is ONLY about those tracking ids; it is not a general ban on abbreviations, so it needs no list of allowed words.
- Commit messages: ONE line, in the house shape `type: [scope] terse summary`. The summary names WHAT changed, nothing more - mechanism, rationale, and sub-part inventories belong in the diff, docs, and FIXME/TODO entries. Length: aim ~72 chars for the whole subject, normally stay under 100; when the content genuinely needs it (e.g. two long API names in a rename) up to 140 is acceptable, never more. At most one `;`-joined second clause, and only when the commit genuinely does two things (e.g. add + rename). Needing more room means the message is explaining instead of naming, or the commit should be split. For the register read the EARLY history (`git log --reverse | head -40`), not recent commits - matching the latest entries is exactly how subjects once drifted past 400 chars. No paragraph bodies. Trailers (e.g. Co-Authored-By) stay, after a blank line.

### Review panel and decision escalation (llselect)

- Review panel: a fixed set of four models, each run at its highest available effort (`max`) - Fable 5, Opus 5, Opus 4.8, Codex Sol. Codex 5.5 left this list and the committee list (owner ruling): the installed `codex` CLI refuses it on this account ("not supported when using Codex with a ChatGPT account"). This is the panel the `docs/llm/FIXME.md` rounds refer to, and the one any "ask the panel" / "convene the reviewers" instruction means.
- Committee (user ruling): when the user says "convene the committee" / "ask the committee" (they may say it in Chinese), it means: open a FRESH, EMPTY session of EACH of these models and have them review or discuss the proposal at hand - Opus 4.8, Opus 5, Sonnet 4.6, Sonnet 5, plus Codex Sol and Codex Astra whenever the `codex` CLI is installed. Each member runs at its highest available effort (`max`), read-only, and gets the WHOLE brief in its prompt: an empty session knows nothing of this conversation, so the brief must stand on its own (the question, the contracts that constrain it, the candidate options with tradeoffs, and the repo paths to verify). Invocation from this devcontainer, brief piped on stdin, members may all run AT ONCE under a memory watchdog (the RAM rule in the next bullet): `claude -p --model claude-opus-4-8 --effort max --allowedTools Read,Grep,Glob` (same for `claude-opus-5` / `claude-sonnet-4-6` / `claude-sonnet-5`; `--allowedTools` is variadic and swallows a positional prompt placed after it, hence stdin), `codex exec -m gpt-5.6-sol -c model_reasoning_effort=max -s read-only`, `codex exec -m gpt-6-astra -c model_reasoning_effort=max -s read-only`. A member whose model id the installed CLI cannot resolve is skipped and the skip is reported to the user. While a committee or a review round runs, the tree stays frozen: no commit, and no edit to any file the members may read; the brief cites symbols, never line numbers (user ruling, after a brief's `src/base.ts` line numbers drifted by about thirty lines when a commit landed mid-run). The committee is the DISCUSSION body for design questions and proposals; the review panel above stays the FIX-REVIEW body for the `docs/llm/FIXME.md` rounds - the lists overlap on purpose and the escalation bullets below apply to both.
- When you hit a genuine fork - a design choice, a claim you cannot settle alone, anything where guessing wrong is costly - do NOT settle it solo: first convene the OTHER THREE panel members (every panel model except the one you are running as) to review and discuss it together, by whatever channel reaches them. From this devcontainer the three are invoked directly and read-only (a model the installed CLI or the account cannot run is skipped and the skip reported): `codex exec -m gpt-5.6-sol -c model_reasoning_effort=max -s read-only`, and `claude -p --model claude-opus-5 --effort max` / `--model claude-opus-4-8` (allow only `Read,Grep,Glob`); redirect stdin from `/dev/null` or the CLIs wait on it. Fall back to subagents or the user's relay only when a CLI is unavailable. Run the reviewer CLIs all at once under a memory watchdog (a sampler every five seconds that kills the most recently started member when available memory drops under 300 MB and records the skip), and never alongside `npm run verify` or a build. Measured on this devcontainer (2.9 GB total and about 1.6 GB available at idle from `free -m`, per-process peaks from `ps -eo rss,args`, both sampled every ten seconds): each `claude -p` or `codex exec` session peaks near 330 MB (a per-process transient peak, rarely reached by all at once), the lowest available figure sampled with three running was about 1.06 GB (a simultaneous floor; the two numbers are different measurements and do not subtract), a `npm run verify` adds a node process near 320 MB, and the interactive session itself holds about 450 MB. Two sessions died mid-turn when four reviewer CLIs ran concurrently next to a verify on an earlier 1.9 GB container (the pattern of an OOM kill; the container exposes no dmesg / cgroup counters to confirm it). Re-measure before raising the count. The memory goes to the CLI process itself, not to what it reviews: a later run of all six committee members at once (four Claude sessions at 250 to 270 MB each, two Codex sessions at about 290 MB plus a 48 MB node wrapper) kept at least 505 MB available over ten minutes, on which the owner lifted the count; the watchdog stays as the guard. The earlier deaths came from four CLIs next to a `verify` on a 1.9 GB container. A runner script that starts members in the background must `wait` on their pids, never a bare `wait`, when a sampler loop runs beside them.
- Every fix goes to the OTHER THREE panel members for a POST-FIX review before it counts as done - even a low-risk one executed directly (the MEDIUM-79 round proved the post-fix review catches self-introduced defects, e.g. a DESIGN-forbidden CSS rule). A genuine fork is reviewed BEFORE execution too (bullet above); a low-risk fix that only executes a panel-given direction is done directly, then reviewed. Batch related low-risk fixes into one review when practical.
- Stop rule for post-fix loops (user ruling, after a loop spent about twenty rounds on the review log's own wording): when every finding of a post-fix round is a wording issue inside `docs/llm/FIXME.md` itself - how an entry, its title, fix line or Q&A, or a Process record of the rounds is phrased, or how precisely it records the review - do not fix and re-review on your own. Stop the loop, report those findings to the owner, and ask whether to end the loop with them unfixed, fix them without another round, or keep going. A finding that anything outside the log is wrong, or that the log misstates a fact about the code, the docs or the commit history, is fixed and re-reviewed as the bullet above says.
- Then hand the user the call to make, in short plain unambiguous language: state the question, the options, your recommendation, and the exact decision they must ratify. Keep it scannable - no dense tables, no long-winded framing.

### Verification commands (llselect)

Run before claiming a change is done; all must pass:

```sh
npm run verify      # one shot: check + build + test + angularjs (npm ci + test) + build:site; exactly what CI runs
npm test            # tsc test compile + node:test under jsdom
npm run build       # d.ts + rollup bundles + themes
npm run check       # mechanical style checks (ASCII punctuation, doc links)
npm pack --dry-run  # when package.json / exports / files changed
```

The repo holds a SECOND package, `angularjs/` (`@llselect/angularjs`), with its own tests and its own dependencies. The root `npm test` does not touch it, so a green root run says nothing about it. When changing anything under `angularjs/` (or anything in `src/` its directives lean on), also run:

```sh
cd angularjs && npm install && npm test   # jsdom + real angular; needs a root `npm run build` first
cd angularjs && npm run build             # terser only, no bundler; also checked by prepublishOnly
```

`angularjs/*.min.js` and `angularjs/node_modules/` are build outputs / installs and are gitignored: change the source, rebuild. The `angularjs/` directives are plain ES5-style IIFEs on purpose (a legacy AngularJS app drops them into `vendor/` behind a `<script src>`), so the ES2020 / TypeScript rules above do not apply inside that directory - but the ASCII, brace and comment rules do.

jsdom cannot test layout, native Tab focus navigation, scrollbar dragging, visual-viewport behavior, or assistive-technology output. Changes touching positioning, focus order, RTL, themes, or ARIA need a real-browser pass - record what to verify in `docs/llm/TODO.md` ("manual verification") if it cannot happen in the same session. A real-browser pass IS possible in this no-sudo devcontainer: `docs/llm/rootless-browser-testing.md` has the rootless Playwright recipe.

The user previews the demo / site through `make server`, which serves the `public/` build output. `public/` regenerates only when `build:site` runs - after changing `demo/`, site generation, or READMEs, run `npm run build:site` before reporting anything as viewable (no server restart needed; mention a browser hard refresh when cached CSS / JS is involved). `make server` runs `npm run build` and then `build:site` before serving, so a fresh start after a branch switch serves the checked-out code; `make build` is the library build alone.

### Generated and abandoned files (llselect)

- `dist/` and `.build/` are build outputs. Never edit them manually; change `src/` (or the build config) and rebuild.
- `src/draft.ts` is an abandoned early reference, excluded from builds and tests. Do not repair, extend, or "clean it up".
- A public API change is not done until everything it touches moves together: exports (`src/index.ts`), declarations, README examples, tests, and the owning contract doc (`docs/llm/DESIGN.md` / `docs/llm/A11Y.md`).

### Review-findings log (`docs/llm/FIXME.md`)

Findings from reviews (external, `/code-review`, audits) are tracked in `docs/llm/FIXME.md`, newest round on top under a `## review (<topic>)` heading. No date in the heading, or anywhere in the file - `git log` carries the when (see the no-dates-in-docs rule). Each finding is one entry:

`- [ ] **[SEVERITY-N] - title**` - `[ ]` open, `[x]` resolved. SEVERITY is a full word, never abbreviated: HIGH / MEDIUM / PERFORMANCE / QUALITY / DOCUMENTATION / NEEDS-VERIFICATION / LINT. N is a number unique across all rounds (e.g. `[QUALITY-7]`).

Nested body:

- Plain facts use a label, one per line: `Symptom:` / `Cause:` / `Impact:` / `Fix:` / `Verified:` (Verified only on resolved entries).
- A non-obvious judgement becomes a two-level Q&A: `- Q: Why <judgement>, not
  <the tempting alternative>?` then `  - A: Because <why the alternative fails
  / why this holds>.` Add one only when the answer is non-trivial; keep each A terse.
- Cross-round correction is the PRIMARY use of the Q&A: when a later round finds a prior call wrong, delete the wrong CONCLUSION but keep the LESSON as a Q&A for why it was wrong. These accumulate across rounds - keep them. The Q asks about the judgement itself, never which round made it.
- `file:line` refs: keep line numbers while the entry is open (`[ ]` - you still navigate there); on resolving (`[x]`), drop the line number and keep only the file / symbol (lines drift after the fix; git blame / grep finds the exact spot).
