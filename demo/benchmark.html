llselect vs the field

Two browser benchmarks against the native <select> (the baseline floor), Choices.js, Select2, Tom Select and Slim Select: building many selects at once (mass instantiation), and interacting with one (interaction latency). Everything runs in your browser. Lower is better; numbers depend on your machine.

Mass instantiation

A stress test: build many independent selects at once and measure it, with the widgets actually rendered in the scroll area below.

Heavy. Each library gets a time budget (about 20 s); a competitor that cannot finish in it stops early and its row shows how many it built before the cut-off. "Run all" walks the five libraries in turn, so it can take a while.

What the columns mean
  • Built / target - how many widgets finished before the time budget. A competitor that cannot mass-instantiate at this scale shows e.g. 240 / 10000 (timeout) - itself a result.
  • Build total (ms) - total synchronous time to build all the widgets (the deliberate yields that keep the page responsive are excluded). One run, not a median: at this scale the signal dwarfs the noise.
  • DOM nodes (resting) - element nodes left under the scratch area after building, popups closed. llselect builds no option DOM until a popup opens, so this shows its lazy-render footprint.
  • Filter candidates (ms) - open the first built widget, type a character that narrows the candidate list, re-render the matches; median of a few, timed to the next rendered frame (so a library that defers rendering to requestAnimationFrame is not read as 0). Every widget is searchable.

Interaction latency

The other axis: one dedicated widget per library, timing a real open / filter / select / close cycle, so opening a big list is measured in isolation - this is where llselect builds its option DOM (it renders nothing until you open). The widgets stay live below; click them yourself too. Native <select> is shown for reference but its dropdown is browser-driven, so it is not timed.

Stacked chart: the whole bar is the full cycle cost (shorter is better), each segment a phase; click a legend entry to show or hide it.

What the columns mean
  • Open - open the dropdown. For a big list this is where llselect builds its option DOM (it renders nothing until you open).
  • Filter - clear the search box, then type one character that narrows the list to about half. Clearing first makes every keystroke a real change (a library that keeps the query after a selection would otherwise re-render nothing on a repeated character).
  • Select - pick one option: single-select replaces its one value, multiple-select adds a chip and keeps the list open.
  • Close - close the dropdown.
  • Each op is timed to the next rendered frame, not just its synchronous return: some libraries (Choices.js) schedule their dropdown DOM work with requestAnimationFrame, so a purely synchronous timer would read ~0 for them. The floor is therefore about one frame. Median of a few cycles (first dropped as warm-up); native <select> is shown for reference but not timed.

Method and caveats

  • Widgets are built in small chunks with a yield between them, so the page stays responsive and a runaway library can be cut off at its time budget. A forced reflow ends each build so deferred layout is not hidden. Tick no timeout to build every widget regardless (it may take minutes or run out of memory).
  • The chart defaults to throughput (widgets built per second) because that stays a fair comparison even when a library timed out - it is a per-widget rate, not a total. Switch the metric to compare init time, DOM nodes, or filter latency instead; a bar from an incomplete run is shown in amber with its built count.
  • Every widget is independent - its own chosen state, no cross-widget interaction (that would be an integration test, not a render stress test).
  • Libraries render differently, which is the point of the DOM-nodes column: llselect lazy-renders options on open; Tom Select caps rendered options; Choices, Select2 and Slim Select render eagerly. None is cheating.
  • The custom-renderer variant adds one MDI icon per item through each library's item-render hook, and to the chosen display too (llselect tag / trigger, Select2 templateSelection, Tom Select render.item, Choices HTML label). One exception: Slim Select v2 renders a selected chip as textContent = option.text with no per-chip HTML hook, so its chips stay plain text - a real library limitation, not a missing adapter. This benches a plain searchable select otherwise; tagging, remote data and templating are out of scope.
  • A "-" or error means the adapter could not drive that library on the loaded CDN version - tell me which cell.
