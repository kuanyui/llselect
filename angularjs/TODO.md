# TODO - angularjs-llselect

Remaining work for the AngularJS 1.x package. Same conventions as the root `docs/TODO.md`: `[ ]` todo, `[~]` in progress, `[x]` done. No dates anywhere - `git log` carries the when.

Findings are named by what they are, never by a bare code.

## Open decisions (blocking, need the user)

- [ ] **Publish to npm at all?** The primary consumer downloads the file into `vendor/` and adds a `<script src>` - no npm anywhere. That makes publishing speculative, and it is the one decision that drags in the others (a name that cannot change, semver, a second release process). Recommendation: `"private": true` for now. The package.json still earns its place - it holds the test devDependencies so `npm test` can run - it just does not publish. Flipping to published later is `private: false` plus a name.
- [ ] **npm package name** - only if the above becomes yes. No convention to appeal to: the ecosystem is split (`ui-select` has no prefix at all; `angular-translate` / `angular-sanitize` / `angular-ui-router` use `angular-`; nothing surveyed uses `angularjs-`). `llselect-angularjs` sorts next to `llselect` on a registry search, which is the only real argument either way. Renaming after publish is breaking, so decide before, not after.
- [ ] **Workspaces or not.** Two packages in one repo means either `npm install` twice, or a `"workspaces": ["angularjs"]` field on the root `package.json`. The field is dev-time only (it does not reach consumers, and `files` still controls what ships), but it does change root `npm install` behavior. Currently: no workspaces, install separately.

## Bugs found in the demo

- [x] **Clear button gets a box that llselect never draws.** Cause: `demo/style.css` has `.demo-row button { border; background; padding; ... }` - a descendant selector, so it also hits llselect's own clear button inside `.llselect-trigger`. This page is the first to put a `clearable` select inside `.demo-row` (the clearables in `examples.html` are not), so it is a new exposure, not a pre-existing bug. Fixed: `.demo-row > button` in `demo/style.css`, which cannot reach into the widget. Verified: the rule is a direct-child selector now; `examples.html`'s action buttons are direct children so they are unaffected. NEEDS-VERIFICATION: eyeball both pages in a real browser - jsdom has no styling.
- [x] **`<ui-llselect>` flickers on first open, showing raw `{{p.name}}`.** Cause: `createItemContentElFn` returns a `$compile`d element whose bindings have not evaluated yet - AngularJS fills them on the next digest, and the open came from a native click, i.e. outside one. Confirmed under jsdom: immediately after open the rows read `["{{p.name}}","{{p.name}}","{{p.name}}"]` and only become `["Alice","Bob","Carol"]` after a digest. So llselect measures and positions the popup against uninterpolated template text, then it resizes. Fixed: `compileSlot()` digests the row scope before returning the element (guarded on `$rootScope.$$phase`, since `$digest` throws inside a digest and the ambient one already traverses the new child); all three slots (choices, tag, trigger) route through it and the `$applyAsync` is gone. Verified by mutation test: removing the sync digest turns exactly this assertion red with `["{{p.name}}","{{p.name}}"]`.
  - Q: Why did the first version of this regression test pass even with the fix removed?
    - A: Because an earlier check in the same file ran `$rootScope.$digest()`, so by the time it read the rows they were already filled. A test that asserts a state a previous test fixed up is false-green. It now forces a fresh render and reads with no digest in between. Mutation-test every regression test that guards a timing bug.
- [x] **Section 5's markup toggle showed the wrong thing, and the multiple pane had none.** Cause: the `data-src="5"` marker sat ON the `<ui-llselect>` element, and the extractor reads `innerHTML` - so the snippet started at the transcluded children and dropped the `<ui-llselect ng-model=... required>` opening tag, which is the whole point of that section. Every other section marks a wrapping element, which is why they were right. Fixed: wrap it like the others, and add a `5b` marker + toggle for the multiple pane. Verified: extraction now yields `<ui-llselect ng-model="vm.person" name="person" required="">` and 8/8 markers pair up.
- [x] **Source-code blocks have no background and the palette is unreadable.** Cause: `demo/style.css` scopes the code styling to `pre[data-demo]`, which is `examples.html`'s attribute; the AngularJS page uses `pre[data-src-for]` and a bare `<pre>`. So the Monokai `.hl-*` colors (`#e6db74` yellow strings, `#f92672` pink tags) land on white instead of `#282c34`. One cause, both halves of the report. Fixed: rescoped to `.code-toggle > pre` / `.code-toggle > pre code` in `demo/style.css`; both pages use that wrapper (34 blocks in `examples.html`, 10 here). NEEDS-VERIFICATION: re-check the HTML tag colors in a real browser now that the background is dark - the palette is Monokai and was being drawn on white, which likely explains the whole report.

## Missing API

- [ ] **Arrow icon attribute.** llselect has `createTriggerArrowContentElFn` plus the built-in `createChevronDownSvgEl` / `createTriangleDownSvgEl` / `createCheckSvgEl` / `createCheckboxSvgEl`; the directives expose none of it. Expose the built-ins only, by name (e.g. `ll-arrow="chevron"`), and say in the docs that a custom arrow means forking the file - that is the whole point of a copy-paste package.
- [ ] **Configuration phase (provider).** AngularJS apps expect app-wide defaults from `.config()`. Today every setting is per-element, so a 40-select app repeats `ll-arrow="chevron"` 40 times. A `llselectConfigProvider` with the defaults an app would actually set once (arrow, and whatever else survives review) would fix that. Open question to settle first: is the arrow really the only one? `searchable` and `placeholder` are plausible, but `placeholder` is app copy per field, not a default. Decide from the real API surface, not by guessing.

## Benchmark

- [x] **Raise the item count.** Now 3000 items / 20 widgets, both overridable via `?items=&widgets=` so a reader can find the knee. Measured under jsdom (absolute numbers are inflated for everyone there - it has no real layout - but the shape is real): at 500 items the incumbent's build was 13.7x llselect's; at 3000 it is 197.7x, and with `validation="required"` on both it is 225x. Corrected while writing it up: the incumbent is NOT superlinear - its build is linear (it renders every option up front) while llselect's is flat (the list is built only on open), and that flat-vs-linear split is what widens the ratio. ui-select is the genuinely superlinear one, and only per digest.
- [ ] **Real-browser pass.** jsdom has no layout, so only the digest column is meaningful there; build / open / filter need a real browser before being cited anywhere. Already tracked in the root `docs/TODO.md`.
