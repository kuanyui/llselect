## Open decisions (blocking, need the user)

- [x] **Publish to npm at all?** Decided: yes. The deciding argument was the CDN - publishing to npm is what makes `https://cdn.jsdelivr.net/npm/llselect-angularjs@0/llselect-angularjs.min.js` exist, and that is the link you hand someone who does not use npm either. The primary consumer downloads the file into `vendor/` and adds a `<script src>` - no npm anywhere. That makes publishing speculative, and it is the one decision that drags in the others (a name that cannot change, semver, a second release process). Recommendation: `"private": true` for now. The package.json still earns its place - it holds the test devDependencies so `npm test` can run - it just does not publish. Flipping to published later is `private: false` plus a name.
- [x] **npm package name**: `llselect-angularjs`, ONE package holding both files. Two packages were considered and rejected: a script-tag consumer picks a FILE, not a package, so the granularity is identical either way, while two packages cost two versions and two releases - and a gradual migration uses both files at once anyway. No naming convention to appeal to (`ui-select` has no prefix; `angular-translate` / `angular-sanitize` use `angular-`; nothing surveyed uses `angularjs-`); `llselect-angularjs` sorts next to `llselect` on a registry search, which was the only real argument. - only if the above becomes yes. No convention to appeal to: the ecosystem is split (`ui-select` has no prefix at all; `angular-translate` / `angular-sanitize` / `angular-ui-router` use `angular-`; nothing surveyed uses `angularjs-`). `llselect-angularjs` sorts next to `llselect` on a registry search, which is the only real argument either way. Renaming after publish is breaking, so decide before, not after.
- [ ] **Workspaces or not.** Two packages in one repo means either `npm install` twice, or a `"workspaces": ["angularjs"]` field on the root `package.json`. The field is dev-time only (it does not reach consumers, and `files` still controls what ships), but it does change root `npm install` behavior. Currently: no workspaces, install separately.

## Bugs found in the demo

- [x] **Clear button gets a box that llselect never draws.** Cause: `demo/style.css` has `.demo-row button { border; background; padding; ... }` - a descendant selector, so it also hits llselect's own clear button inside `.llselect-trigger`. This page is the first to put a `clearable` select inside `.demo-row` (the clearables in `examples.html` are not), so it is a new exposure, not a pre-existing bug. Fixed: `.demo-row > button` in `demo/style.css`, which cannot reach into the widget. Verified: the rule is a direct-child selector now; `examples.html`'s action buttons are direct children so they are unaffected. NEEDS-VERIFICATION: eyeball both pages in a real browser - jsdom has no styling.
- [x] **`<ui-llselect>` flickers on first open, showing raw `{{p.name}}`.** Cause: `createItemContentElFn` returns a `$compile`d element whose bindings have not evaluated yet - AngularJS fills them on the next digest, and the open came from a native click, i.e. outside one. Confirmed under jsdom: immediately after open the rows read `["{{p.name}}","{{p.name}}","{{p.name}}"]` and only become `["Alice","Bob","Carol"]` after a digest. So llselect measures and positions the popup against uninterpolated template text, then it resizes. Fixed: `compileSlot()` digests the row scope before returning the element (guarded on `$rootScope.$$phase`, since `$digest` throws inside a digest and the ambient one already traverses the new child); all three slots (choices, tag, trigger) route through it and the `$applyAsync` is gone. Verified by mutation test: removing the sync digest turns exactly this assertion red with `["{{p.name}}","{{p.name}}"]`.
  - Q: Why did the first version of this regression test pass even with the fix removed?
    - A: Because an earlier check in the same file ran `$rootScope.$digest()`, so by the time it read the rows they were already filled. A test that asserts a state a previous test fixed up is false-green. It now forces a fresh render and reads with no digest in between. Mutation-test every regression test that guards a timing bug.
- [x] **Section 5's markup toggle showed the wrong thing, and the multiple pane had none.** Cause: the `data-src="5"` marker sat ON the `<ui-llselect>` element, and the extractor reads `innerHTML` - so the snippet started at the transcluded children and dropped the `<ui-llselect ng-model=... required>` opening tag, which is the whole point of that section. Every other section marks a wrapping element, which is why they were right. Fixed: wrap it like the others, and add a `5b` marker + toggle for the multiple pane. Verified: extraction now yields `<ui-llselect ng-model="vm.person" name="person" required="">` and 8/8 markers pair up.
- [x] **Source-code blocks have no background and the palette is unreadable.** Cause: `demo/style.css` scopes the code styling to `pre[data-demo]`, which is `examples.html`'s attribute; the AngularJS page uses `pre[data-src-for]` and a bare `<pre>`. So the Monokai `.hl-*` colors (`#e6db74` yellow strings, `#f92672` pink tags) land on white instead of `#282c34`. One cause, both halves of the report. Fixed: rescoped to `.code-toggle > pre` / `.code-toggle > pre code` in `demo/style.css`; both pages use that wrapper (34 blocks in `examples.html`, 10 here). NEEDS-VERIFICATION: re-check the HTML tag colors in a real browser now that the background is dark - the palette is Monokai and was being drawn on white, which likely explains the whole report.

## Lessons

- Q: Why did the benchmark's off-screen stage pass every jsdom run and then fail instantly in a browser?
  - A: Because llselect refuses to open a trigger that is off-screen or clipped (`positioning.ts` `isAnchorHidden`), and jsdom is structurally blind to it: every rect is 0x0 at 0,0, and the check uses strict comparisons *precisely* so an unsized jsdom anchor reads as "in viewport, no rect yet". So `position: absolute; left: -9999px` - written to exclude paint - silently measured an open that never happened, and no jsdom test could ever have caught it. `angularjs/test/offscreen.test.mjs` now stubs the rect so the path is at least observable.
  - The deeper miss: `demo/benchmark.js` had already learned this the hard way (`6d7a29f`, "scroll a widget on-screen before measuring it - off-screen open() no-ops") and says so in a comment. A second benchmark was written in the same repo without reading what the first one paid for. Read the existing one's caveats before writing a new one.

- Q: Why does the benchmark harness fail on console output instead of just printing it?
  - A: Because filtering it is how a real defect stayed hidden. The runner piped its output through `grep -v "Could not translate"` for several runs, so 100 rejected promises per run - real work inside the timed section - read as a clean pass. What a page says is part of the test; silencing it is not tidying, it is deleting the evidence.
- Q: Why inline translations in the benchmark rather than the `useStaticFilesLoader` the demo uses?
  - A: The loader does an `$http` GET. A benchmark must not put network I/O in the middle of what it measures. The demo wants real messages, so it pays the fetch; the benchmark only needs the validator to resolve without extra work.

- Q: Why do the "invalid input" tests assert on `$exceptionHandler` instead of `assert.throws`?
  - A: Because a directive can never throw at the caller. `$compile`'s `invokeLinkFn` wraps every link fn in its own try/catch and hands the error to `$exceptionHandler` (`angular.js:11374`). The first version of these tests asserted a throw and failed; the second blamed `$apply`'s try/catch and bypassed it, and still failed. The observable contract is "reported, and nothing rendered" - which is also why the README no longer claims the directives "throw".
- Q: Why is `llselect` a `file:..` devDependency when the tests never import it?
  - A: They do not, but npm auto-installs peers, and `llselect` is not on the registry yet, so `npm install` 404s on its own peerDependency. `file:..` satisfies it locally and stays honest: the tests really do run against the sibling build. Revisit once llselect itself is published.
- Q: Why `prepack` for the build rather than `prepublishOnly` alone?
  - A: `prepublishOnly` does not run for `npm pack`, so the tarball would have shipped without the `.min.js` files - they are gitignored build outputs, so nothing else would have put them there.

## Missing API

- [x] **Arrow icon attribute.** llselect has `createTriggerArrowContentElFn` plus the built-in `createChevronDownSvgEl` / `createTriangleDownSvgEl` / `createCheckmarkSvgEl` / `createOutlinedCheckboxSvgEl`; the directives expose none of it. Expose the built-ins only, by name (e.g. `ll-arrow="chevron"`), and say in the docs that a custom arrow means forking the file - that is the whole point of a copy-paste package.
- [x] **Configuration phase (provider).** `llselectConfigProvider.defaults({...})`, per-element `ll-*` still wins, unknown keys throw. The open question - is the arrow really the only app-wide setting? - was settled by going through the actual settings surface rather than guessing, and the answer is no: `uiTranslationPack` is the strongest case of all (an app picks its language once, and llselect's chrome strings are not per-field copy) and the directives did not expose it at all before. Admitted: `arrow`, `filterable`, `popupWidthPolicy`, `uiTranslationPack`. Refused: `placeholder`, for the mirror-image reason - it IS per-field copy.
